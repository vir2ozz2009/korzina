## F4 · Реализация и проверка

- Ветка `task/F4-sessions`, начало от `219aaf9`; по ходу работы fast-forward до `e5d7207` с решениями D13 и S1/D17. Чужих незакоммиченных изменений не было. По ссылке карточки прочитан только `vir2ozz2009/Lavka/server/telegram-accounts.mjs` (blob `f3308499a104be77c71adb992c80c5187f35c3d7`): там хранение известных Telegram-аккаунтов, HMAC-валидатора нет. Код не копировался; проверка `initData` написана самостоятельно и сверена независимым контрольным вектором Node `createHmac`.
- DO: таблица `sessions`, случайный 256-битный токен, в SQLite только SHA-256, срок 30 дней, изоляция по магазину. Cookie с `HttpOnly`, `SameSite=Lax`, `Secure` вне localhost, отдельное имя на каждый shop ID; bearer для Mini App; неверный Authorization не подменяется cookie. Гость восстанавливается после eviction, logout удаляет запись. Telegram: WebAppData HMAC через Web Crypto, проверка подписи через `subtle.verify`, возраст до 24 ч, допуск часов вперёд 30 с, уникальные query-параметры, валидация ID; подмена, чужой бот, будущее, просрочка и malformed user отклоняются.
- D1: `accounts`, `memberships`, `seller_sessions`, `email_challenges`. Коды email — 6 случайных цифр, хеш привязан к challenge ID, TTL 10 мин, 5 попыток. Погашение/сессия/аккаунт — один атомарный D1 batch; nonce попытки предотвращает повтор и конкурентное погашение. Права не выдаются при входе автоматически. Заглушка возвращает `devCode` только на localhost, никогда в логах и на demo. Настоящая email-доставка не входит в F4. `PLATFORM_BOT_TOKEN` и `ENCRYPTION_KEY` не установлены на demo, Telegram там закрыт с 503 до настройки собственных ботов; работа при валидном секрете проверена в runtime. Токен магазина читается только из его зашифрованного `settings.telegram_bot_token` (AES-GCM, AAD = shop ID), ключ — отдельный secret. Привязка владельца по приглашению и кабинет остаются S1.
- `authenticateSeller` одним индексным JOIN читает живую сессию и членство через `withSession("first-primary")` при каждом запросе. `requireRole` и `requirePermission`: владелец — всё в своём магазине; сотрудник — orders/assembly/chat/products/stock по умолчанию, payments/refunds/payment_methods/publish/exports/team/bot — только по отдельному разрешению. Смена разрешений и `revoked_at` действуют на следующем запросе с той же cookie. Публичных команд выдачи ролей нет; подставленные клиентские заголовки роли/аккаунта не используются.
- Лимиты: IP в Worker/DO, 15 запросов/мин на платформенный auth, 30 на auth магазина, 120 на проверенную сессию покупателя или аккаунт продавца в магазине. 429 с Retry-After. Это ограничение всплесков в пределах изолята, не глобальная квота. Сами роли/сессии не кешируются.
- Команды auth проходят общий контроль Origin, размера, JSON и наличия Idempotency-Key. Секретные ответы сессий не складываются в idempotency; одноразовый код нельзя получить повторным выполнением. Бизнес-команды продолжают использовать механизм F3. Истёкшие записи отклоняются по TTL без фонового опроса; автоматическая уборка таблиц в F4 не добавлялась.
- `npm run check`: **109 тестов**, прежние не удалялись; build и dry run успешны. Проверены email-гонка, лимит попыток, guest/Telegram/bearer, logout, expiry, права/отзыв, отсутствие сырого токена в базе, cross-origin, разделение магазинов, индексный план проверки прав без SCAN. В тестах используются только синтетические секреты/адреса `korzina.invalid`. UI и MagicPath не применяются; историй с задачей F4 в индексе нет, их статусы не менялись.
- Локальный `platform:setup -- --local --seed` прошёл с `XDG_CONFIG_HOME=/tmp/korzina-cf-config`; стандартный путь в `/home/agent/.config` в этом окружении недоступен для записи.
- D1 demo `korzina-demo-platform`: новая миграция `0001_awesome_hedge_knight.sql` применена через авторизованный Cloudflare API атомарным batch и записана в `d1_migrations` до публикации; исходная `0000` сохранена. Новая DO-миграция `0002_hard_azazel.sql` применяется автоматически при первом запросе. Ресурсы Lavka не затрагивались.

- Коммит `0f76875672c10861d796321e24751fd3cdab5c62` влит fast-forward в `main`; Workers Builds `20398bae-2597-47c7-9530-b0e9c443e438` — `success`.
- Приёмка на `https://demo.korzina.app` через Cloudflare Browser Rendering, **390 × 844**: Korzina отображается; гость → 201 и cookie, чтение/повтор создания → тот же subject, чужой магазин → 401, logout → 200 и затем 401. Продавец-сотрудник → orders 200, payments/team 403, чужой магазин 403. После отдельного UPDATE permissions в D1 тот же session token дал payments 200; после UPDATE revoked_at — orders/payments 403, хотя сама сессия оставалась действительна (200). Это проверено на отдельных новых браузерных запросах, без переавторизации.
- Для проверки продавца создана только временная синтетическая запись `@korzina.invalid`, её membership, тестовая сессия и одноразовый challenge с хешем кода. На demo проверено погашение этого challenge → 200 и новая cookie, `/session` → 200, повтор кода → 401, logout → 200 и затем 401. Письмо не отправлялось: это проверка погашения кода, не доставки. `email/start` на demo корректно возвращает AUTH_UNAVAILABLE и не раскрывает devCode. Секретов ботов на demo нет; валидные/поддельные/просроченные Telegram-данные проверены в Workers runtime с синтетическими токенами, реальный Telegram не объявлен проверенным.

Гостевая тестовая сессия удалена через logout. Данные и секреты проверки в Git не записывались. Три браузерных прохода вернули `passed:true`.
