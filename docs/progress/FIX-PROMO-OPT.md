## Исправление и доказательства

- Исходный `calculatePromo`: AB/AC/BC по 150, A/B/C по 100 × 2 → **500**, регрессия ожидала 450 и упала. Исправленный: **450**, по одному комплекту, строки **150/150/150**.
- Перебираются частичные количества комплектов и допустимые распределения подарков по SKU. Мемоизация учитывает наличие ручного кода; равенство предпочитает автоматику. Нулевое применение — пропуск акции.
- Верхняя граница экономии по единицам отсекает только доказанно проигравшие ветви; итог всегда из допустимого целого сочетания. Лимитов числа акций и приближённой цены нет. Повторные одинаковые расчёты подсказок кешируются внутри запроса.
- Контракты, SQL, финансовый снимок существующих заказов и интерфейс не менялись. Пример продавца изолирует одну редактируемую акцию по прежнему контракту: каждая пара даёт 150; реальная корзина/заказ со всеми тремя — 450. Подмешивание других акций в пример не добавлялось.
- Локально: `check:fast` зелёный; `VITEST_MAX_WORKERS=1 npm run test:related`: **84 файла / 298 тестов**, 209,71 с (последовательный API-прогон). Новый выделенный API-файл проверен дополнительно; полный Check выполняется только в CI.
- Chromium 390 px: на исходном `group-pricing.ts` проверка ожидания 450 упала (видно 500); на исправленном **450 → 400 → 450 → reload → оформление**, PASS (12,5 с; запуск с сервером 43,3 с). API в браузерной фикстуре вызывает настоящий `calculatePromo`; настоящие storage/checkout отдельно проверяет API-тест. Физический iPhone не подменяется Chromium.
