# План разработки Korzina

Порядок строгий: задача начинается, когда закрыты её зависимости. Каждая задача — одна ветка, один чат Codex (иногда два), результат на demo.
Истории задачи (что должен получить пользователь) — `docs/stories/README.md`, колонка «Задача».
Формат карточки: **Цель** · **Читать** · **Figma** (блоки → `SCREENS.md`) · **Готово, когда**.

**Уровень модели Codex (выбирает Андрей в чате):** «Среднее» — экраны из готовых компонентов, правки текста и стилей, документы, чистка; «Высокое» — деньги, оформление и оплата, заказы и их статусы, права и сессии, миграции данных, архитектура и аудит.

Легенда фаз: **F** — фундамент · **B** — покупатель (волна 1) · **S** — продавец управляет магазином (волна 2) · **O** — жизненный цикл заказа (волна 3) · **L** — запуск · **A** — дополнения под флагами (волна 4+).

### F9 · Медиа: хранилище фото и файлов
- **Цель:** R2 `korzina-media` (demo и prod — отдельные бакеты) + выдача через Cloudflare Images; модуль `server/modules/media` и компонент `<Img>`.
- **Загрузка:**
  - на клиенте перед отправкой: сжатие до длинной стороны 2048 px и JPEG/WebP ~85% (продавец снимает на 12 МБ — уходит 1–2 МБ); HEIC с iPhone конвертируется в JPEG;
  - на сервере: проверка типа по содержимому (не по расширению), размер до 10 МБ, удаление EXIF (геолокация, модель камеры) у всех фото, повторная конвертация HEIC, если пришёл с компьютера;
  - файл привязан к магазину, владельцу, назначению (`product`, `logo`, `cover`, `payment_qr`, `receipt`, `chat`, `review`, `refund`) и статусу `temp` → `attached`.
- **Выдача** (PERFORMANCE §2 п. 9): публичные назначения (`product`, `logo`, `cover`, `payment_qr`) — по постоянной ссылке с ресайзом (размеры: 160, 400, 800, 1600) и кешем на год; приватные (`receipt`, `chat`, `review`, `refund`) — только через API с проверкой прав, короткоживущей подписанной ссылкой. `<Img>`: `srcset`, плейсхолдер цвета `input`, ленивая загрузка ниже экрана, ошибка → заглушка.
- **Уборка:** ежедневная задача — `temp`-файлы старше 24 ч удаляются; файлы удалённых товаров и сообщений — через 30 дней; архивный магазин — по отдельному решению.
- **Лимит:** 2 ГБ на магазин (значение в настройках платформы, меняется в админке); при превышении загрузка отклоняется с понятным сообщением, в кабинете виден объём «занято / доступно».
- **Готово, когда:** тесты — фото 12 МБ с телефона загружается и отдаётся в 4 размерах; в отданном файле нет EXIF-геолокации; HEIC открывается; приватный файл недоступен другому покупателю и другому магазину; `temp` старше суток удаляется задачей; при превышении лимита — `STORAGE_LIMIT`.

### F10 · CI, превью и скрипты проверки
- **Цель:** скрипты `check:fast` (типы + Biome + `check:arch`) и `test:related` (тесты по изменённым относительно `main` файлам); Vitest без лишней изоляции файлов, где это безопасно (сейчас ~7 с экономии); GitHub Action — `npm run check` один раз на ветку задачи, e2e — по метке `e2e` и раз в сутки; превью-версия Worker на ветку; Playwright-заготовка с одним smoke-тестом. Workers Builds тесты не повторяет.
- **Защита от раздувания (в `npm run check`):** `knip` — падает на неиспользуемых файлах, экспортах и зависимостях; бюджет размера сборки — JS первого экрана витрины — цель 135 / потолок 160 КБ gzip (PERFORMANCE.md §7), каждый ленивый чанк ≤ 60 КБ gzip (скрипт читает отчёт Vite); служебные страницы `/dev/*` и демо-экраны недоступны в prod-сборке (только local и demo).
- **Читать:** `TESTING.md`.
- **Готово, когда:** `knip` и бюджет размера проходят без исключений; PR показывает статус и ссылку на превью; `check:fast` ≤ 20 с, `check` ≤ 90 с — время записано в PROGRESS.md.

## Фаза AD — админка платформы (после S1)

Интерфейс для Андрея: создавать магазины для продавцов и управлять ими. Истории — `stories/platform-admin.md`. Экраны — `design-system/navigation.md` «Админка платформы». Оболочка — отдельная (Korzina-бренд, без магазина), шаблоны `list`, `form`, `order`.

### AD1 · Вход администратора, список и создание магазина
- **Цель:** роль `platform_admin` в D1 и команда `npm run admin:grant`; раздел `/admin` с проверкой роли; список магазинов; мастер создания из трёх шагов и экран результата с приглашением.
- **Важно:** мастер вызывает тот же серверный сервис `createShop`, что и `npm run shop:create` из F2. Если в F2 логика живёт только в CLI — сначала вынести её в `server/platform/` (без изменения поведения CLI), затем подключить к API. Вторую реализацию создания магазина не писать.
- **Читать:** `stories/platform-admin.md` (US-AD01–03), ARCHITECTURE §4–7, `design-system/navigation.md` «Админка платформы».
- **Готово, когда:** на demo Андрей создаёт магазин через `/admin`, получает ссылку-приглашение, продавец входит по ней в кабинет; тесты: без роли — `FORBIDDEN`, двойное создание — один магазин, занятый и зарезервированный slug отклоняются, в D1 хранится только хеш приглашения.

### AD2 · Карточка магазина, статусы, дополнения
- **Цель:** карточка магазина (US-AD04), смена статуса с последствиями для витрины и заказов (US-AD05), флаги магазина из реестра F5 (US-AD06), повторное приглашение.
- **Готово, когда:** приостановленный магазин не принимает новые заказы, но кабинет и текущие заказы работают; архив закрывает витрину и кабинет без потери данных; флаг включается одному магазину; всё пишется в журнал.

### AD3 · Журнал и адрес витрины
- **Цель:** общий журнал и журнал магазина (US-AD07), смена slug с перенаправлением со старого адреса на 90 дней (US-AD08).
- **Готово, когда:** любое действие AD1–AD2 видно в журнале; старый адрес открывает новый.

### AD4 · Импорт и экспорт магазина (сборка магазина нейросетью) — после S6
- **Цель:** формат «описание магазина» (`src/shared/contracts/shop-spec.ts`, zod) — данные магазина, оформление, категории, бренды, товары с фасовками, ценами, остатками и ссылками на фото, доставка и самовывоз, расписание, способы оплаты, владелец. Из схемы генерируется `docs/shop-spec.schema.json` и короткая инструкция для нейросети `docs/shop-spec-prompt.md` (как собрать файл из постов канала, прайса и фото продавца).
- **Импорт:** админка → «Импорт магазина»: файл описания + архив фото (или ссылки). Проверка без записи (dry run): ошибки с понятными подсказками по каждому полю, сводка «будет создано / изменено / удалено», предпросмотр витрины. Применение — одной командой с `Idempotency-Key`; фото проходят обычный конвейер F9 (сжатие, HEIC, EXIF). Новый магазин создаётся в статусе `черновик`. То же из консоли: `npm run shop:import -- <файл> [--dry-run]`.
- **Экспорт и повторный импорт:** «Скачать описание» любого магазина в том же формате; повторный импорт сопоставляет записи по стабильным ключам (`key` у категорий, товаров, фасовок, зон) и применяет только разницу, без дублей. Удаление — только явным флагом, по умолчанию отсутствующее в файле не удаляется.
- **Читать:** `stories/platform-admin.md` (US-AD09), `DOMAIN.md`, PERFORMANCE §1 (импорт пакетами, один проход по базе).
- **Готово, когда:** магазин из файла (≈50 товаров, 3 категории, доставка, оплата) создаётся за один импорт и выглядит на витрине как собранный руками; экспорт → импорт без изменений даёт «0 изменений»; ошибка в цене или пустое обязательное поле видны в dry run и не попадают в базу; тест изоляции — импорт не трогает другие магазины.
