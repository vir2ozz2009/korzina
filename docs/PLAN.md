# План разработки Korzina

Порядок строгий: задача начинается, когда закрыты её зависимости. Каждая задача — одна ветка, один чат Codex (иногда два), результат на demo.
Истории задачи (что должен получить пользователь) — `docs/stories/README.md`, колонка «Задача».
Формат карточки: **Цель** · **Читать** · **Figma** (блоки → `SCREENS.md`) · **Готово, когда**.

Легенда фаз: **F** — фундамент · **B** — покупатель (волна 1) · **S** — продавец управляет магазином (волна 2) · **O** — жизненный цикл заказа (волна 3) · **L** — запуск · **A** — дополнения под флагами (волна 4+).

---

## Фаза F — фундамент (до первого экрана)

Без неё каждая страница будет изобретать своё — это и тормозило Lavka.

### F1 · Чистый каркас
- **Цель:** репозиторий пустой (код удалён 17.11.2026, сохранены `cloudflare.config.ts`, `.node-version`, `.codex/`, `public/brand/korzina.svg`). Создать `package.json` и каркас Vite + React + TS strict + Tailwind v4 + Biome + Vitest + Hono в том же Worker. Скрипты `dev`, `build`, `check`, `check:arch` (CONVENTIONS «Автоматическая проверка»), `deploy`.
- **Читать:** ARCHITECTURE §2–3, CONVENTIONS.
- **Готово, когда:** `npm run check` зелёный; на demo открывается пустая страница Korzina, `GET /api/health` → `{ok:true}`; Workers Builds проходит.

### F2 · Магазины: платформа + Durable Object
- **Цель:** D1 `platform` (shops, domains), DO `Shop` с Drizzle и автоприменением миграций, `resolveShop(host)`, сид из двух магазинов (`lavka`, `test2`).
- **Читать:** ARCHITECTURE §4–5, §8.
- **Готово, когда:** `GET /api/shop` возвращает разные магазины для разных host и `?shop=`; тест изоляции: запись в `lavka` не видна в `test2`.

### F3 · Контракты, ошибки, идемпотентность
- **Цель:** `src/shared/contracts`, `errors.ts`, `money.ts` (+ тесты), Hono RPC-клиент, middleware: request-id, формат ошибок, `Idempotency-Key` (таблица `idempotency` в DO), лимит запросов. Экономия запросов (PERFORMANCE §1, §6): `server/metrics.ts` — счётчик SQL и строк на запрос (обёртка над доступом к базе DO), выборочная запись метрики без персональных данных; помощник ревизий (`If-None-Match`/`?rev=` → `304`/`unchanged`); шаблон теста бюджета `*.budget.test.ts`.
- **Читать:** PERFORMANCE §1, §6.
- **Готово, когда:** повтор POST с тем же ключом возвращает тот же ответ, с другим телом — `IDEMPOTENCY_CONFLICT`; `money.ts` покрыт тестами распределения и округления; метрика запроса содержит число SQL и строк; пример бюджет-теста падает при превышении.

### F4 · Сессии и роли
- **Цель:** гостевая сессия, проверка Telegram `initData` (HMAC, срок), вход продавца (Telegram платформы или код на email — заглушка отправки в dev), `memberships`, `requireRole`/`requirePermission`.
- **Читать:** ARCHITECTURE §7, DOMAIN «Роли». Пример проверки initData: Lavka `server/telegram-accounts.mjs` (только как справку).
- **Готово, когда:** тесты: поддельная или просроченная initData отклоняется; сотрудник без права получает `FORBIDDEN`; отозванный доступ гаснет сразу.

### F5 · Флаги функций
- **Цель:** реестр `flags.ts` (`addon`, `rollout`), `feature_overrides`, `requireFeature`, `useFeature`, скрипт `npm run flag`.
- **Готово, когда:** addon выключен по умолчанию, включается для одного магазина, второй его не видит; core без флага.

### F6 · Токены, шрифт, тема MagicPath
- **Цель:** подключить готовый `src/styles/tokens.css` и Inter Variable; механизм оформления витрины (`src/shared/theme-presets.ts`: стиль на `<html>` от Worker; тесты: контраст пресетов, `deriveTheme` для светлых, тёмных и ярких цветов, отклонение почти белых; в `/dev/kit` переключатель пресетов и поле своего цвета); создать в MagicPath отдельный проект **«Korzina»** (ID записать в DESIGN.md §5) и тему **Korzina** из тех же значений; знак и иконка приложения из `public/brand/korzina.svg`.
- **Читать:** DESIGN §2, `design-system/tokens.md`.
- **Готово, когда:** `get-theme Korzina` совпадает с `tokens.css`; классы `bg-primary`, `text-title-2`, `rounded-xl` работают; на demo видна страница с палитрой и типографикой.

### F7 · UI-кит + витрина кита
- **Цель:** все компоненты из `design-system/components.md` в `src/ui`, страница `/dev/kit` со всеми вариантами и состояниями; тот же кит компонентом «Korzina UI Kit» на холсте MagicPath.
- **Читать:** DESIGN §3, §5, `design-system/components.md`. **Figma:** узлы из колонки «Эталон».
- **Готово, когда:** Андрей одобрил кит на холсте; `/dev/kit` на demo; `check:arch` без исключений.

### F8 · Каркас приложения, шаблоны и переходы
- **Цель:** TanStack Router, оболочки витрины и кабинета, 8 шаблонов экранов, `Screen`/`Header`/`QueryBoundary`/`SheetRoute`/`Transition` (push, sheet, tab), адаптер Telegram (viewport, safe-area, BackButton, тема, раскрытие на всю высоту), тосты, восстановление прокрутки, десктоп — колонка по центру.
- **Также:** `src/app/query-defaults.ts` — `staleTime` по типам данных, объединение запросов, точечная инвалидация, остановка опросов в скрытой вкладке (PERFORMANCE §3); разделение кода по маршрутам (витрина / кабинет / админка).
- **Читать:** PERFORMANCE §3, DESIGN §3–4, `design-system/templates.md`, `design-system/reference-screens.md`, «Оболочки» в `design-system/navigation.md`, CONVENTIONS «Экраны».
- **Готово, когда:** восемь шаблонов на демо-данных и три демо-маршрута показывают все виды переходов; «назад» работает жестом, кнопкой браузера и BackButton в Telegram; состояния загрузки, пусто и ошибки демонстрируются на флаге `?simulate=`.

### F9 · Медиа: хранилище фото и файлов
- **Цель:** R2 `korzina-media` (demo и prod — отдельные бакеты) + выдача через Cloudflare Images; модуль `server/modules/media` и компонент `<Img>`.
- **Загрузка:**
  - на клиенте перед отправкой: сжатие до длинной стороны 2048 px и JPEG/WebP ~85% (продавец снимает на 12 МБ — уходит 1–2 МБ); HEIC с iPhone конвертируется в JPEG;
  - на сервере: проверка типа по содержимому (не по расширению), размер до 10 МБ, удаление EXIF (геолокация, модель камеры) у всех фото, повторная конвертация HEIC, если пришёл с компьютера;
  - файл привязан к магазину, владельцу, назначению (`product`, `logo`, `cover`, `payment_qr`, `receipt`, `chat`, `review`, `refund`) и статусу `temp` → `attached`.
- **Выдача** (PERFORMANCE §2 п. 9): публичные назначения (`product`, `logo`, `cover`, `payment_qr`) — по постоянной ссылке с ресайзом (размеры: 160, 400, 800, 1600) и кешем на год; приватные (`receipt`, `chat`, `review`, `refund`) — только через API с проверкой прав, короткоживущей подписанной ссылкой. `<Img>`: `srcset`, плейсхолдер цвета `input`, ленивая загрузка ниже экрана, ошибка → заглушка.
- **Уборка:** ежедневная задача — `temp`-файлы старше 24 ч удаляются; файлы удалённых товаров и сообщений — через 30 дней; архивный магазин — по отдельному решению.
- **Лимит:** 2 ГБ на магазин (значение в настройках платформы, меняется в админке); при превышении загрузка отклоняется с понятным сообщением, в кабинете виден объём «занято / доступно».
- **Готово, когда:** тесты — фото 12 МБ с телефона загружается и отдаётся в 4 размерах; в отданном файле нет EXIF-геолокации; HEIC открывается; приватный файл недоступен другому покупателю и другому магазину; `temp` старше суток удаляется задачей; при превышении лимита — `STORAGE_LIMIT`.

### F10 · CI и превью
- **Цель:** GitHub Action: `npm run check` на PR; превью-версия Worker на ветку; Playwright-заготовка с одним smoke-тестом.
- **Готово, когда:** PR показывает статус проверок и ссылку на превью.

### B1 · Модель каталога + сид

## Фаза AD — админка платформы (после S1)

Интерфейс для Андрея: создавать магазины для продавцов и управлять ими. Истории — `stories/platform-admin.md`. Экраны — `design-system/navigation.md` «Админка платформы». Оболочка — отдельная (Korzina-бренд, без магазина), шаблоны `list`, `form`, `order`.

### AD1 · Вход администратора, список и создание магазина
- **Цель:** роль `platform_admin` в D1 и команда `npm run admin:grant`; раздел `/admin` с проверкой роли; список магазинов; мастер создания из трёх шагов и экран результата с приглашением.
- **Важно:** мастер вызывает тот же серверный сервис `createShop`, что и `npm run shop:create` из F2. Если в F2 логика живёт только в CLI — сначала вынести её в `server/platform/` (без изменения поведения CLI), затем подключить к API. Вторую реализацию создания магазина не писать.
- **Читать:** `stories/platform-admin.md` (US-AD01–03), ARCHITECTURE §4–7, `design-system/navigation.md` «Админка платформы».
- **Готово, когда:** на demo Андрей создаёт магазин через `/admin`, получает ссылку-приглашение, продавец входит по ней в кабинет; тесты: без роли — `FORBIDDEN`, двойное создание — один магазин, занятый и зарезервированный slug отклоняются, в D1 хранится только хеш приглашения.

### AD2 · Карточка магазина, статусы, дополнения
- **Цель:** карточка магазина (US-AD04), смена статуса с последствиями для витрины и заказов (US-AD05), флаги магазина из реестра F5 (US-AD06), повторное приглашение.
- **Готово, когда:** приостановленный магазин не принимает новые заказы, но кабинет и текущие заказы работают; архив закрывает витрину и кабинет без потери данных; флаг включается одному магазину; всё пишется в журнал.

### AD3 · Журнал и адрес витрины
- **Цель:** общий журнал и журнал магазина (US-AD07), смена slug с перенаправлением со старого адреса на 90 дней (US-AD08).
- **Готово, когда:** любое действие AD1–AD2 видно в журнале; старый адрес открывает новый.
