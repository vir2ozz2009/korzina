## 1. Короткие пути
| Задача | Путь и результат |
|---|---|
| Найти покупателя | Главная кабинета → «Покупатели» → поиск имени/телефона → карточка. Отдельного промежуточного меню нет |
| Из текущего заказа | Нажать имя покупателя → карточка; назад возвращает тот же заказ |
| Дать выгоду | Карточка → «Дать скидку» → одна шторка: значение, срок, сводка → «Выдать скидку». Два нажатия плюс ввод; не считаем поиск частью этих двух нажатий |
| Выдать код | В той же шторке раскрыть «Дополнительно» → «По промокоду»; код генерируется сервером. Дополнительный путь сознательно длиннее |
| Применить | Личная скидка применяется автоматически после входа. Код: профиль/корзина → «Использовать»; повторный ввод не нужен |
| Отозвать | Карточка предложения → «Отозвать» → подтверждение с получателем и выгодой. Старые заказы сохраняют снимки |
| Написать | У строки заказа — существующий чат; «Сообщения по заказам» открывает единственный доступный чат либо выбор заказа, если их несколько |

Список, поиск, выбранный фильтр и прокрутка восстанавливаются при «Назад». Прямая ссылка проверяет магазин/права и имеет возврат в список. Перезагрузка читает серверное состояние; незавершённая выдача не публикуется.
Смена магазина/аккаунта очищает данные предыдущего; поздний ответ старого запроса не подменяет новый экран. Telegram BackButton и браузерный Back используют текущий роутер.

### 1.1 Размещение в существующих экранах

Предусмотреть второй вход «Продвижение → Личные предложения», обсуждённый с Андреем. Это один реестр/форма/история, не копия предложений карточки.
В реестре: покупатель, выгода, срок, статус; «Действующие» по умолчанию, «История» для использованных/истёкших/отозванных. Поиск по имени/телефону по правилам §2, 10 + ещё; порядок — дата выдачи убыванию, затем ID. Нажатие строки открывает то же предложение; ссылка покупателя открывает карточку при праве orders.
«Создать» → поиск/выбор подтверждённого покупателя текущего магазина → та же форма §3 с фиксированным получателем. Поиск получателя для owner/manager не выдаёт всю историю заказов без orders. Назад из формы сохраняет выбранного покупателя в текущем сеансе; выход без выдачи не создаёт предложение. Нет покупателей/совпадений — объяснение без ручного создания аккаунта.
Из карточки шаг выбора пропускается. Из обоих входов доступны одни и те же выдача/отзыв/повтор, идентификатор, ревизия, статус и лимит. Обновление отражается в обоих местах при следующем чтении/инвалидации, без дублей.
Права реестра — owner/manager (§6). При выключенных «Акциях» доступна история/отзыв, создание заблокировано. Общий список акций сохраняется отдельно, личные предложения туда не подмешиваются.
Возврат после просмотра/отзыва ведёт в фактический источник: карточку покупателя либо реестр продвижения, сохраняя фильтр/поиск/прокрутку. Deep link без источника возвращает в реестр при доступе; иначе — безопасный разрешённый корень.

## 2. Покупатели и карточка
- Источник — реальные заказы текущего магазина. Список появляется автоматически, без ручного создания клиента. Включаем покупателей с любым оформленным заказом, включая отменённый; посетителей без заказа не включаем.
- Одна запись на серверную личность в магазине. Для гостя — существующая гостевая личность, не телефон. Два аккаунта с одним телефоном остаются разными.
- Поиск по имени без учёта регистра и по нормализованным цифрам телефона; минимум 2 символа имени либо 4 цифры. Телефон в поиске — только контакт, не право доступа. Одинаковые совпадения показываются отдельно с последним заказом.
- Строка: имя (либо «Покупатель без имени»), доступный телефон, дата последнего заказа, число заказов в работе. Сортировка по последнему оформленному заказу убыванию, затем стабильный ID.
- По 10 строк + «Показать ещё». Поиск работает по всей базе, не только загруженным строкам. Без конструктора фильтров, рейтинга клиентов и сегментов.
- Карточка: имя/телефон с «Копировать», статус «Гость» при необходимости; сводка за всё время; «Дать скидку»; действующие личные предложения; последние 3 заказа и «Все заказы»; «Сообщения по заказам».
- История: все состояния, новые сверху, 10 + ещё; простые фильтры «Все / В работе / Выполнены / Отменены», суммы из заказа, переход в существующий заказ. «В работе» в сводке сразу открывает соответствующую историю.
- Чат не создаётся заново: только существующий по заказу; закрытый чат остаётся для чтения, отсутствие доступного чата объясняется. Не показывать кнопку отправки там, где сервер её запрещает.
- Телефон берётся из последнего доступного контакта заказа этой личности в этом магазине; если его нет — «Телефон не указан», без копирования. Общий профиль и контакты других магазинов не раскрываются.
- Не добавляем редактирование личных данных продавцом, заметки, ручное объединение, импорт, день рождения и обязательную регистрацию.

### 2.1 Показатели без второй бухгалтерии
«Всего заказов» — все оформленные; «В работе» — текущая группа; «Выполнено» — completed.
«Сумма покупок» — показатель выручки O9, ограниченный покупателем, за всё время: выполненные заказы после скидок, доставка магазину и проведённые возвраты по П3/§9.2. Не путать с подтверждёнными денежными поступлениями.
«Средний чек» — та же сумма / число выполненных заказов с положительной остаточной стоимостью (§9.1 O9); если знаменатель 0 — «—».
«Последняя покупка» — дата последнего выполнения; полный возврат не стирает дату фактической покупки. Если выполнений нет — «Ещё не покупал».
Поздний возврат меняет сводку, повтор выплаты не вычитает сумму второй раз. Отмена не увеличивает покупки. Недостаточная история — пометка неполноты по O9, не выдуманный ноль.
Пример: completed 1000 и 500, возврат товаров 200 из первого, отменённый 700 → сумма 1300, выполнено 2, средний 650. Полный возврат второго → сумма 800, выполнено 2, средний 800.
Денежные показатели требуют права O9 (`payments` либо owner); без него сервер не возвращает суммы сводки. Суммы доступных заказов остаются в границах текущего права просмотра заказов.

## 3. Одна форма личного предложения
Получатель и магазин уже выбраны; менять получателя в форме нельзя. «Дать скидку» доступно только подтверждённому аккаунту Telegram, владельцу/управляющему и при включённых «Акциях».
Гость видит в карточке продавца пояснение «Личные предложения доступны после входа покупателя через Telegram», без предложения угадать аккаунт по телефону.

| Поле | Правило спецификации |
|---|---|
| Цель | «На следующий заказ» по умолчанию; «Постоянная скидка»; «Вернуть покупателя» |
| Размер | % или сумма в валюте магазина; значение обязательное, пустое по умолчанию. Никакой скидки без явного выбора продавца |
| На следующий заказ | 1 выигравшее применение; старт сейчас; срок 7 календарных дней, включая сегодня, до конца последнего дня по времени магазина |
| Постоянная скидка | Автоматическая, многократная, без срока по умолчанию; срок можно задать |
| Вернуть покупателя | Та же разовая автоматическая скидка на 7 дней; отличается подписью цели. Не проверяет «давно не покупал», не запускает робота/рассылку |
| Срок | 7 / 30 календарных дней, своя конечная дата, без срока; выбранное окончание включительно. Показывать точную дату, старт сразу. Нет отложенного старта |
| Дополнительно | Минимальная сумма; товары/фасовки/категории; максимум суммы для процента; способ «Автоматически / По промокоду». По умолчанию все товары с обычной ценой, без минимума, без максимума |
| Код | Для разовых предложений; сервер генерирует уникальную строку в магазине, без имени/телефона/ID в ней. Ручное переименование и публичность исключены |
| Проверка | Сводка на этой же форме: кому, сколько, на что, минимум, срок, число применений, способ получения. «Выдать» — явное подтверждение этой сводки |
| Пример | Необязательный «Посмотреть пример» использует общий калькулятор с личностью получателя; см. §3.1 |
| Уведомление | Показать доступность: «Бот сообщит» либо конкретную причину, почему не сообщит. Не запрашивать включение уведомлений от имени покупателя |

Процент >0 и ≤100; фиксированная сумма >0 с точностью валюты; минимум ≥0; максимальная скидка >0; выбранные товары не пусты. Пределы значений — §13 и существующий контракт promo, не свободные строки.
100% явно подписывается в сводке как «Бесплатные подходящие товары»; доставка не становится бесплатной.
13.1 ограничен скидками на корзину: личная цена отдельной позиции, личная доставка, N+M, наборы и произвольный лимит N применений не входят.
В действующем предложении условия не редактируем: «Повторить» открывает новый проект; прежнее действует до явного отзыва/замены. Отозванное не «включается» обратно. Это проектное упрощение для личных предложений, не изменение общих акций 12.1.
Одна постоянная автоматическая скидка на покупателя: новая выдача предлагает явную замену; подтверждение атомарно отзывает старую и выдаёт новую, при ошибке старая действует. Разовых может быть несколько; выдача другой не отзывает предыдущие.

### 3.1 Проверка на примере
Не читать живую корзину покупателя для продавца. Только при праве orders предзаполнить учебный пример последним заказом этого покупателя, пересчитанным по текущим ценам/доступности; отметить исключённые позиции и изменения. Без orders или при отсутствии подходящих строк — сразу выбор товаров без раскрытия истории/суммы последнего заказа.
Показать результат без нового предложения, с ним, фактически выигравшую скидку и итог. Это прогноз, не обещание цены будущего заказа.
Пример не меняет заказы/корзины/лимиты и не оформляет заказ. При ошибке примера выдача допустима после валидной сводки; нельзя писать, что расчёт проверен.
Если действующий код/акция выгоднее, объяснить это. Проверка повторяется сервером на реальной корзине.

## 4. Получение покупателем
- Профиль → «Ваши доступные предложения»: личные и доступные публичные предложения текущего магазина, с источником «Для вас»/«Акция магазина», условиями и сроком. Скрытые неперсональные коды не раскрываются.
- В корзине переименовать существующий вход «Доступные акции» в «Доступные предложения» и расширить тот же список, без второго поля промокода и без дублирующих блоков.
- Автоматическая скидка: «Применится автоматически», после выигрыша «Личная скидка −…». Никакой активации/кнопки «Получить».
- Код: «Использовать» передаёт его в существующее поле корзины. При другом введённом коде подтвердить «Заменить код …?»; затем серверный пересчёт, даже если новый код проигрывает. Отмена сохраняет старый.
- Пустая корзина: код можно сохранить в ней; показать «Добавьте товары» и переход в каталог, не объявлять применение. Автоскидка ожидает подходящие товары.
- Активное, но неподходящее предложение остаётся в списке: объяснить минимум, товары, обычную цену либо более выгодную скидку. Истёкшее/использованное/отозванное не показывать активным.
- Если список пуст, вход скрывается; прямая ссылка — «Нет доступных предложений» и переход в магазин.
- Ссылка из бота ведёт в предложение текущего магазина; до входа не раскрывать чужие условия. После Telegram-входа сохранить намерение и проверить получателя. Само открытие ссылки не расходует и не вводит код.
- Чужой аккаунт/магазин получает нейтральное «Предложение недоступно» без имени получателя. Гость — предложение войти, обычное оформление без личной выгоды остаётся доступно.
- Выход очищает личные предложения и код в клиентском представлении, серверные данные аккаунта сохраняются. Повторный вход перечитывает права и актуальность.

## 5. Расчёт и жизненный цикл
Используем promo §4–6 и один серверный расчёт: личная скидка/код — кандидат общей скидки на корзину, не отдельное суммирование.
- Сравнивать итог всего заказа с известной доставкой и действующими позиционными акциями. При неизвестной доставке не обещать окончательную экономию.
- Одна скидка на корзину и один введённый код, включая доставку/набор. Промокод на товары действует на обычные цены; N+M, цены по акции и комбо сохраняют текущие правила.
- Равенство итогов: автоматическая скидка перед введённым кодом; среди автоматических — общая акция магазина (любого лимита), личная постоянная, личная разовая. Внутри общих акций сохраняется нынешний порядок по ID; внутри личных разовых — ближайшее окончание (без срока последним), затем более ранняя выдача, затем ID. Это уточнение Q2 (§10). Группы/доставка и выбор лучшего общего итога сохраняют правила 12.x; новый порядок применяется только после равенства итогов, не взамен сравнения выгод.
- Проигравшее предложение не расходуется; «выбрано в корзине» не означает «использовано». Только победитель расходует применение в транзакции оформления.
- Две параллельные корзины на последнее применение: выигрывает одна транзакция; второй расчёт меняется с объяснением. Повтор оформления с тем же ключом не создаёт заказ или расход.
- Полная отмена до выдачи один раз восстанавливает лимит по promo §6; предложение снова доступно лишь если ещё действует. Частичный возврат и полный возврат после выдачи лимит не восстанавливают.
- Отзыв/истечение/выключение «Акций» меняет открытые корзины, но не снимки оформленных заказов. Рост суммы требует QUOTE_CHANGED и согласия покупателя.
- Гонка «отзыв ↔ оформление»: оформление до отзыва сохраняет снимок; после отзыва использовать предложение нельзя.
- Статусы продавцу: действует, использовано (разовое), истекло, отозвано; использование многократного отображается числом и ссылками на заказы. «Применено» — состояние текущей корзины, не статус предложения.
- История выдачи/отзыва/замены/использования: время, сотрудник, ревизия, условия, заказ; 10 + ещё. Статус вычисляет сервер: отозвано → истекло → использовано (разовое без свободного применения) → действует. Это приоритет отображения; все фактические события сохраняются. Выключенный флаг — отдельная пометка «Акции выключены», а не пятый статус.
- Выключение дополнения не останавливает календарный срок и не обнуляет лимиты; повторное включение не возрождает истёкшее.

## 6. Права, личность, данные и уведомления
| Область | Граница |
|---|---|
| Список/карточка/заказы | owner или действующее право orders, только текущий магазин; чат отдельно по chat. Телефон не даёт полномочий |
| Денежная сводка | Право O9: owner или payments; без права сервер исключает поля |
| Выдача, отзыв и история предложений продавцу | owner или teamRole manager, как текущий sellerPromoRoutes; не наследовать это от orders/payments |
| Покупатель | Только собственный account + shop; проверять на чтении, вводе кода, quote и checkout |
| Гостевой вход | Использовать существующее подтверждённое слияние гостевой сессии с Telegram. Не связывать других гостей по совпавшему телефону |
| Слияние | История переносится существующим merge; сводка пересчитывается без дублей. Личные предложения гостям не выдаются. Лимиты и расход сохраняются при переносе существующих promo_uses |
| Копирование магазина | Не переносить покупателей, личные предложения, коды, расход и события уведомлений. Новый магазин не наследует чужие данные |
| Недоступная личность | Не выдавать и не применять предложения недействительной/удалённой личности, остановить её уведомления. В main нет покупательского API удаления аккаунта; новый процесс удаления в 13.1 не создаётся. При добавлении такого процесса он обязан отзывать предложения и сохранять финансовые снимки по DOMAIN; повторная регистрация не наследует их. Контракт недействительной личности проверяется серверным тестом, UI удаления не рисовать |
| Отзыв сотрудника | На каждом запросе свежая проверка; очистить данные открытого экрана при получении отказа. Запоздавший ответ не раскрывает их снова |

Выдача + событие уведомления фиксируются атомарно. Повтор команды = тот же результат; одинаковый ключ с другим телом отклоняется. Параллельные изменения используют ожидаемую ревизию.
Бот магазина сообщает один раз о новой выдаче только при согласии на акции и доступном канале. Согласие повторно проверяется перед отправкой; отозванные/истёкшие предложения до отправки не отправляются.
При выключенных уведомлениях/блокировке бота предложение всё равно доступно в профиле. Продавцу: «Выдано, уведомление не отправлено» с причиной. Успешная выдача не откатывается из-за Telegram.
Повторы очереди не создают новое предложение и повторное подтверждённо отправленное сообщение. При неоднозначном таймауте Telegram не обещать exactly-once: сохранить неизвестный результат, не слать автоматический дубль; показать неопределённость.
Массовая рассылка, свободный текст, ручная кнопка многократной отправки, SMS/email и гарантии прочтения не входят.

## 7. Зависимости и требования к реализации
1. A13b первым: идентичность + выборка/поиск/права → сводка O9 → карточка/заказы/чат. Никакого нового CRM-сервиса.
2. A12 вторым: расширить текущий promo привязкой получателя и жизненным циклом → quote/checkout/лимиты/отмена/возврат → профиль/корзина → очередь бота.
3. Серверные контракты до экранов: список (query, cursor, revision), summary с allowedActions, история заказов; личное предложение (id, shop/account, terms, revision, status, uses, deliveryStatus), команды выдачи/отзыва/замены, чтение предложений и пример. Поля/операции и ошибки определены в §§13–14; shared contracts должны выразить их до UI.
4. Новая миграция/индексы без переноса личных данных между магазинами; запросы по shop/identity, курсоры стабильны; нет N+1 и полного сканирования заказов на каждой строке.
5. Ревизии/инвалидация при заказе, выполнении, возврате, слиянии, выдаче/отзыве, сроке и смене флага. Частные данные не попадают в общий кеш, URL, логи и телеметрию.
6. Сводка/заказы/предложения загружаются независимо: сбой одного блока не прячет остальные. Offline — показать сохранённое с пометкой; выдача/отзыв/применение без серверного подтверждения не объявляются успешными.
7. Каркас/UI-kit из main, 360/390 px, касания ≥44 px. Если требуется больше трёх новых компонентов — отдельная задача по AGENTS.
8. Покупатели доступны независимо от «Акций»; личные предложения используют существующий promotions, не новый переключатель. Выключение прячет покупательские входы, продавцу сохраняется доступ к истории/отзыву, выдача блокируется.
9. Проверка существующих точек: buyer/merge, promo/routes+calculate+uses, checkout, O9, profile, chat, bot queue. Это адресное расширение, не аудит всего проекта.

## 11. Процессы: вход, действие, результат
Все push-переходы используют штатный роутер; sheet закрывается в тот же источник. Прямая ссылка содержит только непрозрачный ID и магазин, без телефона/имени/кода. При входе намерение сохраняется в текущем сеансе, после проверки личности открывается тот же объект либо нейтральная ошибка. Смена магазина требует обычного подтверждённого контекста магазина, не подменяет tenant по ID.

| ID / вход | Шаги и запросы (§13) | Завершение / возврат / исключение |
|---|---|---|
| P01 · Главная кабинета | «Покупатели» → push S1 → Customers.list; имя/телефон фильтруют серверный список; строка → push S2 → customer + summary + orders + offers независимо | Back сохраняет запрос/страницу/позицию. После reload восстанавливаются маршрут/фильтр, данные заново; прокрутка может начаться сверху |
| P02 · Заказ | Имя при orders → push S2; «Все заказы»/«В работе» → push S3 с фильтром; заказ → существующий order | Назад возвращает в исходный заказ либо S2. Имя не ссылка без orders; отправка чата отдельно проверяет chat и текущий срок переписки |
| P03 · Выдача из карточки | «Дать скидку» → sheet S5; recipient фиксирован, форма по умолчанию «На следующий заказ», % без значения, 7 дней, авто; заполнить → Offer.issue | Во время записи заблокированы поля/повторная выдача; успех закрывает форму, возвращает S2, новая строка + «Скидка выдана». Таймаут не закрывает форму: проверить тем же ключом |
| P04 · Выдача из продвижения | «Личные предложения» → push S4; «Создать» → sheet выбора получателя S4a → S5 внутри той же шторки → Offer.issue | Успех возвращает S4, новая строка. Back S5→S4a сохраняет проект только в памяти; смена получателя сбрасывает пример/расчёт. Закрытие изменённого проекта требует подтверждения |
| P05 · Постоянная уже есть | S5 показывает старую выгоду, срок; CTA «Заменить постоянную скидку» → подтверждение с обеими сводками → issue с replaceId + expectedRevision | В одной транзакции новая выдача + отзыв прежней + события + один outbox. Конфликт перечитывает прежнюю, требует нового подтверждения. При ошибке прежняя действует |
| P06 · Просмотр/отзыв/повтор | Строка → push S6; «Отозвать» → feedback «Отозвать скидку для {имя}?» → Offer.revoke; «Повторить» → S5 | Отзыв с ревизией, без уведомления об отзыве и без отмены заказа. Повтор копирует условия/цель, новый разовый срок 7 дней, постоянный без срока, новый код при выдаче; прежний код не копируется |
| P07 · Покупатель | Профиль → push S7; авто: только условия; личный код «Использовать» → проверка замены → существующая команда кода корзины → корзина | Сам просмотр/вход ничего не расходует. При ошибке остаётся прежний код. Применить при невыгодности можно, UI сообщает проигрыш; другой код не суммируется |
| P08 · Оформление | Существующий quote → сервер проверяет получателя/срок/флаг/лимит → checkout с прежним idempotency | Победитель расходуется вместе с заказом. При гонке новое quote; рост требует согласия. Снижение отражается штатным обновлением итогов. Лимит не расходуется на резерв/просмотр |
| P09 · Отмена/возврат | Штатная отмена до выдачи → освободить единственный расход в одной транзакции; возвраты после выдачи → штатные снимки/распределение | Освобождение не снимает отзыв/истечение и не создаёт новый срок. Повтор команды/события ничего не восстанавливает повторно. Не изменять snapshot заказа |
| P10 · Уведомление | Покупатель включает S8 → preference.set; новая выдача создаёт событие; отправитель повторно проверяет согласие, получателя, флаг, срок, канал | Успех «Отправлено»; отказ/недоступность «Не отправлено» + причина; таймаут «Результат отправки неизвестен». Включение согласия не рассылает старые предложения |
| P11 · Флаг/права/аккаунт изменились | На фокусе/мутации свежая проверка; недоступные секции очищаются; quote пересчитывается | История продавцу с прежними правами доступна при promotions=false, выдача/применение запрещены; вкладка покупателей работает. Выход/смена аккаунта очищает приватный кеш |

Отмена изменённой S5: «Закрыть без выдачи?» / «Продолжить» / «Закрыть». Черновик существует только в памяти текущего сеанса; reload/закрытие приложения его удаляет. Отправленная команда при обрыве не считается отменённой: следующая попытка использует прежний ключ и проверяет результат; до выяснения нельзя начать вторую выдачу этого проекта.
Дата окончания выбирается при открытии/изменении срока и показана явно. Публикация после полуночи её молча не сдвигает; дата в прошлом требует выбора новой. 7 дней = сегодня + 6 дней включительно, 30 = +29; сервер хранит исключительную границу следующей полуночи по поясу магазина. Без срока — null. Своя дата не раньше сегодняшней; отсроченного начала нет.

Имена/телефоны S1/S2/S4a — последние непустые значения контакта заказа этой личности в этом магазине; новый Telegram displayName другого магазина их не подменяет. При сомнении продавец выдаёт предложение из нужного заказа через карточку, не объединяет аккаунты.
Список S7: сначала личные (раньше истекающие, без срока последними, затем issuedAt/id), затем публичные по текущему порядку. 10 + ещё, без дублей; предложение показывается при доступности личности/периода/лимита, даже если текущая корзина не подходит. Одна и та же персональная запись не попадает вторично как публичная.

## 13. Данные, команды и согласованность
Это контракты поведения до кода, не предписание новых таблиц/роутеров. Имена ниже — имена shared schemas/операций; HTTP-маршруты и файлы выбирает Codex в текущих модулях. Все сущности берутся с сервера, shop определяется авторизованным контекстом, account для покупателя — из сессии, не из тела запроса.

| Контракт | Обязательные поля / ограничения |
|---|---|
| CustomerRef | id: opaque string; displayName: string; phone: string или null; confirmed: boolean; lastOrderAt: ISO timestamp; revision: opaque string. ID scoped shop; не Telegram ID в публичном URL |
| CustomerSummary | revision; totalOrders/inProgress/completed: integer≥0; lastCompletedAt: ISO/null; historyComplete: boolean; money только payments: purchasesMinor: integer, averageMinor: integer/null, currency. Расчёт §2.1, округление O9 |
| PersonalOffer | id, revision, recipientId, goal: next/permanent/return; kind: automatic/code; discount: percent(basisPoints 1..10000) либо fixed(amountMinor 1..1e9); scope: all/products/variants/categories + ids (1..50, один тип); minSubtotalMinor: integer 0..1e9; capMinor: null либо 1..1e9 только %; issuedAt/expiresAt(null allowed), timeZone; oneTime:boolean; status §5; usedCount: integer≥0 (занятые применения, отмена до выдачи уменьшает; исторические события сохраняются); notificationStatus; allowedActions |
| Условия | currency магазина; целые minor units, RUB до 2 знаков, VND без дробей; процент до 2 знаков (basis points), без округления неверного ввода. Допустимые ID области принадлежат текущему магазину и не удалены/архивированы; временный нулевой остаток допустим с пояснением. Категории/товары задают динамическую область: состав категории и активные фасовки товара проверяются по текущему каталогу, новые подходящие позиции включаются; конкретные фасовки — только выбранные ID. В сводке выбора категорий/товаров: «Включая новые товары в категории» / «Все доступные фасовки выбранных товаров». Удаление выбранного объекта после выдачи не расширяет область; при пустой области выгода не применяется. Нет скрытого дополнительного глобального лимита |
| Код/сводка | code только для kind=code, у продавца с promo правом или своего покупателя; генерируется сервером, нормализуется существующим promo контрактом. | Page<T> | items≤10; nextCursor: opaque/null; revision; asOf: ISO. Cursor привязан к shop/filter/query/sort и версии набора. При несовместимой ревизии PAGE_CHANGED; не склеивать страницы разных наборов; клиент перечитывает первую с уведомлением |
| OfferEvent | id, occurredAt, type: issued/revoked/replaced/used/restored; actorLabel; revision; безопасная сводка; orderRef только с orders. События неизменяемы, новый снимок условий не переписывает старый |
| PromoPreference | enabled:boolean default false; revision; channelStatus: available/unavailable; shop из контекста, account из сессии. Не наследовать от другой настройки, Telegram-входа или другого магазина |

Валидация числа не допускает NaN, экспоненты, отрицательного значения, лишней точности и превышения максимума; разделитель запятая принимается как десятичный. При фиксированной скидке выше подходящей базы скидка ограничена базой; товары не уходят в минус. Минимум проверяется по сумме подходящих обычных товаров после штатных позиционных правил, без доставки; предел процента уменьшает выгоду, не меняет минимум.
**Отличие от main:** общая автоматическая акция сейчас может работать по акционным строкам; для новых личных предложений ordinary-price eligibility обязательна и для авто, и для кода. Общие акции 12.x не менять; именно этот признак передаётся общему калькулятору.

Точный HTTP status/code отображается общим API-клиентом; §14 задаёт обязательную семантику новых ошибок, существующие wire-коды допускаются через явное сопоставление shared contracts. Не заводить дубли действующих quote/checkout ошибок.
Идемпотентная операция узнаётся до проверки изменившихся условий её повторного исполнения, но после свежей авторизации; отозванный сотрудник не получает старый ответ. Результат содержит исходный ID и актуальное состояние при последующем чтении, не выдаёт второй объект. Ключи/тела команд не писать в телеметрию с PII.
Ревизии включают видимость/права, данные и временную валидность; ответ содержит serverNow и nextChangeAt для ближайшего истечения. На видимом экране по nextChangeAt инвалидировать предложения/quote, не запускать постоянный polling. На checkout время проверяется заново даже при старом 304/кеше.
Кеш приватный по shop/account/permissions; очищение при logout/403/смене контекста; кеш браузера не отдаёт личные ответы другим аккаунтам. Статус offline допустим только в памяти уже авторизованного сеанса, не долговременный общий storage.
После issue/revoke/replace инвалидировать обе продавецкие проекции и buyer offers/quote; после заказа/отмены/возврата — summary/orders/offer usage. Возврат на экран перечитывает ревизию. Ошибку одного блока не превращать в перезагрузку всего кабинета.
Нужны индексированные выборки и batched summaries, никаких N+1 на 10 покупателей; бюджеты SQL checkout/cart/quote — [PERFORMANCE §6](../PERFORMANCE.md). До UI серверные тесты подтверждают бюджет; увеличение бюджета не прятать в миграцию. Новые таблицы/индексы выбирает Codex, без CRM-сервиса и копирования заказов.
Отправка: одно логическое outbox событие на выдачу, без автоотправки при повторном включении флага/согласия. Повторять только подтверждённо неотправленный retryable сбой по действующей очереди; unknown не пересылать. Общие технические сбои не раскрывают токены/Telegram ID покупателю/продавцу.

## 14. Ошибки → поведение
Общий принцип: валидация сохраняет поля; авторизация очищает защищённое; сеть не сообщает «успешно»; пересчёт никогда не тратит применение.

| Семантический код / HTTP | Текст и действие |
|---|---|
| UNAUTHENTICATED / 401 | «Войдите, чтобы продолжить»; существующий вход, возврат к намерению после повторной проверки, личных условий до входа нет |
| FORBIDDEN / 403 | «Нет доступа»; очистить раздел, Back в разрешённый корень; нет бесконечного «Повторить» |
| NOT_FOUND / 404 | Продавцу «Покупатель не найден»/«Предложение не найдено»; покупателю «Предложение недоступно» без различия чужого магазина/аккаунта/удаления; Back |
| PROMOTIONS_DISABLED / 409 | «Акции выключены»; проект сохранить, выдачу заблокировать, продавцу history/revoke остаются; покупателю актуальный quote |
| RECIPIENT_UNCONFIRMED / 422 | «Личные предложения доступны после входа покупателя через Telegram»; выбор другого получателя, никакого сопоставления по телефону |
| VALIDATION_ERROR / 422 | Поле: «Укажите размер скидки», «Процент должен быть больше 0 и не больше 100», «Сумма должна быть больше 0», «Проверьте точность и предел суммы», «Минимальная сумма не может быть отрицательной», «Выберите товары», «Выберите сегодняшнюю или будущую дату». Фокус первое поле |
| SCOPE_UNAVAILABLE / 422 | «Некоторые товары больше недоступны. Измените выбор»; перечислить допустимые текущему продавцу названия, убрать/заменить явно, без автоматического расширения на всё |
| REVISION_CONFLICT / 409 | «Данные изменились. Проверьте условия ещё раз»; перечитать affected object, проект сохранить, новое явное подтверждение и новый ключ изменённой команды |
| PERMANENT_EXISTS / 409 | «У покупателя уже есть постоянная скидка»; свежая сводка прежней и путь P05, не автоотзыв |
| OFFER_NOT_ACTIVE / 409 | «Предложение уже недоступно» + собственный статус; перечитать, отзыв disabled, «Повторить» при праве |
| PERSONAL_CODE_UNAVAILABLE / общий invalid-code | Покупателю «Промокод недоступен»; прежний код сохраняется до успешной замены, чужой recipient не раскрывается |
| QUOTE_CHANGED / существующий код | Штатная новая сводка/разница, «Условия скидки изменились»; при росте итогов требуется подтверждение, заказ не создаётся до него |
| IDEMPOTENCY_CONFLICT / 409 | «Эта попытка уже отправлена с другими условиями»; проверить исходную операцию, не переиспользовать ключ для изменённого тела |
| PAGE_CHANGED / 409 | «Список обновился»; перечитать первую страницу текущего фильтра, не добавлять дубли |
| RATE_LIMITED / 429 | «Слишком много запросов. Попробуйте позже»; соблюдать retryAfter, не терять поля и не повторять мутацию новым ключом |
| NETWORK / 5xx / timeout | «Не удалось загрузить. Повторить» для чтения; для команды «Не удалось подтвердить результат. Проверить» — тот же ключ, поля заблокированы от новой выдачи до выяснения исхода |

## 15. Покрытие и готовность к передаче
Дополнение к C01–C18: **C19** [сервер + UI] — согласие по умолчанию false, независимость магазинов, доступ только self, смена/конфликт ревизии/обрыв сети/нет канала, нет ретроотправки; **C20** [сервер] — равная итоговая выгода для public/constant/oneoff/code, обычная/акционная цена, expiry/issuedAt/ID, проигравший не расходуется; **C21** [сервер + UI] — PAGE_CHANGED, истечение без действий, readonly preview без orders, повтор с архивным товаром, формы после полуночи/смены цели, неизвестный результат выдачи.
