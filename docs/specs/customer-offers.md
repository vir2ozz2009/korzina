## 1. Короткие пути
| Задача | Путь и результат |
|---|---|
| Найти покупателя | Главная кабинета → «Покупатели» → поиск имени/телефона → карточка. Отдельного промежуточного меню нет |
| Из текущего заказа | Нажать имя покупателя → карточка; назад возвращает тот же заказ |
| Дать выгоду | Карточка → «Дать скидку» → одна шторка: значение, срок, сводка → «Выдать скидку». Два нажатия плюс ввод; не считаем поиск частью этих двух нажатий |
| Выдать код | В той же шторке раскрыть «Дополнительно» → «По промокоду»; код генерируется сервером. Дополнительный путь сознательно длиннее |
| Применить | Личная скидка применяется автоматически после входа. Код: профиль/корзина → «Использовать»; повторный ввод не нужен |
| Отозвать | Карточка предложения → «Отозвать» → подтверждение с получателем и выгодой. Старые заказы сохраняют снимки |
| Написать | У строки заказа — существующий чат; «Сообщения по заказам» открывает единственный доступный чат либо выбор заказа, если их несколько |

Список, поиск, выбранный фильтр и прокрутка восстанавливаются при «Назад». Прямая ссылка проверяет магазин/права и имеет возврат в список. Перезагрузка читает серверное состояние; незавершённая выдача не публикуется.
Смена магазина/аккаунта очищает данные предыдущего; поздний ответ старого запроса не подменяет новый экран. Telegram BackButton и браузерный Back используют текущий роутер.

## 2. Покупатели и карточка
- Источник — реальные заказы текущего магазина. Список появляется автоматически, без ручного создания клиента. Включаем покупателей с любым оформленным заказом, включая отменённый; посетителей без заказа не включаем.
- Одна запись на серверную личность в магазине. Для гостя — существующая гостевая личность, не телефон. Два аккаунта с одним телефоном остаются разными.
- Поиск по имени без учёта регистра и по нормализованным цифрам телефона; минимум 2 символа имени либо 4 цифры. Телефон в поиске — только контакт, не право доступа. Одинаковые совпадения показываются отдельно с последним заказом.
- Строка: имя (либо «Покупатель без имени»), доступный телефон, дата последнего заказа, число заказов в работе. Сортировка по последнему оформленному заказу убыванию, затем стабильный ID.
- По 10 строк + «Показать ещё». Поиск работает по всей базе, не только загруженным строкам. Без конструктора фильтров, рейтинга клиентов и сегментов.
- Карточка: имя/телефон с «Копировать», статус «Гость» при необходимости; сводка за всё время; «Дать скидку»; действующие личные предложения; последние 3 заказа и «Все заказы»; «Сообщения по заказам».
- История: все состояния, новые сверху, 10 + ещё; простые фильтры «Все / В работе / Выполнены / Отменены», суммы из заказа, переход в существующий заказ. «В работе» в сводке сразу открывает соответствующую историю.
- Чат не создаётся заново: только существующий по заказу; закрытый чат остаётся для чтения, отсутствие доступного чата объясняется. Не показывать кнопку отправки там, где сервер её запрещает.
- Телефон берётся из последнего доступного контакта заказа этой личности в этом магазине; если его нет — «Телефон не указан», без копирования. Общий профиль и контакты других магазинов не раскрываются.
- Не добавляем редактирование личных данных продавцом, заметки, ручное объединение, импорт, день рождения и обязательную регистрацию.

### 2.1 Показатели без второй бухгалтерии
«Всего заказов» — все оформленные; «В работе» — текущая группа; «Выполнено» — completed.
«Сумма покупок» — показатель выручки O9, ограниченный покупателем, за всё время: выполненные заказы после скидок, доставка магазину и проведённые возвраты по П3/§9.2. Не путать с подтверждёнными денежными поступлениями.
«Средний чек» — та же сумма / число выполненных заказов с положительной остаточной стоимостью (§9.1 O9); если знаменатель 0 — «—».
«Последняя покупка» — дата последнего выполнения; полный возврат не стирает дату фактической покупки. Если выполнений нет — «Ещё не покупал».
Поздний возврат меняет сводку, повтор выплаты не вычитает сумму второй раз. Отмена не увеличивает покупки. Недостаточная история — пометка неполноты по O9, не выдуманный ноль.
Пример: completed 1000 и 500, возврат товаров 200 из первого, отменённый 700 → сумма 1300, выполнено 2, средний 650. Полный возврат второго → сумма 800, выполнено 2, средний 800.
Денежные показатели требуют права O9 (`payments` либо owner); без него сервер не возвращает суммы сводки. Суммы доступных заказов остаются в границах текущего права просмотра заказов.

## 3. Одна форма личного предложения
Получатель и магазин уже выбраны; менять получателя в форме нельзя. «Дать скидку» доступно только подтверждённому аккаунту Telegram, владельцу/управляющему и при включённых «Акциях».
Гость видит в карточке продавца пояснение «Личные предложения доступны после входа покупателя через Telegram», без предложения угадать аккаунт по телефону.

| Поле | Предложенное правило |
|---|---|
| Цель | «На следующий заказ» по умолчанию; «Постоянная скидка»; «Вернуть покупателя» |
| Размер | % или сумма в валюте магазина; значение обязательное, пустое по умолчанию. Никакой скидки без явного выбора продавца |
| На следующий заказ | 1 выигравшее применение; старт сейчас; срок 7 календарных дней, включая сегодня, до конца последнего дня по времени магазина |
| Постоянная скидка | Автоматическая, многократная, без срока по умолчанию; срок можно задать |
| Вернуть покупателя | Та же разовая автоматическая скидка на 7 дней; отличается подписью цели. Не проверяет «давно не покупал», не запускает робота/рассылку |
| Срок | 7 / 30 календарных дней, своя конечная дата, без срока; выбранное окончание включительно. Показывать точную дату, старт сразу. Нет отложенного старта |
| Дополнительно | Минимальная сумма; товары/фасовки/категории; максимум суммы для процента; способ «Автоматически / По промокоду». По умолчанию все товары с обычной ценой, без минимума, без максимума |
| Код | Для разовых предложений; сервер генерирует уникальную строку в магазине, без имени/телефона/ID в ней. Ручное переименование и публичность исключены |
| Проверка | Сводка на этой же форме: кому, сколько, на что, минимум, срок, число применений, способ получения. «Выдать» — явное подтверждение этой сводки |
| Пример | Необязательный «Посмотреть пример» использует общий калькулятор с личностью получателя; см. §3.1 |
| Уведомление | Показать доступность: «Бот сообщит» либо конкретную причину, почему не сообщит. Не запрашивать включение уведомлений от имени покупателя |

Процент >0 и ≤100; фиксированная сумма >0 с точностью валюты; минимум ≥0; максимальная скидка >0; выбранные товары не пусты. Пределы значений — существующий контракт promo, не свободные строки.
100% явно подписывается в сводке как «Бесплатные подходящие товары»; доставка не становится бесплатной.
Предлагаем ограничить 13.1 скидками на корзину: личная цена отдельной позиции, личная доставка, N+M, наборы и произвольный лимит N применений не входят.
В действующем предложении условия не редактируем: «Повторить» открывает новый проект; прежнее действует до явного отзыва/замены. Отозванное не «включается» обратно. Это проектное упрощение для личных предложений, не изменение общих акций 12.1.
Одна постоянная автоматическая скидка на покупателя: новая выдача предлагает явную замену; подтверждение атомарно отзывает старую и выдаёт новую, при ошибке старая действует. Разовых может быть несколько; выдача другой не отзывает предыдущие.

### 3.1 Проверка на примере
Не читать живую корзину покупателя для продавца. Предзаполнить учебный пример последним заказом этого покупателя, пересчитанным по текущим ценам/доступности; отметить исключённые позиции и изменения. При отсутствии подходящих строк — предложить выбор товаров.
Показать результат без нового предложения, с ним, фактически выигравшую скидку и итог. Это прогноз, не обещание цены будущего заказа.
Пример не меняет заказы/корзины/лимиты и не оформляет заказ. При ошибке примера выдача допустима после валидной сводки; нельзя писать, что расчёт проверен.
Если действующий код/акция выгоднее, объяснить это. Проверка повторяется сервером на реальной корзине.

## 4. Получение покупателем
- Профиль → «Ваши доступные предложения»: личные и доступные публичные предложения текущего магазина, с источником «Для вас»/«Акция магазина», условиями и сроком. Скрытые неперсональные коды не раскрываются.
- В корзине использовать существующий вход «Доступные предложения» и единый список, без второго поля промокода и без дублирующих блоков.
- Автоматическая скидка: «Применится автоматически», после выигрыша «Личная скидка −…». Никакой активации/кнопки «Получить».
- Код: «Использовать» передаёт его в существующее поле корзины. При другом введённом коде подтвердить «Заменить код …?»; затем серверный пересчёт, даже если новый код проигрывает. Отмена сохраняет старый.
- Пустая корзина: код можно сохранить в ней; показать «Добавьте товары» и переход в каталог, не объявлять применение. Автоскидка ожидает подходящие товары.
- Активное, но неподходящее предложение остаётся в списке: объяснить минимум, товары, обычную цену либо более выгодную скидку. Истёкшее/использованное/отозванное не показывать активным.
- Если список пуст, вход скрывается; прямая ссылка — «Нет доступных предложений» и переход в магазин.
- Ссылка из бота ведёт в предложение текущего магазина; до входа не раскрывать чужие условия. После Telegram-входа сохранить намерение и проверить получателя. Само открытие ссылки не расходует и не вводит код.
- Чужой аккаунт/магазин получает нейтральное «Предложение недоступно» без имени получателя. Гость — предложение войти, обычное оформление без личной выгоды остаётся доступно.
- Выход очищает личные предложения и код в клиентском представлении, серверные данные аккаунта сохраняются. Повторный вход перечитывает права и актуальность.

## 5. Расчёт и жизненный цикл
Используем promo §4–6 и один серверный расчёт: личная скидка/код — кандидат общей скидки на корзину, не отдельное суммирование.
- Сравнивать итог всего заказа с известной доставкой и действующими позиционными акциями. При неизвестной доставке не обещать окончательную экономию.
- Одна скидка на корзину и один введённый код, включая доставку/набор. Промокод на товары действует на обычные цены; N+M, цены по акции и комбо сохраняют текущие правила.
- Равенство: существующий приоритет автоматической выгоды над кодом; среди равных автоматических — публичная многократная, личная постоянная, разовая. Среди равных разовых — ближайшее окончание, затем время выдачи и стабильный ID. Проверить совместимость с действующим калькулятором; это дополнение, не отмена принятых tie-break 12.x.
- Проигравшее предложение не расходуется; «выбрано в корзине» не означает «использовано». Только победитель расходует применение в транзакции оформления.
- Две параллельные корзины на последнее применение: выигрывает одна транзакция; второй расчёт меняется с объяснением. Повтор оформления с тем же ключом не создаёт заказ или расход.
- Полная отмена до выдачи один раз восстанавливает лимит по promo §6; предложение снова доступно лишь если ещё действует. Частичный возврат и полный возврат после выдачи лимит не восстанавливают.
- Отзыв/истечение/выключение «Акций» меняет открытые корзины, но не снимки оформленных заказов. Рост суммы требует QUOTE_CHANGED и согласия покупателя.
- Гонка «отзыв ↔ оформление»: оформление до отзыва сохраняет снимок; после отзыва использовать предложение нельзя.
- Статусы продавцу: действует, использовано (разовое), истекло, отозвано; использование многократного отображается числом и ссылками на заказы. «Применено» — состояние текущей корзины, не статус предложения.
- История выдачи/отзыва/замены/использования: время, сотрудник, ревизия, условия, заказ; 10 + ещё. При одновременном исчерпании/окончании показывать первичную причину по серверным событиям, не текущему порядку UI.
- Выключение дополнения не останавливает календарный срок и не обнуляет лимиты; повторное включение не возрождает истёкшее.

## 6. Права, личность, данные и уведомления
| Область | Граница |
|---|---|
| Список/карточка/заказы | owner или действующее право orders, только текущий магазин; чат отдельно по chat. Телефон не даёт полномочий |
| Денежная сводка | Право O9: owner или payments; без права сервер исключает поля |
| Выдача, отзыв и история предложений продавцу | owner или teamRole manager, как текущий sellerPromoRoutes; не наследовать это от orders/payments |
| Покупатель | Только собственный account + shop; проверять на чтении, вводе кода, quote и checkout |
| Гостевой вход | Использовать существующее подтверждённое слияние гостевой сессии с Telegram. Не связывать других гостей по совпавшему телефону |
| Слияние | История переносится существующим merge; сводка пересчитывается без дублей. Личные предложения гостям не выдаются. Лимиты и расход сохраняются при переносе существующих promo_uses |
| Копирование магазина | Не переносить покупателей, личные предложения, коды, расход и события уведомлений. Новый магазин не наследует чужие данные |
| Удаление аккаунта | Отозвать неиспользованные предложения, прекратить доставку уведомлений, обезличить отображение по существующему жизненному циклу; снимки и минимальная финансовая история сохраняются по правилам проекта. Повторная регистрация не оживляет предложения |
| Отзыв сотрудника | На каждом запросе свежая проверка; очистить данные открытого экрана при получении отказа. Запоздавший ответ не раскрывает их снова |

Выдача + событие уведомления фиксируются атомарно. Повтор команды = тот же результат; одинаковый ключ с другим телом отклоняется. Параллельные изменения используют ожидаемую ревизию.
Бот магазина сообщает один раз о новой выдаче только при согласии на акции и доступном канале. Согласие повторно проверяется перед отправкой; отозванные/истёкшие предложения до отправки не отправляются.
При выключенных уведомлениях/блокировке бота предложение всё равно доступно в профиле. Продавцу: «Выдано, уведомление не отправлено» с причиной. Успешная выдача не откатывается из-за Telegram.
Повторы очереди не создают новое предложение и повторное подтверждённо отправленное сообщение. При неоднозначном таймауте Telegram не обещать exactly-once: сохранить неизвестный результат, не слать автоматический дубль; показать неопределённость.
Массовая рассылка, свободный текст, ручная кнопка многократной отправки, SMS/email и гарантии прочтения не входят.

## 7. Зависимости и требования к реализации
1. A13b первым: идентичность + выборка/поиск/права → сводка O9 → карточка/заказы/чат. Никакого нового CRM-сервиса.
2. A12 вторым: расширить текущий promo привязкой получателя и жизненным циклом → quote/checkout/лимиты/отмена/возврат → профиль/корзина → очередь бота.
3. Серверные контракты до экранов: список (query, cursor, revision), summary с allowedActions, история заказов; личное предложение (id, shop/account, terms, revision, status, uses, deliveryStatus), команды выдачи/отзыва/замены, чтение предложений и пример. Точные схемы и ошибки фиксируются в спецификации и shared contracts.
4. Новая миграция/индексы без переноса личных данных между магазинами; запросы по shop/identity, курсоры стабильны; нет N+1 и полного сканирования заказов на каждой строке.
5. Ревизии/инвалидация при заказе, выполнении, возврате, слиянии, выдаче/отзыве, сроке и смене флага. Частные данные не попадают в общий кеш, URL, логи и телеметрию.
6. Сводка/заказы/предложения загружаются независимо: сбой одного блока не прячет остальные. Offline — показать сохранённое с пометкой; выдача/отзыв/применение без серверного подтверждения не объявляются успешными.
7. Каркас/UI-kit из main, 360/390 px, касания ≥44 px. Если требуется больше трёх новых компонентов — отдельная задача по AGENTS.
8. Покупатели доступны независимо от «Акций»; личные предложения используют существующий promotions, не новый переключатель. Выключение прячет покупательские входы, продавцу сохраняется доступ к истории/отзыву, выдача блокируется.
9. Проверка существующих точек: buyer/merge, promo/routes+calculate+uses, checkout, O9, profile, chat, bot queue. Это адресное расширение, не аудит всего проекта.

## 9. Не входит
Кэшбэк/кошелёк (13.2), любимый товар (13.3), рефералы (13.4), отзывы (14.3), массовые сообщения (14.4), регулярные заказы (15.1), вход без Telegram (16.2), выгрузки (16.4).
Также: CRM-теги/сегменты, автоматический win-back, произвольные сценарии/кампании, публичные переносимые купоны, ручное объединение клиентов, приватные заметки, новый общий чат, правка уже оформленного заказа через предложение, отдельный desktop-дизайн.
Не рисовать будущие блоки в карточке.

## 10. Что требуется одобрить
Рекомендован единый пакет: одна шторка с явной сводкой; автоматический способ основной; разовые + одна постоянная скидка; срок разовых 7 дней, сумма без предвыбранного значения; возврат клиента как преднастройка; доступ по существующим ролям; сводка по O9.
Альтернатива: только разовые скидки — меньше работы, но нет постоянной привилегии; полноценный конструктор CRM — больше настроек и не соответствует цели.
Новые правила §§1–9 до ответа Андрея остаются предложением. После одобрения карточек Work оформляет точную спецификацию экранов/ошибок/контрактов без новых продуктовых догадок, затем отдельный СТОП одобрения спецификации и холста.
