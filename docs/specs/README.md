# Спецификации блоков: как описывать и как MagicPath собирает экраны

**Решение Андрея 18.11.2026** (после эксперимента с покупкой): экраны покупателя собираются **без макетов** — по спецификации логики и нашей дизайн-системе. Figma — только справочник для Claude.

## Стандартный порядок блока (решение Андрея 18.11.2026, эталон — блок 2 «Покупка»)

Так делается **каждый** блок. Эталон уровня детализации — `docs/specs/purchase.md` и холст «Блок 2 · Покупка» (MagicPath, ревизия, одобренная Андреем).

1. **Карточки** задач блока (Claude) — что входит, что нет; Figma — только справочник Claude, не обязателен.
2. **Спецификация** `docs/specs/<блок>.md` по шаблону ниже (Codex, «Высокое») — включая сервер и настройки продавца, от которых зависит блок. **СТОП:** проверка Claude, ответы Андрея на «Открытые вопросы», «одобряю».
3. **Холст** — один интерактивный компонент «Блок N · <сценарий>» по спецификации, в новом чате (Codex, «Высокое»). Отчёт: «Что я решил сам», «Чего не хватило в спецификации».
4. **Правки Андрея по холсту** («Правки: …») — Claude вносит их в спецификацию, решения и карточки, Codex обновляет холст по спецификации. Повторять до «одобряю». Ни одна правка не живёт только в чате.
5. **Сервер** задач блока по спецификации и карточкам, с тестами.
6. **Экраны** — перенос одобренной ревизии в код (контракт точности ниже), подключение к серверу.
7. **Приёмка** — smoke основного пути, один отчёт со снимками, ссылкой на demo и «кругов правок: N».

Шаги блока в `PROGRESS.md` Claude пишет по этому порядку; Андрею — только короткие команды («Продолжай», «Одобряю», «Правки: …»).

## Где что лежит

| Файл | Что в нём | Кто пишет |
|---|---|---|
| `docs/specs/<блок>.md` | **Спецификация блока** — единственный источник поведения и состава экранов: путь, данные, экраны, состояния, тексты, правила, приёмка | GPT (Codex) по этому шаблону, проверяет Claude, утверждает Андрей |
| `docs/tasks/<ID>.md` | Карточка задачи: что именно делает этот PR (сервер, тесты, какие экраны спецификации) — **ссылки на разделы спецификации, без пересказа** | Claude |
| `docs/DOMAIN.md`, `DECISIONS.md` | Бизнес-правила и решения | спецификация на них ссылается, не копирует |

Противоречие: решение Андрея → спецификация → карточка → код в `main`. Найденное противоречие — в «Открытые вопросы» спецификации, не догадка.

## Шаблон спецификации блока

Объём — **до ~500 строк на блок**. Правила из других документов не копировать — ссылка (`DOMAIN «Оформление»`, `PERFORMANCE §6`). Каждое утверждение проверяемо: без «удобно», «красиво», «по возможности».

```markdown
# Спецификация · Блок N · <Название>

## 0. Рамки
- Задачи: B…; истории: K…
- Входит в блок / не входит (с номером будущего блока или задачи A…)
- Источники: карточки, DOMAIN, DECISIONS (строки с датой), одобренные экраны в main

## 1. Путь
Схема шагов (экран → экран), тип перехода (`push` / `sheet` / замена), что сохраняется при «назад»,
перезагрузке и закрытии приложения, куда ведёт прямая ссылка на шаг, вход и выход блока.

## 2. Данные
Для каждой сущности: поля и типы (имя контракта в `src/shared/contracts`), кто источник (сервер),
когда читается и когда перечитывается (ревизии, кеш, что НЕ перечитывается), что клиент не считает сам
(цены, итоги, доступность — только сервер). Команды: имя, вход, выход, `Idempotency-Key`, коды ошибок.

## 3. Экраны
По каждому экрану (и шторке):
### 3.N <Экран>
- Назначение (одна фраза) · Шаблон (`checkout`/`form`/…) · Открывается из …
- **Состав сверху вниз** — таблица: элемент · компонент UI-кита · данные · текст · виден когда
- **Действия** — таблица: нажатие · условие · что происходит · запрос · что блокируется на время запроса
- **Состояния** — таблица: состояние · когда · что видно · что можно нажать · текст
  (обязательно: загрузка, пусто, ошибка + повтор, нет сети, данные изменились, частные случаи)
- **Тексты** — все строки экрана дословно (кнопки, подписи, ошибки, подсказки)
- **Вид** — только отличия от общих правил DESIGN (§2–4, §5а); без своих цветов и теней
- **Доступность** — размеры касания ≥ 44 px, клавиатура (тип поля, «Готово»), фокус после ошибки

## 4. Сервер: команды и правила
По каждой команде и запросу блока (поведение и инварианты, **не реализация**: таблицы, файлы и код
выбирает Codex по ARCHITECTURE и PERFORMANCE):
- что проверяется и в каком порядке (сессия, ревизия, цены, остатки, зона, интервал, способ оплаты…);
- что меняется, и что — в одной транзакции; что пишется в историю событий и уведомления;
- повтор с тем же `Idempotency-Key` → тот же результат; гонки (последний товар, последнее место) → кто выигрывает;
- что кешируется и когда сбрасывается; внешние вызовы (геокодер) — через сервер, с кешем;
- бюджет SQL горячих путей (ссылка на PERFORMANCE §6);
- какие серверные тесты обязательны (по TESTING §2).

## 5. Ошибки сервера → поведение экрана
Таблица: код ошибки · где возникает · что видит покупатель · что сохраняется · действие.

## 6. Правила
Нумерованные П1, П2… — каждое проверяемо, со ссылкой на DOMAIN/DECISIONS.

## 7. Приёмка
Given / When / Then. У каждого пункта пометка: [сервер-тест] · [smoke] · [холст].

## 8. Не входит
Что не рисовать и не делать — с блоком или задачей, где появится.

## 9. Открытые вопросы
Вопрос · варианты · что блокирует. Без ответа Андрея этот кусок не строится.
```

## Как писать спецификацию (задание для GPT)

1. Прочитать **только**: этот файл; карточки задач блока `docs/tasks/<ID>.md` (в них уже перенесено всё нужное из Figma); `docs/DOMAIN.md` (разделы, которые называют карточки); `docs/DECISIONS.md`; контракты `src/shared/contracts`; одобренные экраны блока в `main`; холст эксперимента или одобренную ревизию MagicPath блока, если есть (их тексты и решения — вход, но каждое проверить по правилам ниже).
   **Опыт Lavka (серверная логика):** сначала уже извлечённое — `docs/reference/lavka/system-analysis.md` (для покупки: §3 контракт команд, §5 корзина/получение/оплата, §10 надёжность, §12 сквозная приёмка T03–T04) и `process-map.md`. Если там нет ответа — **только чтение** репозитория `vir2ozz2009/Lavka` (разрешение Андрея 18.11.2026, только для спецификаций): модули оформления, доставки и зон, расписания и интервалов, оплаты. Брать **правила, проверки, крайние случаи и тексты ошибок**; код, структуру файлов и таблиц не копировать (Korzina пишется с нуля — DECISIONS 17.11.2026); ничего в Lavka не менять и не запускать. Каждое правило из Lavka — с пометкой «из Lavka: <файл>» и проверкой против DOMAIN и DECISIONS; противоречие — в «Открытые вопросы».
2. Figma не открывать. Бизнес-правил не придумывать: чего нет в источниках — в «Открытые вопросы». Решения по виду можно предлагать — с пометкой «предложение».
3. Заполнить шаблон целиком, без пустых разделов; всё неприменимое — словом «нет».
4. Проверить себя: у каждого экрана есть все состояния; у каждого действия — результат, запрос и блокировка; у каждой ошибки сервера — поведение экрана; каждый пункт «Не входит» карточек есть в «Не входит» спецификации; нет копий текста из других документов, только ссылки; объём — до ~400 строк.
5. Черновой PR «spec: блок N»; в описании — список открытых вопросов. **СТОП** — Claude проверяет, Андрей утверждает словом «одобряю».

## Как MagicPath собирает экраны по спецификации

**Источники вида (только они):**
1. Токены — `src/styles/tokens.css`, `docs/design-system/tokens.md`.
2. UI-кит — `src/ui`, `docs/design-system/components.md`.
3. Шаблоны экранов — `src/app/templates`, `docs/design-system/templates.md`, `reference-screens.md`.
4. Правила вида — `docs/DESIGN.md` §2–4, §5а.
5. Образец живого стиля — одобренные экраны в `main` и `/dev/kit` на demo.

Figma, старые холсты и `docs/SCREENS.md` не открывать.

**Правила сборки** (наши + официальные правила MagicPath для холста — «Design Defaults» навыка `magicpath`):
- Холст — из свежего `main`; первая строка отчёта — «Собрано из main <хеш>». Создание — `code start --project 473310532867354624 --name "…" --width 390 --height 844`, затем `code submit --wait`.
- **Путь блока — один интерактивный компонент** «Блок N · <сценарий>»: экраны и шторки переключаются внутренним состоянием (так рекомендует MagicPath для шагов одного сценария), по нему можно пройти кликами от начала до конца. Экраны вне сценария — отдельными компонентами. **Никогда** не ставить несколько экранов рядом в одном кадре.
- **Собирать частями, а не за один раз:** (1) основной путь кликами — экраны и переходы без ошибок; (2) состояния и ошибки по разделам «Состояния» и «Ошибки сервера»; (3) панель «Состояния» и сверка с «Текстами». После каждой части — `code submit --wait` и самопроверка по своему разделу спецификации; читать спецификацию по разделам нужного экрана, а не держать всю сразу.
- **Состояния** из раздела «Состояния» включаются отдельной панелью «Состояния» под экраном (вне интерфейса покупателя): выбрать экран → выбрать состояние.
- **Полностью рабочий прототип:** поля управляемые, проверка ввода работает, кнопки меняют состояние, есть hover / focus / active / disabled, шторки открываются и закрываются, «назад» работает. Заглушек `onClick={() => {}}` нет.
- **Без рамок устройства** (никаких айфонов, статус-баров, «чёлок»): холст 390 × 844 — уже и есть экран. Вёрстка резиновая (`w-full`, без жёстких ширин у контейнеров), по центру кадра.
- Редактируются только `src/App.tsx`, `src/index.css`, `src/components/generated/**`. Перед экраном скопировать `src/ui/*` и нужные части `src/app` в `src/components/generated/ui/` — экран собирается из тех же примитивов, что приложение (DESIGN §5 шаг 2); токены — те же, что `src/styles/tokens.css`.
- Только элементы UI-кита и шаблоны. Нового элемента не хватает → добавить его в кит (в стиле кита) и назвать в отчёте; копировать JSX примитива в экран нельзя.
- Тексты — дословно из спецификации. Текста нет → придумать короткий и внести в отчёт «Что я решил сам».
- Демо-данные — по типам контрактов из раздела «Данные», обычные товары магазина, без служебных названий.
- Только мобильная версия 390 px; нижняя кнопка — `StickyFooter` без подложки (§5а).
- Ничего из «Не входит» и будущих блоков — ни элементом, ни заглушкой.

**Перенос в приложение** (официальный «контракт точности» MagicPath + наши правила):
- взять **точную одобренную ревизию** (`code context <componentId> --revision <rev>`), номер ревизии — в PR и PROGRESS;
- сначала **один в один** на 390 px (структура, отступы, тексты, состояния), потом подключать данные: моки → хуки `api.ts`, примитивы `generated/ui` → `@/ui`; изменённый на холсте примитив переносится в `src/ui`, а не копируется в экран;
- преднамеренные отличия от холста — списком в PR;
- поведение приложения не теряется: загрузка, ошибки, блокировка кнопок, «назад», доступность.

**Отчёт Андрею:** хеш `main` · ссылки на компоненты · время · «Что я решил сам» (по экрану) · «Чего не хватило в спецификации» (это правки спецификации, их разбирает Claude).

## Что сохраняется из прежних правил (не ослаблять)

Спецификация и холст не отменяют правил кода — при переносе в приложение действуют `AGENTS.md` и:
- **сервер — источник правды** о цене, итоге, остатке, правах, статусе (AGENTS, правило 3);
- **экономно** — экран получает только то, что показывает; без N+1; неизменившееся не перечитывается; фон без работы не работает (`PERFORMANCE.md`); горячие пути — с тестом бюджета SQL;
- **без разрастания** — файлы до ~200 строк, один компонент на файл, без «на будущее», переиспользовать кит и шаблоны (AGENTS, правила 2 и 4);
- **тесты только на правила** — деньги, права, повторы, гонки, бюджет SQL; не на вид и тексты (`TESTING.md` §2); smoke основного пути на превью (§7);
- **сначала контракт, потом экран**; одобрение — только словом «одобряю»; элементы будущих блоков нигде не видны;
- **дёшево** — новые платные сервисы только с «да» Андрея (`COSTS.md`).
