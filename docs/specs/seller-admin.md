# Спецификация · Блок 4 · Вход продавца и админка

## 0. Рамки

- **S1 / US-M01:** вход продавца через Telegram, профиль Telegram, оболочка кабинета и переключение магазинов.
- **AD1 / US-AD01–03:** вход администратора, реестр, создание черновика и приглашение владельца.
- **AD2 / US-AD04–06:** карточка магазина, владелец и повторное приглашение, статусы, дополнения.
- **AD3 / US-AD07–08:** общий журнал и журнал магазина, смена адреса витрины.
- Источники: карточки [S1](../tasks/S1.md), [AD1](../tasks/AD1.md), [AD2](../tasks/AD2.md), [AD3](../tasks/AD3.md), истории [US-M01](../stories/seller-store.md#us-m01--вход-в-кабинет) и [US-AD01–08](../stories/platform-admin.md), [DOMAIN «Роли»](../DOMAIN.md#роли), [DECISIONS D13–D17, D20](../DECISIONS.md), [ARCHITECTURE §4–7](../ARCHITECTURE.md), [Карта навигации](../design-system/navigation.md#админка-платформы).
- Основа — main `314f2f8`. Переиспользуем F2/F4/F5: подготовку магазина для CLI, сессии продавца, проверку членства, реестр флагов. В исходной сборке Telegram-вход продавца принимает `initData`, резолвер витрины пропускает только `active`.
- Из Lavka: [system-analysis §3, §4, §10](../reference/lavka/system-analysis.md) — повтор команды, проверка срока приглашения и отделение уведомлений от записи.
- За пределами блока — §8. Решения §9 уточняют границы S1 и AD1–AD3 и имеют приоритет над формулировками карточек и историй от 18.11.2026.

## 1. Путь

| Вход | Переходы и возврат |
|---|---|
| Обычный вход продавца | Адрес кабинета, кнопка меню бота платформы или «Кабинет продавца» в профиле витрины (§9.9) → при необходимости вход Telegram → `replace` в кабинет. Возврат продолжает исходный допустимый маршрут. В Mini App бота платформы проверяем `initData`. |
| Кабинет | `/seller` → переключатель магазина (`sheet`) или «Ещё» (`tab-root`) → «Профиль продавца» (`push`) / «Выйти» (`sheet`). У каждой доступной вкладки свой стек и прокрутка. При смене магазина открывается его главная, данные и стеки привязаны к магазину. «Открыть витрину» ведёт на публичный адрес текущего магазина. |
| Администратор | «Админка» в «Ещё» или `/admin` → при необходимости `/admin/login` → реестр → `push` в мастер, карточку или «Журнал». Из карточки можно открыть статус (`sheet`), владельца, дополнения, оформление или адрес черновика. «Журнал» из карточки открывает ту же страницу с фильтром по магазину. Возврат сохраняет фильтр и прокрутку. |
| Создание | `/admin/shops/new` («Магазин») → `/admin/shops/new/owner` («Владелец») → «Создать» → `/admin/shops/$id/created` (`replace`, завершённый мастер убирается из истории) → карточка. «Назад» сохраняет введённое. При перезагрузке без данных первого шага открывается первый шаг. При неизвестном результате восстанавливаем состояние команды, см. §4. |
| Владелец по приглашению | Ссылка → `/seller/invite/$token` (`none`, выдача F2 понимается в прежнем формате `?shop=…&token=…`) → «Войти через Telegram и принять» → проверенный возврат из бота выдаёт сессию и принимает приглашение → `replace` в кабинет этого магазина. При закрытии можно заново открыть действующую ссылку. Следующие входы доступны обычным путём из первой строки. |

Прямая ссылка кабинета или админки проходит те же серверные проверки, что переход из меню. После входа разрешена только внутренняя цель соответствующей оболочки. Выход очищает данные сессии, закрывает защищённые экраны и заменяет их входом. После потери права уже загруженные данные и действия скрываются при проверке доступа. Завершённая авторизация и приглашение очищаются из адресной строки.

## 2. Данные

Типы ниже задают контракт. Существующие входы берём из [`auth.ts`](../../src/shared/contracts/auth.ts), целевые типы платформы добавляются при реализации. Время — UTC в миллисекундах, отображение — локальное. Состояние и права вычисляет сервер.

| Контракт | Поля и чтение |
|---|---|
| `SellerSession` | `accountId: string`, `telegramId: string` собственного профиля, `canAdmin: boolean`, доступные магазины `SellerShop[]`. `SellerShop`: `id, slug, name, storefrontUrl: string`, `status: ShopStatus`, `role: Role`, `permissions: Permission[]`. Читаем после входа, по прямой ссылке, при смене магазина и возврате после потери сети. |
| `ShopStatus`, `AdminShopList` | `draft / active / paused / archived`. Страница `items[], nextCursor?, counts`. Строка: `id, name, slug, storefrontUrl, status, createdAt, logoUrl?, ownerName?, ownerPending: boolean, botConnected: boolean, addonsEnabled: number`. Счётчики: `total, active, awaitingOwner, paused`. На входе и при смене поиска, фильтра или курсора. |
| `AdminShopDetail` | Поля строки и `version: number`, `country, currency, timezone, theme`, `owner?, team[]` (имена и роли), `botUsername?`, `onboardingSteps[]?`, `productCount, orders7d, orders30d: number`. Если возможности из следующих блоков ещё отсутствуют, показываем доступные факты (включая пустую команду и «Бот не подключён»). |
| `ShopDraftInput`, `OwnerInvite` | `name, slug, country, currency, timezone: string`, `ownerName: string, comment?: string`. Страна — код ISO 3166-1 alpha-2, валюта — ISO 4217, пояс — IANA. Сервер создаёт пустой магазин с оформлением по умолчанию. Результат `shop, invite`. Приглашение включает `state: pending / accepted / expired / revoked, expiresAt`. Ссылка доступна в ответе её выпуска. Принимает первый подтверждённый аккаунт Telegram. |
| Профиль покупателя | `sellerCabinet: boolean` вычисляется сервером по Telegram-сессии покупателя и активному членству в текущем магазине (§9.9). |
| Справочники региона | Один файл данных в `src/shared`: страны ISO 3166-1, соответствия стране валюты ISO 4217 и основного пояса IANA, перечни допустимых валют и поясов. Общий источник для клиента и сервера, без библиотек. 17 приоритетных связок и порядок — §9.10. Имена стран — `Intl.DisplayNames`. При нескольких валютах или поясах берём основной вариант из таблицы. Для территории без собственной валюты предлагаем выбрать валюту вручную. |
| `AdminFeature` | `key: FeatureKey`, `kind: addon / rollout`, `description: string`, `default, enabled: boolean`. Читаем при открытии дополнений. Результат команды обновляет только соответствующий магазин. |
| `AuditPage` | Страница `items[], nextCursor?`. Поля записи `id, at, shopId?, shopName?, actorKind: admin / seller / system, actorName?, action, before?, after?, reason?`. Читаем в одном журнале при открытии и смене фильтра магазина или действия. Список содержит только разрешённые поля. |

API ниже задаёт целевые действия. Токены и данные покупателей не передаются в журнал. Личные ответы — `Cache-Control: no-store`. После команды обновляется её сущность и зависимые ключи, например строка реестра, счётчики и журнал. Данные другого магазина хранятся под отдельными ключами. Список читает только строки страницы и счётчики, без обращения к каждому Shop DO. Агрегаты читаются при открытии карточки одного магазина. У неизменившихся персональных списков допустима условная проверка по ревизии после проверки прав. См. [PERFORMANCE §2, §3 и §6](../PERFORMANCE.md).

## 3. Экраны

Для всех экранов загрузка данных — скелетон шаблона. Сеть или 5xx — «Нет подключения» или «Не удалось загрузить» и «Повторить»; введённые данные сохраняются. Состояния доступа — §5. При конфликте версии показываем свежие данные и сохраняем введённое для повторной проверки. Пустые состояния с отдельным действием указаны в строках экранов. Тексты в кавычках — видимые подписи. На телефоне используем шаблоны и токены [DESIGN §2–4 и §5а](../DESIGN.md): область касания ≥44 px, фокус на первом ошибочном поле, заголовок ошибки читается скринридером, состояние видно по тексту, CTA доступна над клавиатурой. Для копирования ссылки предусмотрен доступный текстовый статус.

| Журнал · `list` | «Журнал», `Select` «Магазин», `Select` «Действие», лента «когда · кто · действие · было → стало» с причиной при наличии, «Показать ещё» | Из реестра открывается общий список, из карточки — он же с выбранным магазином. Изменение или сброс фильтра → первая страница. «Показать ещё» → следующая, кнопка ожидает ответ. | «В журнале пока нет записей», «По этим фильтрам ничего не найдено», «Сбросить фильтры». Роли автора: «Администратор», «Продавец», «Система». |

## 4. Сервер · команды и правила

Пути в таблицах для читаемости даны относительно `/api/platform`. API совместим с используемыми входами F4. Для изменяющих запросов применяются same-origin, `Idempotency-Key` и лимиты из ARCHITECTURE §7, кроме подписанных сервером Telegram-событий и проверяемого одноразового возврата. Повтор с тем же субъектом, ключом, целью и входом возвращает тот же логический результат. Тот же ключ с другим входом — `IDEMPOTENCY_CONFLICT`. Точный повтор успешной выдачи ссылки возвращает тот же действующий результат авторизованному инициатору, при этом в хранилище остаётся только хеш токена. Проверки сессии и актуальных прав выполняются до выдачи результата повтора.

### 4.1 Вход, права и приглашение

| Запрос / команда | Проверки и эффект |
|---|---|
| `POST /auth/telegram`, старт и завершение браузерного обмена | В Mini App принимаем существующий `initData`, проверяем подпись и свежесть токеном бота платформы. Для браузера бот принимает начатую попытку и выдаёт одноразовый возврат, связанный с попыткой, исходным браузером и допустимым маршрутом возврата. Подлинность и срок проверяет сервер. Погашение и выпуск сессии атомарны. Данные бота магазина не дают сессию продавца. |
| `sellerCabinet` в профиле покупателя | Единственная выдаваемая возможность входа — булево поле по сессии Telegram и активному членству в запрошенном магазине. Кабинет независимо проверяет сессию продавца и членство (§9.9). |
| `GET /auth/session`, чтение магазинов и прав | Профиль Telegram и магазины по сессии F4. На всех чтениях и командах кабинета проверяем активное членство для целевого магазина и разрешение на действие. |
| `POST /auth/logout`, полный выход администратора | Обычный выход отзывает текущую сессию; «Выйти из всех сессий» отзывает все сессии аккаунта. Действующий кабинет F4 сохраняет свой срок. Право работы в админке ограничено 12 часами с момента админского входа. На каждое чтение и команду `/admin/*` проверяем действующую сессию, выданную после входа через Telegram, роль D1 и ID из `PLATFORM_ADMIN_TELEGRAM_IDS`. `admin:grant` по Telegram-ID выдаёт роль; D15 проверяется при каждом запросе. |
| Telegram-обмен с приглашением | Привязываем токен и магазин к начатому обмену. При подтверждённом возврате проверяем срок 7 дней, отзыв, погашение, магазин и идентичность Telegram. В одной транзакции погашаем приглашение, назначаем владельца, выдаём сессию и записываем журнал. При замене прекращается прежнее членство, в журнале есть причина и администратор, прежнему владельцу отправляется уведомление при подключённом боте. Повторный возврат следует правилу единственного погашения, отдельное подтверждение в кабинете не требуется. |

### 4.2 Реестр, создание и карточка

| Запрос / команда | Проверки и эффект |
|---|---|
| `GET /admin/shops`, `GET /admin/shops/$id`, `GET /admin/shops/slug-availability` | Роль прежде запроса к данным. Фильтр и поиск по US-AD02, архив вне выдачи по умолчанию. Курсор со стабильной сортировкой, поиск по названию, slug и владельцу. Возвращаем поля §2. Slug в мастере и при смене адреса содержит 3–30 символов: латиница в нижнем регистре, цифры, дефис внутри. Проверяем уникальность среди текущих адресов магазинов, включая архив. Системные имена из D14/D15 и US-AD03: `www`, `app`, `api`, `admin`, `demo`, `help`, `mail`, `static`, `cdn`, `status`, `lavka`, `support`, `shop`, `tg`, `bot` и префикс `korzina`. Имя `seller` зарезервировано в F2 (§9.7). |
| `POST /admin/shops` | Валидируем оба шага, справочники региона и уникальность slug на записи. API и CLI используют общий сервис F2 и валидатор (§9.7). Мастер создаёт пустой `draft` с цветом по умолчанию, CLI для demo — `active`. Запись магазина, приглашения, адреса и события атомарна. Повтор с тем же ключом восстанавливает результат без второго магазина. |
| `PATCH /admin/shops/$id`, `POST /admin/shops/$id/invitations` | Изменение названия или оформления по версии с обновлением витрины. Цвет валидируем общим контрактом темы. Карточка читает статус и имя бота магазина. Подключение относится к S7. Перевыпуск ссылки отзывает прежнюю неиспользованную ссылку и пишет одно событие. При принятом приглашении только администратор выпускает ссылку для нового владельца с обязательной причиной. Прежний владелец сохраняет доступ до принятия новой ссылки. Владелец не подтверждает передачу. Ссылка, причина и событие выпуска фиксируются вместе. Конкурирующие команды сверяют версию и текущее состояние приглашения. |
| `GET /admin/shops/$id/features`, `PUT /admin/shops/$id/features/$key` | Реестр F5, неизвестный ключ отклоняется. Изменение override по версии, журнал только при фактическом изменении. Команда возвращает новое значение. Инвалидируются зависимые снимки одного магазина; устаревший публичный кеш не может разрешить выключенную функцию на сервере. |

### 4.3 Статус и адрес

| Статус | Следующие переходы | Доступ |
|---|---|---|
| `draft` · «Черновик» | В `active` или `archived` | Кабинет владельца доступен по членству, публичная витрина закрыта. |
| `active` · «Активен» | В `paused` или `archived` | Витрина, кабинет и оформление работают по правилам магазина. |
| `paused` · «Приостановлен» | В `active` или `archived` | Витрина, корзина и кабинет доступны. Checkout сообщает «Магазин временно не принимает заказы» и блокирует новый заказ. Доступные действия по существующим заказам продолжают работать. |
| `archived` · «Архив» | В `paused` | Публичная витрина и кабинет закрыты, данные и slug сохранены. Администратор видит карточку и журнал. |

- `POST /admin/shops/$id/status` проверяет роль, версию, переход, совпадение slug для архива и опциональную причину. Статус, журнал и задание уведомления фиксируются вместе на стороне платформы. Сразу после успешной команды граница должна действовать для оформления даже при потере инвалидации кеша или гонке двух запросов. Тест проверяет заказ в момент приостановки и после подтверждённой команды. Уведомление продавцу идёт через бота платформы, один логический результат на событие. Смена статуса фиксируется независимо от доставки. Если владелец не подключён к боту платформы, результат и карточка показывают «Уведомление не отправлено: владелец не подключил Telegram» (§9.8).
- `POST /admin/shops/$id/slug` применяет валидатор мастера, сверяет версию и в транзакции проверяет статус `draft`. Обновляет текущий адрес и журнал, прежний slug освобождается сразу. Открытие магазина и смена slug конкурируют по версии. После открытия адрес фиксирован, права администратора не обходят ограничение. Идентификатор магазина стабилен.
- Маршрутизация по D14/D15 использует wildcard в production без операций DNS на каждый магазин. На demo используем действующий адрес стенда (`?shop=slug` там, где wildcard отсутствует). Резолвер использует текущий slug и статус магазина.

### 4.4 Журнал, фоновые операции и бюджет

- `GET /admin/audit` — один endpoint журнала. Админский доступ проверяется до чтения. Выдача индексирована по магазину, действию и курсору. Для ссылки из карточки передаём тот же фильтр `shopId`. Запись содержит автора, время, целевой магазин, действие и разрешённую разницу. Токены и покупательские данные исключены.
- Один логический журнал и общий слой F3. Изменение и запись события коммитятся в одной транзакции своего хранилища. Для платформенных действий это D1, для последующих операций магазина — его транзакция с общим механизмом доставки в журнал, без записи от клиента и без отдельных журналов каждой фичи. Повтор не добавляет событие. Отказ локальной записи откатывает действие. Запись видна в общем и отфильтрованном списке.
- Уборка событий старше 12 месяцев, истёкших сессий, обменов, приглашений и ключей повтора — ограниченными порциями при наличии работы. Внешнюю доставку выполняем вне транзакции, ошибки отправки повторяются отдельным заданием в допустимых случаях. См. [PERFORMANCE §5–6](../PERFORMANCE.md).
- Бюджет для тестов в реализационных PR: реестр и страница журнала с постоянным числом индексированных запросов на страницу, без N+1 и без обхода всех магазинов; проверка членства переиспользует одно актуальное чтение F4. Числовые ограничения новых запросов закрепляются в реализационных PR после замера. Горячие пути витрины и оформления сохраняют существующие бюджеты. Админские чтения и команды измеряются по PERFORMANCE §6.

## 5. Ошибки сервера → поведение экрана

Новые коды ниже — целевой контракт; существующие совместимые ответы F4 переводятся в соответствующее состояние.

| Код | Где и что видно | Что сохраняется и куда дальше |
|---|---|---|
| `UNAUTHORIZED`, `AUTH_FAILED` | «Войдите в кабинет» при отсутствии или истечении сессии; «Не удалось подтвердить вход» при отклонённом подтверждении | Разрешённая цель входа сохраняется, защищённые данные скрываются. Вход или новая попытка подтверждения. |
| `TELEGRAM_EXCHANGE_EXPIRED`, `RATE_LIMITED` | «Ссылка для входа истекла» или «Повторите через <N> с» | Цель входа остаётся. «Начать заново» при истечении, повтор по `Retry-After` при лимите. |
| `AUTH_UNAVAILABLE` | «Telegram временно недоступен» | «Повторить» после восстановления доступности. Подтверждённое изменение статуса сохраняется, ошибки уведомления обрабатываются отдельно. |
| `FORBIDDEN` | «Нет доступа» | Закрыть защищённое содержимое и скрыть недоступный пункт. «В кабинет» в админке; у продавца переключение на доступный магазин. |
| `SHOP_NOT_FOUND`, `SHOP_CLOSED` | «Магазин не найден» / «Витрина пока закрыта»; для паузы на checkout — «Магазин временно не принимает заказы» | Пауза сохраняет корзину; из карточки отсутствующего магазина можно вернуться в список. |
| `INVITE_EXPIRED`, `INVITE_UNAVAILABLE` | «Ссылка недействительна или истекла. Попросите администратора прислать новую» | Запросить у администратора новую ссылку. Сессия с ошибкой принятия не даёт права на кабинет магазина. |
| `VALIDATION`, `SLUG_RESERVED`, `SLUG_TAKEN` | Ошибка у конкретного поля. Для занятого адреса «Адрес уже занят», для системного — «Этот адрес зарезервирован» | Введённое сохраняется, фокус на поле. Повтор после исправления. |
| `SLUG_LOCKED` | «Адрес можно изменить только в черновике» | Показать свежий статус и адрес только для чтения. |
| `VERSION_CONFLICT`, `INVALID_TRANSITION`, `IDEMPOTENCY_CONFLICT` | «Данные изменились. Проверьте перед сохранением» / «Этот переход больше недоступен» / «Не удалось подтвердить повтор действия» | Сверить свежую версию или итог исходной команды. Новая осознанная команда получает новый ключ. |
| Сеть / 5xx | «Нет подключения» / «Не удалось выполнить действие» | Повторить тот же вход с тем же ключом. Если результат уже зафиксирован, показать его без второй команды. |

## 6. Правила

1. **П1. Изоляция:** сессия не даёт доступа к чужому магазину или роли, отзыв прав действует на открытых устройствах. [DOMAIN «Роли»](../DOMAIN.md#роли)
2. **П2. Административный доступ:** подтверждённый Telegram-ID из списка и роль обязательны одновременно, срок до 12 часов, отзыв всех сессий с UI. [D15](../DECISIONS.md#принятые) · [US-AD01](../stories/platform-admin.md#us-ad01--вход-администратора)
3. **П3. Одна операция:** один магазин при двойном создании; приглашение 7 дней, одно погашение; перевыпуск отзывает прежнее. [US-AD03–04](../stories/platform-admin.md)
4. **П4. Статус:** пауза сохраняет работу по прежним заказам; архив закрывает кабинет и витрину, сохраняя данные. [US-AD05](../stories/platform-admin.md#us-ad05--статус-магазина) · [D20](../DECISIONS.md#принятые)
5. **П5. Флаги:** выключение действует только на выбранный магазин и сохраняет данные. [US-AD06](../stories/platform-admin.md#us-ad06--дополнения-магазина)
6. **П6. Один журнал:** изменение и событие атомарны, записи читаемы 12 месяцев. [AD3](../tasks/AD3.md)
7. **П7. Адрес:** редактирование доступно только для `draft`. После открытия slug постоянный. [US-AD08](../stories/platform-admin.md#us-ad08--адрес-витрины) · §9.10
8. **П8. Telegram:** браузерный обмен и Mini App подтверждают идентичность через бота платформы. На demo проверяем оба входа. [S1](../tasks/S1.md) · §9.1, §9.4
9. **П9. Регион и создание:** каждый новый магазин в мастере — пустой черновик с цветом по умолчанию. Страна задаёт редактируемые валюту и пояс. §9.10

| Given | When | Then | Проверка |
|---|---|---|---|
| Продавец с двумя магазинами | Входит через тестового бота в браузере и через Mini App, открывает профиль и переключает магазин | Один Telegram-аккаунт, только свои магазины, профиль Telegram и две вкладки «Главная» и «Ещё» (§9.1, §9.3, §9.4) | smoke, холст |
| Создан Telegram-обмен | Отмена, истечение, повторное погашение, возврат в другом браузере, подпись бота магазина или просроченная `initData` | Только действительный обмен бота платформы выдаёт сессию один раз, лимит возвращает `Retry-After` (§9.1) | сервер-тест |
| Сотрудник без права, чужой, отозванный или архивный магазин | Открывает раздел напрямую и вызывает его API | Доступ закрыт, отсутствует недоступный пункт | сервер-тест, холст |
| Админ без магазина; сотрудник без роли; аккаунт с ролью без Telegram-ID из списка; устаревшая админская сессия | Открывают список и API, админ завершает все сессии | Доступ только у администратора с обоими условиями и актуальной сессией (D15); выход действует на другом устройстве | сервер-тест, smoke, холст |
| Член команды текущего магазина, гость, покупатель по номеру, чужой покупатель или член другой команды | Открывает профиль, член команды переходит в кабинет с сессией продавца и без неё | Пункт доступен только члену текущего магазина, оба пути ведут в тот же кабинет (§9.9). | сервер-тест, холст |
| Реестр с архивом, пустой список и поиск без совпадений | Админ применяет фильтр и открывает карточку | Счётчики и карточка согласованы, архив доступен через фильтр; в ответах нет данных покупателей | сервер-тест, холст |
| Админ заполняет два шага, возвращается назад, дважды отправляет или теряет ответ | Создаёт магазин и передаёт ссылку | Один пустой черновик с цветом по умолчанию, шаги сохранили ввод, есть ровно одна действующая ссылка и событие. Цвет можно сменить в карточке. | сервер-тест, smoke, холст |
| Выдана ссылка владельцу | «Войти через Telegram и принять» запускает обмен, два аккаунта пытаются принять ссылку одновременно. Затем проверяются перевыпуск и истечение 7 дней | Одна кнопка и одно принятие, победитель входит в кабинет именно этого магазина. Повторный вход работает через меню бота, профиль витрины или адрес кабинета. В D1 только хеш приглашения (§9.5, §9.10). | сервер-тест, smoke, холст |
| Владелец принял приглашение | Админ выпускает ссылку замены без причины и с причиной, затем новый владелец принимает ссылку | Без причины отказ. При принятии атомарно передаётся роль, есть журнал с причиной и уведомление прежнему владельцу при подключённом боте. Согласие прежнего владельца не требуется (§9.2) | сервер-тест, холст |
| Активный магазин с заказом и наполненной корзиной | Админ приостанавливает, архивирует и восстанавливает | Пауза действует с прогретым кешем, ранее созданный заказ доступен, новый заказ после паузы отклонён; архив закрывает витрину и кабинет, восстановление ведёт в паузу | сервер-тест, smoke, холст |

## 8. Не входит

- Вход и привязка продавца по email, письма и почтовый провайдер (§9.1, D17) — отдельная задача позже.

- Заказы, счётчик активных заказов, финансовые экраны и рабочий день — O1/O2, O3, O5/O9. Календарь и список сборки — O3, сообщения в шапке — O8.
- Редактор товаров и категорий — S2/S3. Настройки «Получение и доставка», «Оплата», «О магазине» — S4/S5/S6. Импорт и экспорт — AD4.
- Экран подключения бота, управление сотрудниками, история действий для продавца и мастер первого запуска — S7/S8/S9.
- «Покупатели» — A13b; «Продвижение» и интерфейсы дополнений — блоки A; отдельный десктоп с боковым меню — A16. Свой домен продавца — задача фазы A.
- Доступ поддержки к данным покупателей и физическое удаление магазина требуют отдельных решений. Действия на prod и в Lavka исключены из приёмки блока.

## 9. Решения Андрея (19.11.2026)

1. **9.1 · D17 — почта отложена.** Вход продавца в блоке 4 только через бота платформы, в браузере и Mini App. Заглушка почты F4 используется локально. Будущая задача выбирает провайдера и оценивает стоимость по COSTS.md.
2. **9.2 · D16 — смена владельца.** После принятия приглашения владельца меняет администратор: обязательная причина, запись в журнале, уведомление прежнему владельцу через бота платформы (если подключён). Согласие прежнего владельца не требуется.
3. **9.3 · Вкладки.** В блоке 4 в кабинете только «Главная» и «Ещё». Остальные вкладки появляются в своих блоках.
4. **9.4 · Профиль.** Показывает подтверждённый Telegram. Привязка второго способа входит в будущую задачу.
5. **9.5 · Приглашение.** Администратор передаёт ссылку или QR вручную. В мастере — имя продавца и комментарий для администратора. Принимает первый подтвердивший ссылку аккаунт Telegram. Срок 7 дней, одно погашение.
6. **9.6 · Админка.** Только после входа через Telegram с ID из `PLATFORM_ADMIN_TELEGRAM_IDS` (D15), срок 12 часов.
7. **9.7 · Адрес магазина.** Один валидатор для всех новых адресов (мастер, смена адреса, CLI): 3–30 символов, латиница в нижнем регистре, цифры, дефис внутри; закрытые имена — объединение D14/D15, US-AD03 и системных F2 (включая `seller`) и префикс `korzina`. Существующие адреса не меняем. Мастер создаёт `draft`, CLI для demo — сразу `active`.
8. **9.8 · Уведомление о статусе.** Статус меняется всегда; если владелец не подключён к боту платформы, в карточке «Уведомление не отправлено: владелец не подключил Telegram».
9. **9.9 · Вход в кабинет из витрины (19.11.2026).** В профиле покупателя на витрине магазина — пункт «Кабинет продавца». Виден, только если Telegram-аккаунт вошедшего покупателя состоит в команде **этого** магазина (активное членство). Нажатие открывает кабинет этого магазина; если сессии продавца нет — вход через бота платформы с возвратом сюда же. Сервер решает видимость по сессии и членству (клиенту приходит только `sellerCabinet: true/false`), права кабинета проверяются как обычно. Гостю, покупателю по номеру и не члену команды пункт не показывается. Назначение продавца — по-прежнему ссылкой-приглашением (§9.5). Тест: член команды видит пункт, другой покупатель и член команды другого магазина — нет.

10. **9.10 · Упрощения блока 4 (19.11.2026), приоритет над §1–§7 — привести их в соответствие.**
    - **Страна, валюта, пояс.** Выбирается только страна; валюта и часовой пояс подставляются, меняются в том же шаге. Сверху списка: Россия RUB · Москва, Беларусь BYN · Минск, Казахстан KZT · Алматы, Узбекистан UZS · Ташкент, Кыргызстан KGS · Бишкек, Армения AMD · Ереван, Грузия GEL · Тбилиси, Азербайджан AZN · Баку, Турция TRY · Стамбул, ОАЭ AED · Дубай, Вьетнам VND · Хошимин, Таиланд THB · Бангкок, Индонезия IDR · Макассар (Бали), Сербия RSD · Белград, Черногория EUR · Подгорица, Кипр EUR · Никосия, Израиль ILS · Иерусалим. Ниже — поиск по всем странам ISO 3166 (названия через `Intl.DisplayNames`), валюта по стране из таблицы ISO 4217, пояс — основной пояс страны. Валюты — все ISO 4217, USD и EUR сверху. Таблица страна → валюта/пояс — один файл данных в `src/shared`, без библиотек.
    - **Мастер — два шага:** «Магазин» (название, адрес витрины, страна → валюта и пояс) и «Владелец» (имя продавца, комментарий) → «Создать». Цвет витрины — по умолчанию, меняется в карточке («Оформление»). Выбора «Пустой магазин / Демо-каталог» нет: магазин всегда пустой; перенос каталога — AD4.
    - **Приглашение:** по ссылке экран «Приглашение в магазин <название>» с одной кнопкой «Войти через Telegram и принять» (вход через бота платформы и принятие — одним потоком) → кабинет. Дальше продавец входит без ссылки: бот платформы (кнопка меню), «Кабинет продавца» в профиле витрины (§9.9) или адрес кабинета.
    - **Адрес витрины меняется только у черновика.** После первого открытия магазина адрес постоянный: поле в карточке только для чтения. Алиасы, перенаправление 90 дней и их уборка — не делаем (US-AD08 сокращается до смены адреса черновика).
    - **Журнал — один** («Журнал» из реестра) с фильтром по магазину; ссылка из карточки открывает его с этим фильтром. Без отдельного экрана «Журнал магазина» и фильтра «Период»; «Действие» — оставить.
    - **Бот магазина** подключает продавец в кабинете (S7, блок 8). В блоке 4 карточка показывает только «Бот подключён · @имя» / «Бот не подключён».
