## 2. Данные и команды

Названия новых контрактов и команд описывают назначение и согласуются при реализации. Права, состояния, готовность и результат теста рассчитывает сервер.

| Контракт и источник | Поля, чтение и обновление |
|---|---|
| `Role`, `Permission` из `auth.ts` и новый `TeamAccess` | Сервер хранит членство `owner` / `employee`, выбранный шаблон и действующие права. Шаблоны «Управляющий», «Сборщик», «Бухгалтер», «Настроить вручную» не выдают членство владельца. Границы матрицы и роль владельца — §10.1–§10.2. |
| `TeamMember`, `TeamInvite` | В карточке сотрудника хранятся идентификатор, имя для списка, роль, права и версия. У приглашения есть идентификатор, роль, срок и состояние `pending`, `accepted`, `expired`, `revoked`. Список по магазину, карточка по идентификатору. После изменения, возврата из Telegram и при конфликте перечитывается затронутый список или запись. |
| `StaffNotifications`, `ShopBotStatus` | Переключатели `newOrders`, `paymentsAndReceipts`, `cancellations`, эффективное право на каждую тему и возможность отправить тест выбранным ботом. Для экрана бота — имя подключённого бота либо состояние «Бота подключает администратор Korzina». Токен, адресат Telegram и контактные данные к экрану не передаются. |
| `TeamAuditPage` | Страница журнала AD3 содержит курсор, время, актора, раздел, действие и разрешённые значения «было» и «стало». Новый фильтр или магазин сбрасывает курсор. Фильтр по дате учитывает часовой пояс магазина, время выводится по правилам кабинета. |
| `LaunchReadiness` и `AdminShopStatus` из `admin.ts` | Статус `draft` / `active` / `paused`, актуальная ревизия готовности, обязательные пункты и их состояние, право открытия. Состояние тестовой покупки относится к версии проверенных настроек. Чтение при входе, после сохранения связанной настройки и после сбоя открытия. |
| Покупка · `CheckoutCommand`, `PurchaseQuote` из `checkout.ts` | Переиспользуются поля покупки. Тестовая команда `checkout` с `dryRun: true` и подтверждённым тестовым контекстом возвращает результат проверки, без номера заказа. Тестовый расчёт нельзя применить как обычный. |

| Команда | Вход → результат | Повторы и ошибки |
|---|---|---|
| `getTeam`, `getTeamMember`, `getShopBotStatus` | Текущий магазин и идентификатор сотрудника для карточки → разрешённые данные. | `FORBIDDEN`, `NOT_FOUND`. |
| `createStaffInvite`, `revokeStaffInvite` | Шаблон/права либо идентификатор ожидающего приглашения → ссылка и срок либо новый статус. | `Idempotency-Key`. `FORBIDDEN`, `NOT_FOUND`, `VALIDATION`, `STALE_VERSION`. |
| Принятие приглашения в Telegram | Ссылка, подлинное событие бота и Telegram-аккаунт → членство и переход в кабинет. | Повтор тем же получателем безопасен. Ошибки `ALREADY_MEMBER`, `INVITE_EXPIRED`, `INVITE_REVOKED`, `INVITE_USED`, `INVITE_INVALID`. |
| `updateTeamMember`, `revokeTeamAccess` | Идентификатор, версия, изменяемые права и переключатели → актуальная карточка либо подтверждённый отзыв. | `Idempotency-Key`. `FORBIDDEN`, `NOT_FOUND`, `VALIDATION`, `STALE_VERSION`. |
| `sendStaffTest` | Идентификатор сотрудника → статус отправки личного теста конкретному адресату. | `Idempotency-Key`. `FORBIDDEN`, `BOT_NOT_STARTED`, `TELEGRAM_UNAVAILABLE`, `DELIVERY_UNKNOWN`. |
| `getTeamAudit`, `getLaunchReadiness` | Фильтры и курсор либо выбранный магазин → страница журнала либо готовность. | `FORBIDDEN`, `NOT_FOUND`, ошибки чтения. |
| `checkout` для теста | `dryRun: true`, тестовый контекст, тестовая ревизия расчёта и выбранный способ → результат проверки. | `Idempotency-Key`, повтор проверки без эффектов. Ошибки расчёта блока 2, `TEST_CONTEXT_INVALID`, `FORBIDDEN`. |
| `openShop` | Магазин, показанная версия готовности → актуальный статус и версия. Кабинет и админка используют общее правило команды с условием для админки из §10.6. | `Idempotency-Key`. `NOT_READY` с пунктами, `FORBIDDEN`, `ADMIN_PAUSED`, `STALE_VERSION`. |

## 3. Экраны

### 3.0 Общие состояния и доступность

Правила действуют для каждого экрана и шторки ниже. При первом запросе виден каркас. При ошибке — «Не удалось загрузить» и «Повторить». Без сети — «Нет подключения к интернету». Пустое состояние указано у списков. Форма сохраняет введённое при сбое, показывает «Данные изменились. Обновите экран» при конфликте и предлагает «Обновить». При отзыве права защищённые данные и действия убираются, показывается «Недостаточно прав». Кнопки команд блокируются до ответа, шторку можно закрыть после завершения запроса. Ошибки привязаны к полю или действию, фокус переводится к первой ошибке или заголовку результата. Область касания ≥ 44 px, управление доступно с клавиатуры, значки и цвет дублируются текстом. Тексты в таблицах и §5 предназначены для интерфейса.

### 3.4 «История действий»

Обычные шаблоны витрины и `checkout` из [блока 2](purchase.md), переключение только из авторизованного тестового контекста.

### 3.7 Публичная витрина до запуска

Покупатель черновика видит действующее состояние `EmptyState` с заголовком «Магазин скоро откроется» и подписью «Загляните позже.» У приостановленного магазина остаётся «Магазин временно не принимает заказы». После открытия при повторном заходе показывается витрина. Покупатель не видит чек-лист, тестовую полосу и команду открытия.

## 4. Сервер: команды и правила

### 4.1 Команда, права и журнал

1. Чтение и запись проверяют сессию, актуальное членство выбранного магазина и право на действие, затем идентификатор, версию и входные данные. Действия команды доступны владельцу. Смена платформой владельца остаётся действующим процессом блока 4. Связь с шаблоном «Владелец» описана в §10.2. Шаблон управляющего не даёт доступа к команде, роли сборщика и бухгалтера не дают права владельца. Модель действующих разрешений должна одинаково работать в кабинете, API, прямых ссылках и подписках. [§9.2 блока 4](seller-admin.md#9-решения-андрея-19112026)
2. Готовая роль подставляет права, сервер проверяет ручной набор и запрещает расширить его неделегируемыми правами. Изменение прав и отзыв сразу прекращают доступ по затронутому членству на каждом устройстве, включая открытые подписки. Доступ к другим магазинам сохраняется. При одновременной правке сохраняется первая команда с актуальной версией. Поздняя получает `STALE_VERSION`.
3. Изменения команды, прав, приглашений и доступа журналируются вместе с записью изменения в AD3. Чтение использует тот же журнал с фильтрами и курсором. В журнал попадают только разрешённые поля изменения, без ссылок-приглашений, токенов, реквизитов, чеков, данных покупателей и переписки. Поля фильтров и предел страницы проверяются на сервере.

### 4.2 Приглашение

1. Владелец создаёт приглашение в конкретный магазин с проверенным набором прав. Сервер выбирает подключённого бота магазина либо бота Korzina и выдаёт одноразовую ссылку на семь дней. Бот проверяет подлинность Telegram, канал и привязку ссылки к магазину. Ссылку можно отозвать до принятия.
2. Принятие атомарно проверяет срок, отзыв и погашение, создаёт или привязывает действительное членство и добавляет событие журнала. В гонке двух аккаунтов выигрывает первая успешная запись. Повтор тем же аккаунтом возвращает состояние его членства. Второй аккаунт, истёкшая или отозванная ссылка отклоняются. Повтор принятия не восстанавливает отозванный доступ. Уже действующий сотрудник не получает второе членство или новые права через приглашение.
3. Сохранение членства и ответ Telegram — отдельные исходы. Сбой отправки кнопки после принятия не откатывает членство, повтор тем же аккаунтом получает кнопку через того же бота, если доступ по-прежнему действует.

### 4.3 Личные уведомления

1. Сервер вычисляет право на каждую тему и настраиваемое предпочтение. Базовая привязка тем: «Новые заказы» и «Отмены» проверяют `orders`, «Оплаты и чеки» — `payments`. Начальные значения у владельца и управляющего — все темы, у сборщика — новые заказы, у бухгалтера — оплаты и чеки. Выключенный переключатель, отозванное членство или отсутствие права исключают получателя. Настройка не расширяет права. Переход между ролями и начальные значения вручную — §10.4.
2. Одно личное тестовое сообщение идёт указанному действующему сотруднику через бота магазина либо, при отсутствии бота магазина, через бота Korzina. Сервер проверяет право инициатора и действующую связь адресата с выбранным ботом. Тест использует нейтральный текст, без заказов и денег. При неизвестном исходе Telegram возвращается `DELIVERY_UNKNOWN`. Повтор того же ключа не инициирует вторую отправку. Сообщения по событиям и работа очереди O4 относятся к блоку 9. Действующая отправка «Новый заказ» O2 требует решения §10.3.

### 4.4 Готовность, открытие и тестовая покупка

1. Сервер возвращает обязательные пункты S9 из актуальных данных S2 и S4–S6. Пункты меняются по факту сохранения в соответствующих настройках. Валидация открытия повторяет обязательные проверки после подтверждения, включая действующие ограничения платформы для черновика. Детальные границы чек-листа — §10.5.
2. Владелец магазина и администратор платформы могут открыть магазин. Другие роли получают `FORBIDDEN`. Устаревшая готовность требует перечитать пункты, а появившийся блокер возвращает `NOT_READY`. Побеждает один переход из `draft` в `active` с одной записью статуса и журнала. Повтор с тем же ключом возвращает результат первой команды при действующем доступе. При гонке владельца и администратора применившаяся команда оставляет один переход, другой экран получает актуальный открытый статус. Приостановка владельца осуществляется существующими средствами блока 7, администратор использует приостановку платформы. Только администратор снимает паузу платформы.
3. Тестовый контекст проверяется на каждом запросе и связан с магазином и вошедшим сотрудником с правом проверки (§10.7). Проверка из черновика допускает его тестовую витрину, соблюдая изоляцию от публичного оформления. Обычные ограничения по корзине, цене, остаткам, видимости, минимальной сумме, получению, времени и оплате проверяются по B10 на актуальных данных, с имитацией оплаты и чека. Правила доступа к тесту на паузе — §10.7.
4. Тест не создаёт заказ, платёж, чек, запись истории заказа или событие отправки. Не занимает интервалы, не резервирует и не списывает товар, не очищает корзину покупателя, не меняет профиль, реальные заказы, деньги и статистику. Любой тестовый расчёт недействителен для реального оформления. Публичный запрос с `dryRun: true` не открывает тестовый доступ. Результат проверки относится к использованной версии условий. Изменения запускают предложение повторить проверку, открытие по-прежнему возможно без теста.
5. Публичный статус и оформление проверяются по текущему магазину. После открытия перечитывается статус кабинета и витрины. Закрытый черновик и пауза остаются ограничением API независимо от текущего экрана клиента.

### 4.5 Чтение, повторы и бюджеты

- Проверка права предшествует возврату защищённого результата, включая повторы. `Idempotency-Key` связан с актором, магазином, операцией и входными данными. Повтор с изменённым содержимым отклоняется по существующему правилу команд.
- Список команды и журнал читаются ограниченными страницами без запроса на каждую строку. История использует существующий журнал. Готовность перечитывается при переходах и изменении зависимых настроек. Устаревший кэш не разрешает запись и не выдаёт доступ.
- Для горячих путей применяются существующие лимиты и тесты бюджета [PERFORMANCE §6](../PERFORMANCE.md#6-измерение-и-бюджеты). Отдельно проверить, что карточки команды и история не добавляют N+1, тестовая покупка не добавляет работу в фон обычного заказа, а чтение готовности не загружает каталог целиком.

## 5. Ошибки сервера → поведение экрана

Имена новых ошибок уточняются вместе с контрактом. Ошибки оформления с готовыми текстами и переходами используются из [блока 2](purchase.md#5-ошибки-сервера--поведение-экрана).

| Ошибка | Где и что видно | Что сохраняется и действие |
|---|---|---|
| `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND` | «Войдите через Telegram», «Недостаточно прав», «Запись не найдена» | Вход возвращает к разрешённому шагу, при отказе или недоступной записи — «К списку» / «На главную». Защищённая карточка не остаётся открытой. |
| `VALIDATION`, `STALE_VERSION` | «Проверьте выбранную роль и права» или «Данные изменились. Обновите экран» | Показать проблемное поле, сохранить ввод, перечитать текущие данные по «Обновить» и дать заново подтвердить изменение. |
| `INVITE_EXPIRED`, `INVITE_REVOKED`, `INVITE_USED`, `INVITE_INVALID` | «Срок действия приглашения истёк», «Приглашение отозвано», «Приглашение уже использовано», «Ссылка недействительна» | Адресату «Попросите владельца прислать новую ссылку». Владелец может создать новую ссылку с экрана команды. |
| `ALREADY_MEMBER` | «У вас уже есть доступ к магазину» | Действующему сотруднику «Открыть кабинет». Права и членство сохраняются. |
| `BOT_NOT_STARTED` | «Сотруднику нужно открыть бота в Telegram» | Переключатели сохраняются, после подключения «Прислать тестовое». |
| `TELEGRAM_UNAVAILABLE`, `DELIVERY_UNKNOWN` | «Telegram временно недоступен» или «Не удалось подтвердить доставку сообщения» | Настройки сохраняются. При известном отказе «Попробовать ещё раз». При неизвестном результате сначала «Попросите сотрудника проверить чат». |
| `NOT_READY`, `ADMIN_PAUSED` | «Завершите обязательные настройки» с отмеченными пунктами или «Магазин приостановлен администратором» | Перечитать готовность. Открыть нужную настройку либо вернуться на «Главную». |
| Сбой после подтверждения открытия | «Проверяем, открылся ли магазин» | «Проверить статус». Если подтверждён черновик, повторить исходную попытку. |
| `TEST_CONTEXT_INVALID`, `SHOP_CLOSED` | «Тестовый режим завершён» или действующий текст недоступности магазина | «Вернуться к настройке» при наличии доступа. Публичный сценарий сохраняет своё состояние. |
| Изменения расчёта и ошибки покупки | Сообщение и действие из блока 2, в результате теста «Тестовая покупка выявила проблему» | Дать выбрать данные заново или вернуться в нужную настройку. Реальная корзина и заказы сохраняются. |

## 6. Правила

- П1. Команда действует в пределах одного магазина. Проверка разрешений на сервере сопровождает действия интерфейса. Отзыв доступа немедленный. [S8](../tasks/S8.md), [DOMAIN «Роли»](../DOMAIN.md#роли).
- П2. Приглашение действует семь дней, один раз и до отзыва. Повтор тем же адресатом безопасен. [S8, решение 3](../tasks/S8.md).
- П3. Сообщения личные. И право, и включённый переключатель обязательны для уведомлений по событиям. [S7, решения 1–2](../tasks/S7.md).
- П4. Открытие даёт возможность принимать заказы после проверок. Административная пауза сохраняет приоритет. [S9, решение 5](../tasks/S9.md), [блок 7](shop-settings.md).
- П5. Тестовая покупка необязательна и не создаёт бизнес-записей. Публичное оформление остаётся действующим сценарием B10. [S9, решение 6](../tasks/S9.md), [DOMAIN «Оформление»](../DOMAIN.md#оформление-5-t03t04).

## 11. Ответы Андрея на §10 (21.11.2026)

При расхождении с предыдущими разделами и карточками S7–S9 действуют эти ответы. Проверки всех восьми пунктов находятся в §7.

1. **§11.1 · Управляющий — всё, кроме сотрудников:** «Главная», заказы, сборка, товары, деньги, настройки (доставка, часы, оплата, «О магазине», «Витрина»), история действий, открыть и приостановить магазин, тестовая покупка. Меняет правило блока 7 §11.3: настройки — владелец **и управляющий**. Чат по заказу (O8) — по праву «Заказы»; остатки — по праву «Товары».
2. **§11.2 · Владелец один.** Назначить второго владельца в S8 нельзя; сменить владельца — только администратор платформы (D16). В приглашении роли: «Управляющий», «Сборщик», «Бухгалтер», «Настроить вручную».
3. **§11.3 · Уведомления — настраиваются по ролям** (заменяет переключатели в карточке сотрудника из решения 2). Экран «Ещё → Уведомления» (владелец и управляющий): таблица «роль × событие» с галочками — роли «Владелец», «Управляющий», «Сборщик», «Бухгалтер», «Вручную»; события «Новые заказы», «Оплаты и чеки», «Отмены». Галочка недоступна (серая), если у роли нет права на раздел. Изменение применяется сразу ко всем сотрудникам роли. Значения по умолчанию: владелец и управляющий — всё; сборщик — новые заказы и отмены; бухгалтер — оплаты и чеки; «вручную» — всё, на что есть права. Индивидуальных переключателей у сотрудника нет; в карточке сотрудника — «Прислать тестовое». Строка «Покупатель увидит» не нужна; под таблицей одна строка «Сейчас получают: …» (имена по событию).
4. **§11.4 · «Новый заказ» (O2) — сразу по §11.3.** Уже работающая отправка O2 с этого блока учитывает роль, право и галочку роли; проверка — в момент отправки (уже поставленные в очередь тоже проверяются). Оплаты и отмены — O4 (блок 9).
5. **§11.5 · Смена роли и бота.** Сотрудник получает уведомления своей новой роли сразу. Если бот магазина сменился, у сотрудников, которые ещё не начали чат с новым ботом, в кабинете плашка «Бот магазина сменился — нажмите, чтобы снова получать уведомления» со ссылкой на нового бота.
6. **§11.6 · Готовность к открытию:** есть название; хотя бы один товар в продаже (видимый, с доступной фасовкой); включён хотя бы один способ получения; включён хотя бы один способ оплаты. Бот — не обязателен. Часы не обязательны — по умолчанию «каждый день 9:00–20:00».
7. **§11.7 · Открытие из админки:** тот же список готовности; если не всё готово — «Не всё готово. Открыть всё равно?» и открытие с подтверждением. Владелец и управляющий открывают только при полной готовности.
8. **§11.8 · Тестовая покупка:** владелец и управляющий, в любом статусе магазина; результат не сохраняется — виден, пока открыт экран.

## 12. Правки Андрея после холста (21.11.2026)

Этот раздел главнее §1–§11 и карточки S9. Ревизия холста `474850666720927744`.

1. **§12.1 · Тестовой покупки нет.** Убрать режим тестовой покупки целиком: полосу «Тестовый режим», `checkout` с `dryRun`, пункт «Тестовая покупка» в списке готовности, результат теста, повтор после изменения настроек. Отменяет решение 6 и §11.8. Причина: заказ не создаётся, поэтому проверка не показывает полный путь (уведомление, заказы, чек, выдача), а настоящий заказ продавец может сделать сам и отменить.
2. **§12.2 · Вместо неё — «Открыть витрину как покупатель»** необязательной строкой внизу списка готовности: открывает витрину магазина (для черновика — предпросмотр, видный только команде). Подпись: «Чтобы проверить всё целиком, сделайте заказ и отмените его».
3. **§12.3 · Приёмка.** Строки §7 про тестовую покупку и §11.8 удалить; добавить строку §12.2 (ссылка открывает витрину; черновик виден только команде). Остальное без изменений.

4. **§12.4 · Предпросмотр — это настоящая витрина, а не отдельная страница.** «Открыть витрину как покупатель» открывает **ту же витрину покупателя** (главная с мозаикой категорий, карточки товаров с фото, поиск, корзина, оформление — экраны блоков 1–3), а не упрощённый список товаров. Отличие одно: сверху тонкая плашка «Предпросмотр для команды · Покупатели пока не видят магазин» (у открытого магазина плашки нет). Оформить заказ в черновике нельзя: на «Оформить» — «Магазин ещё не открыт» (у открытого — обычный заказ). На холсте — кадр главной витрины с плашкой; отдельный кадр «Товары» списком убрать. Тест: предпросмотр черновика отдаёт те же данные витрины команде и `NOT_FOUND` / «скоро откроется» постороннему.

5. **§12.5 · Ни одного нового экрана для предпросмотра — тот же код витрины.** Предпросмотр — это **тот же адрес и тот же код витрины** (`<slug>.korzina.app`, на demo `demo.korzina.app/?shop=<slug>`), открытый членом команды. Новых маршрутов, страниц, компонентов и запросов для предпросмотра не создавать. Единственные отличия: (1) сервер отдаёт данные черновика, если запрос от члена команды магазина (то же правило доступа на всех эндпоинтах витрины); (2) один общий компонент плашки «Предпросмотр для команды» в шаблоне витрины; (3) `checkout` черновика отвечает «Магазин ещё не открыт». Кнопка в кабинете — обычная ссылка на адрес витрины. Тест: ссылка из кабинета ведёт на адрес витрины; в коде нет отдельного маршрута или компонента предпросмотра (проверка `check:arch` или тест маршрутов). На холсте предпросмотр не рисуется отдельно — достаточно существующих кадров витрины и кадра плашки.

6. **§12.6 · В предпросмотре всё работает как у покупателя, включая заказ** (главнее §12.4 и §12.5 в части оформления). Член команды в закрытом магазине проходит **весь путь покупателя по настройкам продавца**: витрина, каталог, поиск, корзина, доставка и самовывоз, карта и зоны, интервалы и часы, минимальная сумма, способы оплаты, QR и чек — и **оформляет настоящий заказ**. Заказ попадает в «Заказы», уведомления уходят по ролям, его можно собрать, выдать или отменить. Посторонние в закрытом магазине по-прежнему видят «Магазин скоро откроется» и оформить не могут (тест). Отличие от открытого магазина — только доступ и плашка «Предпросмотр для команды» сверху. Правило «checkout черновика отвечает «Магазин ещё не открыт»» отменено для членов команды. Тест: член команды оформляет заказ в черновике тем же `checkout`, что покупатель открытого магазина; посторонний — отказ.
