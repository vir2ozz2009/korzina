# Спецификация · Блок 9 · Рабочий день и уведомления

## 0. Рамки

- **O3 / US-R09.** Сводка на «Главной» кабинета, переходы в отфильтрованные «Заказы», список сборки, календарь заказов и сообщение о ближайшем времени на витрине вне часов работы.
- **O4 / US-R01.** Личные уведомления сотрудникам по таблице ролей, включая оплаты и чеки, отмены и низкий остаток. Покупателю в Telegram приходят уведомления о четырёх этапах. «Новый заказ» и денежные уведомления покупателю уже работают в блоке 5.
- Источники: [O3](../tasks/O3.md), [O4](../tasks/O4.md), [US-R01 и US-R09](../stories/seller-orders.md), [DOMAIN · получение, заказ, деньги и Telegram](../DOMAIN.md#получение-5), [DECISIONS · D13, D20 и решения от 22.11.2026](../DECISIONS.md). Существующие сценарии: [заказы блока 5](seller-orders.md), [остатки блока 6](seller-catalog.md#11-ответы-андрея-на-10-20112026), [расписание и пауза блока 7](shop-settings.md), [роли и запуск блока 8](team-and-launch.md).
- Правила от 22.11.2026 применяются по §9. Новые подписи и предложенный вид отмечены в разделе экранов. Ответы на §10 нужны перед сборкой затронутых сценариев. Код блока 9 начинается после приёмки блока 8.

## 2. Данные

Имена новых ответов в таблице рабочие. Даты дня и месяца — календарные строки `YYYY-MM-DD` и `YYYY-MM` по часовому поясу магазина. Суммы — целые в минимальных единицах валюты с кодом валюты. Числа, состав выборки, права и доступность рассчитывает сервер.

| Чтение | Вход → ответ | Когда обновляется |

| «Заказы» / `SellerOrdersQuery`, `SellerOrderPage` | Существующие фильтры, курсор и ревизия плюс дата, этап или причина действия по ссылкам O3. Список `SellerOrderSummary`, число совпадений для всей выборки, курсор. | Изменение выборки сбрасывает курсор. Прежняя ревизия и курсор действуют только для той же выборки. | Доступность в витрине | Публичные данные выбранного магазина дополняются серверным состоянием расписания и ближайшим доступным получением: дата, способ, начало и конец для интервала. Если время неизвестно, значение отсутствует. **Команды.** Галочка использует существующую `notificationChange` (`role`, `topic`, `enabled`). Результат — сохранённая таблица и получатели. Повтор отправляет тот же явный `enabled` с исходным `Idempotency-Key` по правилам блока 8. «Список сборки» и календарь только читаются. Переходы заказа и `checkout` сохраняют входы, ревизии и `Idempotency-Key` блоков 2, 3 и 5. Новых пользовательских команд для отправки события нет. Ошибки — §5.

## 3. Экраны

### 3.0 Общие состояния и доступность

Существующие шаблоны, `QueryBoundary` и UI-кит. При первом чтении — скелетон по форме содержимого. Ошибка загрузки — «Не удалось загрузить» и «Повторить». Без сети — «Нет подключения к интернету». При обновлении той же выборки её последнее успешное состояние остаётся на экране. При смене магазина, дня, месяца или фильтра показывается только состояние новой выборки. Потеря доступа убирает защищённые данные и показывает «Недостаточно прав». Для состояний без данных используются тексты соответствующего экрана.

Предложенные подписи приведены в кавычках. У интерактивных элементов область касания ≥ 44 px и видимый фокус. Фильтры и дни доступно объявляют выбранность. У счётчиков читаются заголовок и значение. Просрочка подписана текстом. При ошибке действия фокус переходит к сообщению, после перехода — к заголовку экрана. Новых полей ввода нет.

Существующая «Главная», шаблон кабинета. Состав сверху вниз для открытого магазина:

Сохранённый поиск или другой фильтр не может сузить этот переход. | Операция только читает данные. Пока выборка грузится, показан её скелетон. |

### 3.2 «Заказы» после перехода из сводки или календаря

Действующий список и карточка O2. Сверху заголовок «Заказы», затем применённая дата и причина выборки, существующие фильтры и список. Предложение для вида — (дата) и (фильтр) видны как подписанные чипы. Состав карточек, поиск, платежи и действия — [блок 5 §12](seller-orders.md#12-вариант-a-экрана-заказы).

| Нажатие / состояние | Результат и запрос |
| --- | --- |
| «Сегодня» / «Завтра» или «Календарь» в выборе дня | Сегодня и завтра по серверному дню магазина → заменить дату и перечитать список. Календарь → открыть §3.4, затем применить выбранную дату. |
| Снять фильтр или «Сбросить фильтры» | Обновить ссылку и прочитать первую страницу. Сброс возвращает обычный список O2. |
| Нажать заказ или его действие | Открывается карточка O2 или выполняется существующее действие. Навигация не блокируется чтением этого списка, команда O2 блокирует повтор по её текущему правилу. |
| День пуст / фильтр пуст | «На этот день заказов нет» / «По этим фильтрам заказов нет». Можно выбрать день или сбросить фильтры. |
| Изменение ревизии при подгрузке | «Список изменился. Откройте первую страницу». Перечитать текущую выборку с первой страницы, сохранив дату и фильтр. |

### 3.3 «Список сборки»

Шаблон списка. `TopBar` «Список сборки» → дата и `ChipGroup` «Сегодня», «Завтра», «Календарь» → строки `ListItem` с названием, фасовкой и «<N> шт.». Строки только для чтения. «Сегодня» / «Завтра» меняют день и читают его агрегат. «Календарь» в этом пути выбирает день для сборки и возвращает в её список. Кнопки дня доступны при чтении, работающий запрос не подменяет данные нового дня. Пусто — «На этот день собирать нечего». При изменении состава или состояния заказа обновляется только показанный день.

### 3.4 «Календарь»

Шаблон списка с календарём из выбора даты. `TopBar` «Календарь» → название месяца и кнопки «Предыдущий месяц», «Следующий месяц» → дни с числом заказов. Подпись для дня — «<дата>, <N заказов>» с согласованным числительным. Дни без заказов остаются доступными. Пустой месяц — сетка с нулевыми днями. Нажатие месяца запрашивает новый месяц. Нажатие дня из основного пути открывает §3.2 и читает дневную выборку, из списка сборки — §3.3. Кнопки навигации остаются доступны при чтении. При изменении заказов числа обновляются, выбранный день сохраняется.

### 3.5 «Ещё → Уведомления»

Существующая таблица «Уведомления по ролям» в шаблоне списка блока 8. Сверху статус бота, затем роли «Владелец», «Управляющий», «Сборщик», «Бухгалтер», «Вручную» и столбцы «Новые заказы», «Оплаты и чеки», «Отмены», «Товар заканчивается». Внизу — «Сейчас получают: …» по темам, «никто» для пустого списка. Предложение для вида — перенос длинного заголовка столбца на две строки. В остальном используется существующий вид таблицы.

Галочка доступна при праве управления и наличии права на тему у роли. Нажатие сохраняет явное новое значение. Остальные галочки на время записи заблокированы как в блоке 8. При ошибке остаётся последнее подтверждённое значение, рядом сообщение и «Повторить». При изменении состава команды сервер возвращает актуальные доступность и имена. Отсутствие связи с ботом использует статус и переподключение блока 8.

### 3.7 Витрина вне часов работы

На главной витрины, перед содержимым каталога, действующий компонент статусного сообщения с текстом «Сейчас закрыто · примем заказ на <ближайшее время>». Для интервала подставляются день и время получения, для режима по дням — день. Плашка информационная, без кнопки. Покупатель добавляет товары и выбирает доступное время обычным путём B8. При загрузке или ошибке доступности время не подставляется из догадки. При потере сети действует общий статус витрины. При изменении расписания, наступлении нового дня или смене доступного интервала текст обновляется в успешном ответе. Если у выбранного способа время заняли, оформление пользуется существующим возвратом к выбору времени. Паузы и их видимость действуют по [блоку 7 §13](shop-settings.md#13-правки-андрея-после-второй-ревизии-холста-21112026). Неподдержанные варианты расписания и сочетаний с паузой — §10.

## 4. Серверные команды и правила

### 4.1 Сводка, списки и доступ

1. Проверить сессию, актуальное членство и права в выбранном магазине, затем дату и параметры выборки. Дневная сводка, календарь и чтение заказов используют право `orders`, агрегат сборки — также `assembly`. Денежные действия и видимость новых финансовых показателей проверяются отдельно по §10. Прямой запрос к выборке проверяет те же условия, что ссылка на неё.
2. Календарь использует дату получения заказа по поясу магазина. Дневной список и календарь используют одну выборку на дату. Одни и те же предикаты применяются к счётчику сводки и ссылке на «Заказы». Пагинация не влияет на счётчики и суммы. Определения «сегодня», готовой доставки и точный состав действий — §10.
3. Суммировать позиции выбранных заказов по товару и фасовке, сохраняя снимки строк. Одинаковые названия разных товаров не сливаются. Отбор заказов для сборки согласуется в §10. Просрочка основана на действующем правиле O2 для активного заказа с прошедшим временем получения. Открытые доплаты и суммы к возврату прошлых дней остаются доступны в существующих «Заказах» и карточках. «Долги клиентов» суммирует только открытый долг из блока 5, включая прошлые дни. [Блок 5 §4](seller-orders.md#4-серверные-правила)
4. Один запрос к данным сводки по `seller_order_index` возвращает все доступные показатели и ревизию. Неизменный рабочий день — до одного SQL на проверку актуальности в Shop DO, без чтения строк заказов и позиций. Для календаря и сборки — агрегаты, без N+1. Ключ выборки учитывает магазин, разрешённый объём данных и дату или месяц. При полуночи, смене пояса и наступлении границы просрочки версия заказа сама по себе недостаточна для ответа «без изменений». При живом обновлении используется действующий канал O2, без отдельного фонового опроса сводки. [PERFORMANCE §4 и §6](../PERFORMANCE.md#4-живые-обновления)

### 4.2 Расписание и оформление

1. Публичное чтение сначала применяет существующие условия публикации и доступа к предпросмотру. Для доступной витрины сервер берёт эффективные расписания способов, местную дату и часы магазина, выходные, подготовку и доступность интервалов. После закрытия ближайшее время должно соответствовать текущему допустимому выбору B8. Истечение интервала, изменения расписания и ёмкости делают прежнее значение неактуальным.
2. Ночь или выходной не запрещают оформить заказ на ближайшее доступное время. Оформление повторно проверяет доступность, паузу и ёмкость в существующей команде. При гонке за последнее место выигрывает существующее атомарное бронирование B8/B10. Повтор команды с тем же ключом сохраняет её действующую семантику. [D20](../DECISIONS.md), [получение B8](../tasks/B8.md), [настройки блока 7](shop-settings.md)

### 4.3 Темы и очередь Telegram

1. «Новые заказы» продолжают использовать существующую отправку O2. Для «Оплаты и чеки» обязателен перевод или загруженный чек, перешедший на проверку. Отмена ставится в очередь после подтверждённого перехода в `cancelled` независимо от того, кто отменил. Список остальных событий оплаты и замена чека — §10. Порог «Товар заканчивается» сверяется с фильтром каталога по каждой конечной фасовке. Предыдущее и новое количество берутся из одной операции изменения остатка. Повтор внутри диапазона не создаёт сообщение. Пополнение выше порога позволяет следующему снижению создать отдельное событие. Переход сразу в ноль и дополнительные источники изменений — §10.
2. Получатели продавца определяются в том же магазине по таблице блока 8. Перед каждой попыткой проверяются действующие членство, роль, галочка темы, право и связь с выбранным ботом. Права тем: `orders` для новых заказов и отмен, `payments` для оплат и чеков, `stock` для нового столбца. Для нового столбца по умолчанию включены владелец и управляющий. Состояния первых трёх столбцов берутся из действующих настроек, включая сохранённые галочки. Старые настройки без нового столбца получают его значение по умолчанию. Для ручной роли проверяется право каждого сотрудника. Для личного канала сотрудника действует выбор бота блока 8. [Блок 8 §11.3–§11.5](team-and-launch.md#11-ответы-андрея-на-10-21112026)
3. Триггеры покупателя: принятие → `accepted`; доставка → `handed`, самовывоз → `ready`; завершение → `completed`; отмена → `cancelled`. Готовность доставки к передаче и откат этапа не создают статусных уведомлений. Адресат — текущий обладатель заказа с подтверждённым Telegram-входом. Новые статусные уведомления предназначены для бота магазина. Денежные уведомления остаются на схеме блока 5, включая запасной канал. [Блок 5 §4.1 и §10.9](seller-orders.md#41-исполнение-и-резервы)
4. В той же транзакции, что изменение заказа, чека или остатка, фиксируется событие outbox. Состояние доставки учитывается по событию и получателю. Повтор команды, конкурирующие обработчики и повторное чтение события не создают второе задание на ту же доставку. Повтор отдельного фактического перехода после отката — §10. HTTP-вызов Telegram идёт после транзакции. Сбой отправки не откатывает заказ, оплату, отмену или остаток.
5. Shop DO ставит alarm при наличии работы. Для подтверждённой временной ошибки — ограниченные повторы с экспоненциальной задержкой, разбросом и `Retry-After`. Если Telegram мог принять запрос и результат неизвестен, фиксируется неопределённый исход без автоматического повторного вызова `sendMessage`. Постоянный отказ прекращает попытки. При отсутствии бота для конкретного канала недоставленное событие живёт до суток по O4. У пустой очереди нет alarm для уведомлений. В журнале — идентификатор события, тема, время и исход без текста, токена и содержимого чека. Уборка по [PERFORMANCE §5](../PERFORMANCE.md#5-фоновая-работа).

## 6. Инварианты

- **П1.** На одну ревизию, одинаковые параметры и одинаковые права число и сумма на «Главной» соответствуют полной выборке в «Заказах». [O3](../tasks/O3.md)
- **П2.** Пояс магазина определяет границы дня, просрочку, подписи и ближайшее время. Долг закрывается по правилам блока 5 и не исчезает при смене дня. [US-R09](../stories/seller-orders.md#us-r09--рабочий-день), [блок 5 §6](seller-orders.md#6-инварианты)
- **П3.** Доступ к личному событию и заказу повторно проверяется при отправке и при открытии соответственно. Очередь изолирована по магазинам. [Блок 8 §11](team-and-launch.md#11-ответы-андрея-на-10-21112026)
- **П4.** Зафиксированное бизнес-событие не зависит от результата Telegram. Один подтверждённый переход даёт не более одной отправки данного события каждому допустимому адресату. [O4](../tasks/O4.md)
- **П5.** Вне часов доступное время соответствует правилам оформления. Явная пауза управляется блоком 7 и сохраняет настройки своей видимости. [D20](../DECISIONS.md), [блок 7 §13](shop-settings.md#13-правки-андрея-после-второй-ревизии-холста-21112026)

## 11. Ответы Андрея на §10 (22.11.2026)

Этот раздел главнее §10 и карточек O3, O4. Каждый пункт с правилом — тест с номером; таблица приёмки §7 дополняется строками §11.

1. **§11.1 · «Сегодня».** Заказы с датой получения сегодня (по поясу магазина), как в календаре. Сумма — без отменённых. Заказ «время согласуем» без даты попадает в «Сегодня» в день оформления. **Список сборки** — ещё не собранные позиции неотменённых заказов на выбранный день.
2. **§11.2 · Доставка собрана и ждёт курьера** — в «Ждут выдачи», как в блоке 5.
3. **§11.3 · «Решить по оплате»** — заказы, где продавцу нужно действие с деньгами: выдача без оплаты, переплата к возврату, неполученная доплата. **Суммы («Сегодня … ₽», «Долги клиентов») видят только сотрудники с правом «Деньги»**; без права — только количество заказов, строка долгов скрыта. «Долги клиентов» ведёт на все заказы с долгом (активные и завершённые).
4. **§11.4 · «Оплаты и чеки»** — одно событие: каждый новый чек на проверке, включая повторный после «чек не подходит». Других триггеров нет.
5. **§11.5 · «Товар заканчивается».** При переходе остатка видимого товара в 1–5 шт. — «Заканчивается: <товар>, осталось N»; при падении до 0 — «Закончился: <товар>». Источник изменения любой (заказ, ручная правка, массовое действие). По скрытым товарам — нет. Одно сообщение на переход, повтор — только после подъёма выше порога.
6. **§11.6 · Вид сообщений.** Отдельное сообщение на каждый шаг (не редактирование одной карточки). После отката этапа и повторного перехода вперёд повторно не отправлять (ключ: заказ + событие).
7. **§11.7 · Нет бота магазина** — статусы покупателю шлёт бот Korzina, как денежные сообщения блока 5. Ничего не копить.
8. **§11.8 · Витрина: ближайшее время вместо «закрыто».** Слово «закрыто» на витрине не используется; заказ можно оформить всегда (кроме паузы блока 7). Вверху витрины всегда — и днём, и ночью — одна строка по способу: «Ближайшая доставка: сегодня с 14:00» / «завтра с 9:00»; «Самовывоз: завтра с 9:00»; режим «согласуем» — «Время доставки согласуем после заказа»; ближайшего времени нет в горизонте — «Время уточнит магазин после заказа». При паузе — плашка паузы блока 7 вместо строки для приостановленного способа; при тихой паузе строка приостановленного способа просто не показывается. Ближайшее время считается по расписанию, выходным, лимитам и «Сколько готовите» (блок 7 §14).
