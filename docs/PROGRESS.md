Цель: главная работает как сейчас, корзина — как после последнего релиза; любая будущая правка, которая это ломает, не проходит CI. Принципы: проверяем **поведение, а не вид** (снимков пикселей нет — TESTING §7); данные — демо-магазин `test2`, время заморожено; каждый тест назван по правилу или строке приёмки спецификации (`П2`, `§7.5`), чтобы его можно было удалить вместе с правилом; без повторов в цикле и без `retries`. Один PR «test: главная и корзина», Codex «Высокое». Источники: `docs/specs/catalog.md` §6–§7, `docs/specs/purchase.md` (корзина §3.1, §5–§7), `docs/PERFORMANCE.md` §6, `docs/TESTING.md`.

- [x] 1. **Сервер (Vitest, Workers pool)** — по одному тесту на правило, которого ещё нет: корзина — добавить SKU, увеличить и уменьшить, удалить, объединение одинакового SKU, предел по остатку, закончившаяся фасовка (уменьшение разрешено, увеличение — нет, §9.3), изменение одной фасовки не трогает другую (П2), пересчёт при смене цены и остатка с «было / стало» и «Принять изменения», минимальная сумма без доставки, конфликт ревизии, повтор с тем же ключом, слияние гостевой корзины после входа без дублей, чужой магазин и чужая сессия недоступны (П5, П1); главная и каталог — видимые разделы и их порядок, скрытые и пустые разделы не видны, фильтры и сортировка по всей серверной выборке (П3), поиск и подбор не меняют корзину (П4). **Бюджет SQL `cart/change` ≤4 запросов, 1 транзакция** (PERFORMANCE §6) — этот пункт закрывает часть техдолга №2.
- [x] 2. **Фиксирующий тест главной** (characterization): ответ главной и первой страницы каталога на демо-данных сводится к смысловой проекции — разделы и их порядок, число плиток, для каждой плитки `sku`, цена, наличие, число фасовок, бейджи — и сравнивается с сохранённым эталоном (`toMatchSnapshot` на проекцию, не на весь JSON и не на картинку). Намеренное изменение — обновление эталона одной командой, разница видна в PR.
- [x] 3. **Поведение экранов без браузера** (Vitest + `happy-dom` + `@testing-library/react`, dev-зависимости): поиск элементов по роли и доступному имени, не по классам; моки — через реальный слой `api.ts` с подменой `fetch` фикстурами из контрактов. Проверить: плавающая корзина видна на витрине и скрыта на корзине, оформлении, заказе и при открытой экранной клавиатуре; плитка с несколькими фасовками — метка «N фасовки ›» открывает шторку; в шторке «+» отключён у закончившейся фасовки, «−» работает; «Сбросить» сбрасывает фильтры и сохраняет сортировку; «Удалить → Вернуть» в корзине; кнопки количества и «Продолжить» блокируются на время пересчёта; «Загрузка…» до ответа корзины; «Показано N из M»; «Нет соединения · Повторить» сохраняет загруженное.
- [x] 4. **Сверка «сервер ↔ экран»**: в серверных тестах главной, каталога, поиска и корзины каждый ответ разбирается той же zod-схемой из `src/shared/contracts`, по которой его читает клиент (`schema.parse(body)`); фикстуры для п.3 строятся из тех же схем.
- [x] 5. **Браузер (Playwright)** — расширить `e2e/catalog.spec.ts` и добавить не больше двух сценариев (лимит TESTING §3 — 10 на продукт): (а) главная → категория → товар → фасовка → корзина → «+» / «−» → удалить → «Вернуть» → пустая корзина; (б) товар в корзине → цена и остаток меняются тестовой командой (только dev и превью) → открыть корзину → «было / стало» → «Принять изменения». В обоих — **счётчик запросов к API** при открытии главной и корзины (не больше эталона, без водопадов) и отсутствие `pageerror`.
