# Тесты: что проверять и сколько это стоит

Цель тестов — не пропустить ошибку в деньгах, правах, заказах и изоляции магазинов. Не цель — покрыть каждую строку. Каждый тест должен защищать правило, которое можно сломать и не заметить.

## Как выбрать раздел

Для кода — §1 и §2. Новое правило/тест или регрессия — §8; бюджет/замедление — §3; нестабильность/удаление — §4; физическая проверка — §5 и §8; выпуск — §6; видимые изменения — §7. Docs-only: проверить diff, ссылки и сохранность требований без runtime. Разделы вне маршрута читать по конкретной зависимости.

## 1. Уровни проверки — по размеру изменения

| Изменение | Что запускать | Браузер |
|---|---|---|
| Текст, цвет, отступ, токен, иконка | `npm run check:fast` (типы + Biome + `check:arch`) | Взгляд на один экран |
| Экран или компонент без новой логики | `check:fast` + `npm run test:related` | Путь экрана на 390 px |
| Логика фичи, API, схема БД | `test:related` во время работы, полный `check` — в CI на PR | Путь фичи |
| Деньги, заказ, права, изоляция, общие модули (`server/platform`, `shared/money`, сессии, `src/ui`, шаблоны) | полный `check` в CI на PR + e2e затронутых сквозных маршрутов (метка `e2e`) | Путь обеих ролей |
| Перед запуском (L1) и раз в неделю | `npm run check` + все e2e | Сквозные маршруты |

- `test:related` сравнивает рабочее дерево с общей базой `HEAD` и `origin/main` (обновить через `git fetch origin main`; другой ref — `TEST_BASE_REF`). Учитывает коммиты ветки, staged/unstaged и новые файлы; имена передаются без shell-подстановки. При изменении зависимостей, конфигурации сборки/тестов или удалении исходника запускает все тесты.
- Для `server/**` и `src/shared/**` дополнительно запускает все API-тесты: вызов `cloudflare:workers` не виден в обычном графе импортов Vitest. Для остальных изменений — `vitest related --run`. Документы без исходников тесты не запускают.
- `check:fast` генерирует типы Cloudflare, проверяет TypeScript, Biome и архитектуру. `check` добавляет Knip, Vitest и сборки prod/demo с проверкой размера. Изоляция отключена только для Node unit-тестов; API-тесты сохраняют отдельные runtime и хранилища.
- `Check` сначала запускает `python3 scripts/test_check_docs.py` и `python3 scripts/check-docs.py --base <base SHA>`: новые ошибки внутренних Markdown-ссылок/якорей в изменённых документах и входящих ссылках, flat YAML name/description навыка. Старые неизменённые ошибки отмечаются отдельно; внешние URL не запрашиваются. Рост стартового текста — предупреждение, не повод удалить требования. Docs-only: AGENTS.md, документальные расширения docs и точный SKILL.md; scripts, workflows и openai.yaml требуют полного Check. Остальные PR проходят `npm run check` в CI (~1,5 мин) и браузерный smoke. Локально запускаем `check:fast` и `test:related`. Полный локальный `check` нужен, если CI недоступен.
- После вливания runtime-изменений Codex подтверждает выпуск и предусмотренный Demo smoke до передачи по [полному циклу](WORKFLOW.md#полный-технический-цикл-до-demo); в ожидании продолжает разрешённую независимую работу. Docs-only — без runtime.
- Упал тест → после исправления перезапустить упавший файл локально; финальный полный `check` — в CI на актуальном SHA. Локальный полный прогон — только если CI недоступен.

## 2. Какие тесты писать

**Обязательно:**
- по одному тесту на каждый критерий приёмки истории, который проверяется кодом (не «на каждую функцию»);
- деньги: суммы, округления, распределение скидки, возвраты — с конкретными числами из `DOMAIN.md`;
- права и изоляция: чужой магазин, чужой покупатель, сотрудник без права, отозванный доступ;
- команды: повтор с тем же ключом, конфликт версии, гонка за последний товар или слот;
- бюджет SQL — только для горячих путей из `PERFORMANCE.md` §6;
- поведение главной и корзины — Vitest с DOM из шага 3 раздела «Тесты главной и корзины» в [PROGRESS](progress/archive/ctx-1/catalog-cart-tests.md#тесты-главной-и-корзины-решение-андрея-19112026--после-переработки-каталога-до-техдолга). Эталон главной обновляется только при намеренном изменении, командой `npx vitest run server/modules/catalog/home.test.ts --update`.

**Не писать:**
- тесты внешнего вида (снимки экранов, сравнение с Figma, проверка классов и цветов). Явно согласованные пропорции фото и плиток F11 проверяются геометрией в существующих сценариях Playwright;
- тесты текстов интерфейса;
- тесты, повторяющие типы TypeScript или zod-схему («поле строка»);
- тесты библиотек (Hono, Drizzle, TanStack, React);
- тесты сгенерированного кода MagicPath до его подключения;
- несколько тестов на одно правило с разными, но равноценными данными.

## 3. Бюджет времени

- `npm run check` — не дольше **90 с** на машине Codex. `check:fast` — не дольше 20 с.
- Один тест — не дольше 1 с; медленный тест ускорить (общая фикстура, меньше данных) или объединить с соседним.
- Превысили бюджет → сравнить с базой и найти самые медленные файлы. Ухудшение от текущей правки устранить в задаче; известное прежнее превышение вести одной отдельной задачей с владельцем, не расследовать заново в каждом PR. Без сравнения не объявлять превышение старым. Обязательные проверки не обходить; тесты ради бюджета не удалять без замены.
- e2e (Playwright) — не больше 10 сценариев на весь продукт (сквозные маршруты из `design-system/navigation.md`), не в каждой задаче.
- **Ночной набор «Регрессии»** (решение Андрея 24.11.2026, [QA1](tasks/QA1.md)) — отдельно от этих 10 и без лимита сценариев: короткие проверки «как должно быть» по принятым блокам. Гоняется каждую ночь на demo в магазине `e2e` (не `test2`) и вручную перед «Одобряю блок N». В проверку PR не входит и её время не увеличивает. Падение ночного прогона — ошибка, разбирается первой задачей утром.

## 4. Нестабильные и устаревшие тесты

- Нестабильный тест (то проходит, то нет) не повторяем в цикле и не пропускаем: чиним в той же задаче (обычно время, порядок или общий стейт) или заменяем надёжным.
- Если функцию удалили решением Андрея — её тесты удаляются вместе с ней в том же коммите.
- Тест, который проверяет то же, что другой, — объединить при аудите (раз в 10 задач, `NEW_FEATURE.md`).
- Без решения Андрея нельзя ослаблять тест правила денег, прав и заказа.

## 5. Проверка на demo

Первичная физическая приёмка блока — полный чек-лист. Перепроверка исправления — дефект и непосредственно затронутые зависимости; открытый остаток сохраняется отдельно, не запускается автоматически. Среды выбираются по дефекту и изменённым интеграциям: для D2 нужны Safari и Telegram. Проверка исправления не закрывает приёмку блока.

- Подробная проверка (все состояния, переходы, ошибки) — **локально** в `npm run dev` до вливания.
- После вливания на demo — короткая проверка: сборка Workers Builds успешна, затронутый экран открывается, основное действие работает. 2–3 минуты, не повторять локальную проверку целиком.
- Ожидание сборки не простаивать: пока идёт сборка, пиши отчёт задачи.

## 6. Выпуск

- Workers Builds на `main` только собирает и публикует (`build` + `deploy`), тесты не гоняет повторно — они уже прошли перед вливанием.
- Для PR, требующих полного Check, GitHub Actions (F10) запускает `npm run check` на актуальном SHA ветки задачи; новые коммиты после Ready проверяются снова. Основной smoke выполняется на превью, расширенные сценарии главной и корзины запускаются отдельно.
- `Check` запускается на открытие/обновление PR из `task/*` в `main` (без дублирования на push). `E2E` запускает сценарии главной и корзины на PR с изменениями в их путях. Полный набор запускается вручную и ежедневно в 06:00 МСК. Сценарий изменения цены и остатка использует локальный тестовый Worker. Smoke открывает локальную витрину на 390 px, сверяет bootstrap с API своего магазина и проходит товар → шторку → назад; отчёт при ошибке хранится 7 дней. **Разные экраны (дёшево):** в том же smoke главная и затронутый экран открываются ещё на 360 и 412 px и проверяются одним скриптом в браузере — нет горизонтальной прокрутки страницы и ни один текст не вылезает за свой блок (`scrollWidth > clientWidth`). Без снимков и без отдельных прототипов в MagicPath (холст — только 390 px).
- `check:build` сначала проверяет prod, затем demo; последним остаётся готовый к публикации demo-артефакт. Отчёт Vite находится в `.cloudflare/output/v1/workers/default/assets/bundle-report.json`. Первый экран включает entry, статические зависимости, таблицу demo-маршрутов и главную; бюджет — PERFORMANCE.md §7: цель 135 КБ gzip, 135–160 — предупреждение и строка в отчёте, > 160 — падение; любой другой JS-чанк — 60 КБ. Первый экран — настоящая главная (B2).
- Превью веток используют только D1/R2 `korzina-preview-*`, их миграции применяются только туда; удалённые D1/R2 demo изменяет только `main`.

## 7. Ворота перед вливанием (решение Андрея, 18.11.2026)

Ловим поломки **до** `main`, а не на demo. Схема: быстрые тесты правил (много) → один сквозной smoke в браузере с проверкой содержимого (мало) → снимки для взгляда человека. Сравнение снимков по пикселям не делаем.

1. **Smoke на превью PR, до вливания.** При полном Check CI ждёт превью ветки и прогоняет браузерный smoke по его адресу на 390, 360 и 412 px. Красный smoke — PR не вливается. После вливания smoke повторяется на demo.
2. **Smoke проверяет содержимое, а не только «не пусто»:**
   - главная: есть хотя бы одна категория; есть плитки товаров с ценой; **каждое `<img>` первого экрана загрузилось** (`complete && naturalWidth > 0`);
   - карточка товара: есть фото (загружено), название, цена, кнопка «+»; **кнопку ничто не перекрывает** (`document.elementFromPoint` в центре кнопки возвращает саму кнопку или её потомка);
   - нет `pageerror` и ответов API 4xx/5xx, кроме ожидаемых.
3. **Снимки.** Smoke сохраняет снимки главной и карточки товара (390 px) как артефакт CI (бесплатно, 7 дней). Если PR меняет видимое покупателю (`src/ui`, `src/app/templates`, `src/features/*/ui`, стили, форма данных каталога или фото) — Codex вставляет ссылку на снимки в описание PR и отчёт задачи, **включая «чистки» и рефакторинг**. Андрей смотрит снимки; замечание — правка до вливания.
4. **Стоимость:** +20–40 с к `Check`; GitHub Actions в бесплатном лимите. Новые проверки — внутри существующего smoke, а не отдельными тестами.


## 8. Тесты на каждом этапе блока (решение Андрея 20.11.2026)

Цель — закрепить основную логику, не раздувая набор и не замедляя CI.

- **Каждое реализуемое кодом правило решения Андрея — свой тест** (TESTING §2, §8). Каждый такой пункт §9+ спецификации и строка `DECISIONS.md` получают хотя бы один тест правила с номером решения в названии (`«§9.3 объединение переносит заказы, адреса и избранное»`). В отчёте задачи — таблица «решение → тест». Правило без теста — задача не готова. Визуальное или процедурное решение получает строку «не автотест → снимки/сценарий/проверка документа» в таблице покрытия; визуальное доказательство не заменяет тест денег, прав или поведения.
- **Новое подключай к старому.** Добавляешь данные покупателя или магазина (новую таблицу, поле, список) — найди все места, которые переносят, сливают, копируют или удаляют такие данные (слияние профилей и гостя, выход, уборка, удаление магазина), и включи новое туда. Каждое такое место — тест «после операции новые данные на месте».

| Этап блока | Что делаем с тестами |
|---|---|
| Спецификация | Раздел «Проверки» перечисляет тесты правил блока: по одному на каждое реализуемое кодом правило решения §9+, права и изоляцию, деньги, повторы и гонки, бюджет SQL горячих путей. Без него спецификация не готова. |
| Сервер | Тесты правил — в том же PR, что и код. В отчёте — таблица «решение → тест» (правило покрытия выше); визуальные/процедурные решения отмечаются отдельным доказательством и не подменяют автотест поведения. Данные — через общие фабрики `server/testing/*`, не копированием. |
| Экраны | Тестов внешнего вида нет. Поведение экранов закрепляет один сквозной сценарий блока (ниже). |
| Сквозной сценарий | Каждый блок добавляет или расширяет **ровно один** e2e своего главного пути. Блок 5: покупатель оформил → продавец получил и принял → собрал → выдал с оплатой (и в долг) → покупатель видит «Выдан» / «Доплатите». Всего на продукт ≤ 10 сценариев: если новый выходит за лимит — объедините с ближайшим. |
| Локальная проверка | Каждая ❌, которую можно проверить кодом, становится регрессионным тестом: сначала падает на старом коде, потом проходит. Внешний вид и Telegram-клиент — нет. **Плюс шаг в ночном наборе «Регрессии»**, если ❌ видна в браузере. Так же — каждая находка Андрея на demo и каждый пункт BACKLOG при выполнении. |

**Переходы из §7 спецификации.** До demo облачный Codex воспроизводит исходное состояние и действие, проверяет видимый результат и следующее доступное действие через интерфейс. Для исправляемого дефекта сохраняет воспроизводимую автоматическую проверку и фиксирует её результат до и после правки. Если дефект проявляется только в конкретном клиенте, указывает границу автоматической проверки и передаёт точные шаги для этого клиента прямо локальному Codex после проверенного выпуска; новый продуктовый вопрос возвращает в Work. На demo локальный Codex начинает с короткого прогона в указанной среде. При повторении дефекта фиксирует сборку, среду и шаг, сразу передаёт результат и продолжает независимые сценарии. Объём остальных проверок определяется по §1.

**Скорость (держать, а не догонять):**
- `npm run check` ≤ 90 с, e2e в CI ≤ 2 мин, один тест ≤ 1 с. На 20.11.2026 `check` ≈ 99 с, e2e ≈ 83 с — первой задачей блока 5 вернуть `check` в 90 с (медленные файлы: `vitest --reporter=verbose`, общая фикстура, меньше данных).
- В отчёте каждой задачи — время `check` и три самых медленных файла тестов, если `check` > 80 с.
- Новый тест сначала ищет место в существующем файле того же правила; новый файл — только для нового правила.
- Раз в блок (при приёмке) — дубли тестов объединить, тесты удалённых функций удалить.
