# План разработки

Цель — запустить параллельный магазин Korzina с собственной витриной, кабинетом продавца, серверной логикой, Mini App и ботом. Продолжаем с витрины. Каждую часть можно принять и проверить отдельно.

| Этап | Что делаем | Что считаем результатом |
|---|---|---|
| 0. Старт | Отдельный репозиторий, инструкции, источники, правила именования и принятый тест карточки. | Новый чат продолжает из репозитория. Карточка запускается локально. |
| 1. Витрина | Общая оболочка и айдентика, главная и каталог, категории, поиск, карточки, избранное и корзина. По мере реализации собираем связанный путь по макетам покупателя начиная с блока 30. | Покупатель открывает товар, меняет количество и возвращается в исходный список. Корзина доступна с витрины. |
| 2. Вертикальный сценарий | Реальные данные каталога и остатков, создание тестового заказа, кабинет со списком и карточкой заказа, подтверждение статуса продавцом. | Заказ проходит через API и отдельную базу Korzina, покупатель и продавец видят согласованный статус. |
| 3. Кабинет продавца | Развиваем сценарии из FigJam и связанных макетов. Добавляем управление товарами, фасовками, остатками, ценами, публикацией и заказами по подтверждённым правилам. | Продавец меняет свои данные, и результат отражается в витрине. Доступ проверяется на сервере. |
| 4. Telegram и Cloudflare | Развёртываем тестовое окружение Cloudflare. Проверяем витрину на HTTPS, подключаем отдельного тестового бота, вход Mini App и уведомление о смене статуса. | Тестовый заказ, изменение статуса и сообщение в Telegram работают в одной цепочке. |
| 5. Полнота и запуск | Закрываем остальные блоки и состояния из реестра, проверяем оба интерфейса и устройства. Подключаем собственный домен и рабочее окружение Korzina по готовности. | Веб и Mini App используют один API, данные и бот раздельны между окружениями. Рабочие сценарии проверены. |

Нумерация этапов задаёт приоритет. Контракты API, модель заказа и тестирование открытия Mini App можно начинать параллельно с интерфейсом, когда они уменьшают риск переделки. Полную серверную реализацию не откладываем до конца всей витрины.

Перед первой интеграцией API для чтения каталога и товара проверь, какие модули Lavka подходят для Korzina. Повторяй оценку перед реализацией каждого следующего серверного модуля. Переноси совместимый код, адаптируй полезную логику или пиши модуль с нуля, если подходящего аналога нет или самостоятельная реализация проще. Записывай исходник, решение и причину по [критериям архитектуры](architecture.md#переиспользование-серверного-кода-lavka). API и инфраструктура остаются собственными ресурсами Korzina.

## Следующий блок

Окружение `demo.korzina.app` опубликовано через Workers Builds на отдельном `korzina-demo`; сертификат активен, GitHub `main` подключён, previews отключены. Завершить проверку автоматической публикации push этой записи без `--force`, затем проверить HTTPS, изображения, карточку и корзину на домене. Сетевой доступ из текущего Cloud-окружения к demo пока блокируется; ограничение не означает ошибку сайта. Инфраструктуру и ресурсы Lavka не использовать. Подробности и идентификаторы — в прогрессе.

Сверить принятую главную в проекте MagicPath с актуальными макетами покупателя, включая инструкции к витрине и товарным плиткам. Выбрать наименьший рабочий маршрут «главная или каталог → карточка → назад → корзина». Начать с общей оболочки, перенести нужные элементы из MagicPath и подключить принятую тестовую карточку. Присвоить номера блоков по Figma после проверки, без выдуманных номеров. Зафиксировать отсутствующие состояния и контракт первого чтения каталога.

## Учёт прогресса

Единица учёта — пронумерованный блок Figma, а внутри него проверяемые сценарии. Для каждого блока записываем ссылку, область, этап и принятые состояния. Статусы: в очереди, в работе, прототип принят, интегрирован, проверен. Частичный тест остаётся частью блока. Знаменатель для доли готового определяем после сверки реестра макетов, раздельно для покупателя, продавца и Telegram. Технические работы отслеживаем рядом с экраном, который ими пользуется.

Первый замер относится к ограниченному участку блока 47. Для оценки следующих сроков учитываем число связанных состояний, роли и интеграции, а не только число экранов. [Результат теста](progress.md).
