# Экономия запросов и нагрузки

Цель: каждый экран получает ровно те данные, которые показывает, а база и Worker не делают пустой или повторной работы. Правила проверены на Lavka (замеры в production: пустые чтения 61 → 4 строки, неизменившийся список заказов — без выборки записей, публичные фото — без SQL), с поправкой на нашу архитектуру (база магазина — SQLite в Durable Object).

Экономия принимается только вместе с сохранением актуальности данных и скорости. Сокращение запросов ради цифры, ценой устаревших остатков, статусов или прав, — ошибка.

## 1. База данных

1. **Каждый частый запрос — по индексу.** Для запросов списков и поиска в тесте проверяется план (`EXPLAIN QUERY PLAN`): нет `SCAN` по большим таблицам (товары, заказы, события, сообщения). Индекс добавляем под конкретный запрос, а не «на всякий случай»: каждый индекс удорожает запись.
2. **Выбираем только нужные столбцы.** Никаких `SELECT *` в обработчиках. Список отдаёт компактную форму (плитка: id, название, фасовка, цена, старая цена, признак наличия, одно фото), карточка — полную.
3. **Нет N+1.** Связанные данные — одним запросом по списку ID (`IN (SELECT value FROM json_each(?))`) или JOIN. Сопоставление в коде — через `Map`, не `find` в цикле.
4. **Списки — страницами** по курсору (`after=<id|время>`), до 50 записей. Полную историю за всё время не читаем никогда. **Итоги по всему списку** (какие категории и бренды непустые, счётчики, «есть ли ещё») **считает сервер**, а не экран по загруженной странице; данные следующей страницы не перезапрашивают предыдущие.
5. **Счётчики и сводки храним, а не считаем каждый раз.** Непрочитанные, «требуют действия», индекс заказов продавца обновляются в той же транзакции, что и изменение. Отчёты за период — по проекциям/агрегатам, сверяемым с исходными записями.
6. **Пустая работа не выполняется.** Изменение, которое ничего не меняет, не пишет (`UPDATE … WHERE` с проверкой отличия). Одна проверка «есть ли что делать» вместо нескольких пустых выборок.
7. **Ревизии вместо повторной выдачи.** У изменчивых коллекций (заказы покупателя, заказы продавца, корзина, чаты) есть ревизия, которая растёт в транзакции изменения. Клиент передаёт известную ревизию (`If-None-Match` / `?rev=`); если не изменилось — `304` или `{unchanged:true, rev}` без чтения записей.

## 2. Каталог и публичные данные

8. **Каталог разделён на две части.**
   - *Публичный документ* (названия, описания, фото, категории, бренды, фасовки, оформление магазина) — версия `catalogVersion`, меняется при правке публичных данных, смене настройки скрытия или переходе видимого опубликованного товара между доступным и распроданным. Изменение цены или количества при неизменном статусе наличия публичную версию не меняет. Отдаётся Worker из кеша (Cache API, ключ `shopId + catalogVersion`), с `ETag`; при совпадении версии Durable Object магазина не вызывается.
   - *Оперативные данные* (цены, остатки, доступность, ближайшее время получения) — маленький отдельный ответ без кеша на сервере, короткий `staleTime` на клиенте.
   Так остаток никогда не берётся из устаревшего кеша, а тяжёлое описание не перечитывается.
9. **Публичные файлы — без Worker и без базы.** Статика приложения (JS, CSS, шрифты) — напрямую из Static Assets. Публичные фото — постоянная ссылка с версией в имени, `Cache-Control: public, max-age=31536000, immutable`, ресайз Cloudflare Images. Приватные файлы — только через API с проверкой прав.
10. **Персональное (корзина, заказы, профиль, адреса, права) в общий кеш не попадает никогда.** Ключи кеша не содержат cookie/токенов и разделены по магазину.

## 3. Клиент

11. **Одинаковые одновременные запросы объединяются** (TanStack Query делает это по ключу). Нельзя сбрасывать весь кеш после любого POST — только зависимые ключи.
12. **После изменения используем ответ сервера, а не перечитываем всё.** Команда возвращает изменённую сущность (корзину, заказ); клиент кладёт её в кеш (`setQueryData`) и инвалидирует только реально зависимое (например, остатки после оформления).
13. **`staleTime` по типу данных** (`src/app/query-defaults.ts`): публичный каталог — 5 мин; оперативные цены/остатки — 30 с; корзина, заказы, чат — по сигналам live, иначе 30 с; справочники (страны, валюты) — сутки. `refetchOnWindowFocus` только для заказов и чата.
14. **Грузим только видимое.** Код разделён по маршрутам (витрина и кабинет — разные чанки); фото ниже экрана — лениво; карта (Leaflet), редакторы, графики — при первом открытии; Telegram SDK — только внутри Mini App; шрифт локальный, `font-display: swap`.
15. **Предзагрузка — только лёгкого и вероятного:** публичные данные товара при появлении плитки в зоне видимости/наведении; QR оплаты — при открытии экрана оплаты. Никакой предзагрузки персональных данных «про запас».
16. **Скрытая вкладка и свернутый Mini App ничего не опрашивают.** При возвращении — одна сверка.

## 4. Живые обновления

17. **Сигналы, а не опрос.** Shop Durable Object держит WebSocket с hibernation (простаивающее соединение не стоит вычислений). В сообщении — только «что изменилось» (тема и ID); клиент перечитывает именно это. Курсор событий позволяет восстановить пропущенное после переподключения.
18. **Одно соединение на аккаунт** для всех вкладок (Web Locks + BroadcastChannel). Резервный опрос (заказы — 30 с, непрочитанные — 60 с) — только когда соединение недоступно.
19. **Переподключение и повторы — с экспоненциальной задержкой и случайным разбросом**, с учётом `Retry-After`. Первая попытка действия пользователя не задерживается.

## 5. Фоновая работа

20. **Никаких расписаний «на каждый магазин».** Отправка уведомлений (outbox), истечение резервов, напоминания — через alarm Durable Object, который ставится только когда работа появилась, и снимается, когда очередь пуста. Простаивающий магазин не стоит ничего.
21. **Запуск обработки — только если запрос действительно создал работу** (признак в контексте команды), а не после каждого POST.
22. **Аналитика витрины — пакетами** до 20 событий, с дедупликацией в пределах визита, через `sendBeacon`; «присутствие» и «визит» — один общий запрос раз в 45 с, не два.
23. **Уборка (истёкшие сессии, temp-файлы, старые события) — редко** (раз в 15 мин — сутки) и ограниченными порциями. **Каждая новая таблица, куда пишется строка на посетителя, команду или событие** (сессии, ключи повтора, корзины, события, черновики), в той же задаче получает правило уборки и тест на него. Таблица без уборки — только справочные данные магазина (товары, категории, настройки).

## 6. Измерение и бюджеты

24. **Каждый запрос к API пишет метрику** (выборочно, без персональных данных): маршрут, магазин, число SQL, строк прочитано/записано, время БД и обработчика. Модуль — `server/metrics.ts` (F3), счётчик SQL — обёртка над доступом к базе в DO.
25. **Бюджеты горячих путей проверяются тестами** (`*.budget.test.ts`): тест падает, если число SQL или прочитанных строк выросло выше бюджета.

На demo и превью Workers Logs сохраняет `console.*` без дополнительной выборки, включая ошибки `console.error` и метрики API, которые приложение пишет для 1 % запросов. Автоматические invocation logs выключены для экономии объёма: иначе Cloudflare записывает событие на каждый вызов Worker. Трассировки собираются для 1 % запросов. Настройки prod определяются отдельно в L2.

| Сценарий | Бюджет |
|---|---|
| Публичный каталог при совпадении версии | 0 вызовов DO (ответ из кеша / 304) |
| Объединённая страница категории, документ той же версии в кеше Worker | 1 вызов Shop DO за offers, ≤2 SQL; 0 чтений products/categories/brands/media/product_photos |
| Оперативные данные каталога (страница товаров) | ≤ 2 SQL; строк прочитано ≤ 2 × строк в ответе |
| Карточка товара | ≤ 3 SQL |
| Изменение корзины | ≤ 4 SQL, 1 транзакция. Для добавления одной позиции в пустую корзину ≤ 6 прочитанных и 6 записанных строк |
| Оформление заказа | ≤ 15 SQL, 1 транзакция, внешних вызовов — 0 (уведомления через outbox). Для заказа с одной позицией и чеком ≤ 32 прочитанных и 19 записанных строк, включая строку ревизии заказов и её индекс |
| Виджет активных заказов без изменений (`rev` совпал) | ≤ 1 SQL на сессию и её ревизию заказов, 0 прочитанных строк из `orders` |
| Карточка заказа покупателя | ≤ 3 SQL |
| Идентификаторы избранного для плиток | ≤ 1 SQL |
| Карточка заказа продавца | ≤ 4 SQL |
| Уборка магазина | ≤ 7 SQL за аларм. Если остались просроченные записи, продолжение через 1 с |
| Простаивающий магазин | 0 запросов и 0 SQL в фоне |

Бюджет меняется только с обоснованием в коммите. Перед запуском (L1) — отчёт по реальной нагрузке на demo: запросы, CPU, SQL и строки на каждый сценарий.

## 7. Вес JS (решение Андрея, 17.11.2026)

Цель для пользователя — главная видна за ≤ 2 с на 4G (ARCHITECTURE §9); вес JS — ранний сигнал, его проверяет `check:build` на каждом PR. Для сравнения (2024): медиана JS мобильной страницы — 558 КБ, магазина на Shopify — 800 КБ, ориентир для небольших магазинов — 200 КБ.

| Порог | Первый экран витрины (gzip) | Что делать |
|---|---|---|
| Цель | ≤ 135 КБ | ничего |
| Жёлтая зона | 135–160 КБ | проверка проходит с предупреждением; в отчёте задачи — что выросло (топ модулей было → стало), зачем и что можно вынести |
| Потолок | > 160 КБ | проверка падает; поднять — только решением Андрея |
| Любой другой чанк | ≤ 60 КБ | проверка падает выше |

- **Повышение потолка — как платный сервис (COSTS.md):** запись в `DECISIONS.md`: что выросло, зачем (какая история), какие альтернативы проверены (ленивая загрузка, лёгкая библиотека, отказ), время открытия главной на 4G до/после. Число меняется только в одном месте — конфиге бюджета — после «да» Андрея.
- **Храповик:** на аудите раз в 10 задач цель опускается до текущего веса + 10 КБ (не выше 135), сэкономленное закрепляется.
- **Чем экономить (по порядку):** всё, что не нужно на первом экране, — ленивыми чанками; без тяжёлых библиотек ради одной функции, иконки поштучно; шрифт — только кириллица+латиница и нужные начертания; Preact вместо React — только через решение Андрея.
