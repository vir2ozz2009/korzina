# Архитектура Korzina

Один репозиторий с витриной, кабинетом продавца и серверными модулями. Витрина в браузере и внутри Telegram использует один интерфейс с адаптером окружения. Кабинет, Mini App и бот обращаются к общим правилам каталога и заказа через сервер Korzina.

| Часть | Предлагаемый маршрут | Где развивать код |
|---|---|---|
| Главная, категории, поиск | `/`, `/catalog`, `/catalog/:category`, `/search` | `src/features/storefront/` |
| Товар, избранное и корзина | `/product/:slug`, `/favorites`, `/cart` | `src/features/product-card/`, `src/features/cart/` |
| Оформление и заказы покупателя | `/checkout`, `/orders/:id` | `src/features/orders/` |
| Кабинет продавца | `/seller`, `/seller/products`, `/seller/orders/:id` | `src/features/seller/` |
| Telegram Mini App | `/mini-app` либо маршрут витрины с Telegram-контекстом | `src/platform/telegram/` |
| API и webhook Telegram | `/api/v1/*`, `/api/telegram/webhook` | `server/` |
| Общие элементы и схемы | Используются в соответствующих разделах | `src/shared/`, `contracts/` |

Маршруты в таблице — цель. В стартовом прототипе карточка открывается на `/`, остальные тестовые виды переключаются внутри неё. Папки добавляем по мере реализации. Один домен может обслуживать все экраны по путям. Для тестового окружения выделяем свой адрес. Конкретные DNS-имена фиксируем при подключении купленного домена.

## Данные и backend

Модель растёт вокруг товара и фасовки (SKU), цены, остатка, продавца, корзины, заказа и истории его статусов. В первой интеграции фиксируем небольшой типизированный контракт чтения каталога и товара. Фронтенд переходит с демонстрационного источника на собственный API. Для корзины и оформления сервер повторно сверяет цену, количество и наличие. Повтор запроса на оформление не должен создавать дубль.

Покупатель, продавец и бот читают один статус из записи заказа. Переход меняется на сервере с проверкой роли и принадлежности заказа. Для каждого перехода фиксируем автора и время. Уведомление бота следует за подтверждённым изменением. Повторная доставка события или webhook не должна повторять действие. Названия статусов и разрешённые переходы утверждаем по Figma и FigJam перед реализацией. Когда сценарий затрагивает разные роли, добавляем конкретные проверки прав, смены статуса и обработки ошибок.

## Cloudflare и Telegram

Окружение для текущей разработки: `demo.korzina.app`, отдельный Worker `korzina-demo`, конфигурация `cloudflare.config.ts`. Источник автопубликаций — ветка `main` независимого репозитория Korzina через Workers Builds (подключение ещё требуется подтвердить успешной сборкой). Основной домен `korzina.app` и сервисы Lavka в это окружение не входят. По мере подключения backend база, файлы и бот должны быть собственными ресурсами Korzina. Demo — первое окружение развиваемой платформы, а не отдельная ветка одноразового кода.

Первый вариант для проверки — Cloudflare Workers со Static Assets для фронтенда и серверными маршрутами. Хранилище выбираем, когда определятся требования к транзакциям заказа и остатков. D1 — кандидат для небольшого реляционного каталога и заказов, R2 — кандидат для загружаемых изображений. Настраиваем отдельные тестовые и рабочие ресурсы Korzina и проверяем переходы по прямым ссылкам и HTTPS перед подключением домена. [Документация Cloudflare](https://developers.cloudflare.com/workers/static-assets/).

Mini App открывает по HTTPS тот же магазин. Telegram-адаптер отвечает за область экрана, кнопку «Назад» и контекст открытия. Сервер проверяет подпись и свежесть `initData` перед выдачей сессии и выполняет проверки прав сам. Для бота используются отдельный токен Korzina и серверный webhook с проверкой происхождения запросов. Уведомления используют подтверждённые события заказа. Токены, ключи и данные реальных покупателей храним вне репозитория и прототипа. [Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app) · [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).
