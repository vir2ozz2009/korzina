# Korzina — правила для агента

Korzina — платформа для продавцов еды, которые продают через Telegram. Одна кодовая база обслуживает сотни магазинов: витрину `<slug>.korzina.app`, Telegram Mini App, кабинет продавца и бота. Пишем с нуля. Lavka — только источник продуктовых правил, её код не копируем.

## Как начинать любой чат

1. **Сначала `git fetch` и `git pull` в `main`. Если `pull` не проходит — почини (таймаут, `git remote -v`, переклонировать) и только потом работай; ни холст, ни код не собираются из устаревшей копии или «через просмотр GitHub».** — локальная копия часто отстаёт от GitHub (другие чаты и Андрей пушат правила и закрытие задач). Затем `git status`, ветка и HEAD. Чужие незакоммиченные изменения не трогай. Статусы задач берёшь только из актуального `main`; старое содержимое `PROGRESS.md` поверх нового не записываешь.
2. Прочитай `docs/PROGRESS.md`: в нём текущая задача и следующий шаг.
3. Открой карточку задачи `docs/tasks/<ID>.md` (индекс и блоки — `docs/PLAN.md`, целиком его не читай) и её истории в `docs/stories/README.md` (колонка «Задача»). Открой **только** файл раздела этих историй — в нём критерии приёмки. Читай только документы и разделы, которые называет карточка; не открывай весь `docs/` и `reference/` «для контекста». Делай ровно то, что в карточке во «Входит» и «Нажимается»; всё из «Не входит» — не показывать. Если пункт можно понять двояко — спроси Андрея, не додумывай.
4. **Короткие команды Андрея** — подробности всегда в репозитории, не в сообщении:
   - «Продолжай» (или «Продолжай блок N», «Дальше») — выполнить «Шаги блока» в `PROGRESS.md` с первого не отмеченного до ближайшего **СТОП**;
   - «Одобряю» — одобрение того, что показано последним (холст или снимки); после него — следующие шаги до СТОП;
   - «Правки: …» — исправить сказанное в той же ревизии или PR, показать снова, остальное не трогать;
   - «Статус» — коротко: какой шаг сделан, какой идёт, что ждёт Андрея.

   Шаги блока готовим в Work перед блоком. Если шагов нет или шаг можно понять двояко — спроси Андрея, не додумывай.

### Work и Codex (решение Андрея 25.11.2026)

Подготовку ведём с Андреем в Work (ChatGPT с мышлением Astra): изучаем аналоги, обсуждаем варианты, принимаем продуктовые решения и фиксируем их в плане, карточках, спецификации и критериях приёмки. В облачный Codex передаём согласованное задание на холст, затем на реализацию, тесты и выпуск на demo. Локальный Codex проходит чек-лист на demo и фиксирует результат. Новый продуктовый вопрос, обнаруженный при сборке или проверке, возвращаем в Work с контекстом и рекомендацией. Окончательное решение и приёмка остаются за Андреем.

### Когда Андрей просит команду для другого Codex

Дай одну короткую команду, готовую для вставки в нужный чат. Перед ответом сверь актуальный этап и ближайший СТОП в `docs/PROGRESS.md`, порядок передачи — в `docs/specs/README.md`. Назови блок и, при одобрении холста, точную ревизию. Сошлись на спецификацию, а перечень функций и уже согласованных решений опусти.

Если поручение включает выпуск на demo, доведи команду до передачи на локальную проверку: после зелёных CI и smoke облачный Codex готовит чек-лист и возвращает ссылку на demo и команду для локального Codex. Затем локальный Codex проходит чек-лист и фиксирует результат. Окончательная приёмка блока Андреем — после этой проверки и устранения найденных ошибок.

### Вопросы Андрею

К каждому вопросу, который задаёшь Андрею, приложи конкретный рекомендуемый ответ и коротко объясни, почему он подходит Korzina. Для продуктовых решений сверяй рекомендацию с лучшими сопоставимыми решениями на рынке по первичным источникам, например официальной документации продуктов. Укажи, какой подход подтверждает источник и что ты предлагаешь адаптировать для Korzina. Если прямого аналога нет, назови основание рекомендации и её допущение. Если есть существенный выбор, кратко укажи альтернативу и её последствия. Ответ Андрея фиксирует принятое решение.

## Как мы работаем блоками (решение Андрея 18.11.2026)

**Стандартный порядок любого блока:** карточки → спецификация → холст → правки Андрея в спецификацию → сервер → экраны → **локальная проверка** (чек-лист → локальный Codex на компьютере Андрея: браузер, Telegram, телефон) → приёмка — `docs/specs/README.md` «Стандартный порядок блока». Эталон — блок 2 «Покупка».


1. **Блок** — законченный сценарий, который в конце работает целиком (порядок блоков — `docs/PLAN.md`). Один чат Codex на блок, каждая задача — свой PR (черновик → CI один раз → вливание). Если память чата сжималась больше одного раза — новый чат: «Продолжай блок N».
2. **Карточки сверены заранее** (Work, `docs/tasks/README.md`). Всё, что делает другой блок, записано в «Не входит»: не рисуется, не показывается, не обсуждается. Элементы будущих блоков нигде не видны — ни на холсте, ни на demo (components.md «Элементы будущих блоков»).
3. **Сначала контракт, потом экран.** Серверная часть и контракт задачи (`src/shared/contracts`) делаются первыми; холст и экран берут те же поля.
4. **Вид собирают Codex и MagicPath** из UI-кита, шаблонов и токенов; **Figma Codex не открывает** — экраны собираются по спецификации блока (`docs/specs/`). **Холст разом** — для всех новых экранов блока и экранов, у которых меняется вид (DESIGN §5). Собирается из свежего `main`, первая строка — «Собрано из main <хеш>», только мобильная версия. Элементы кадров, которых нет в карточке, не рисуются: их нужно перечислить списком «В Figma есть, в карточке нет».
5. **Одобрение — только слово «одобряю»** по ревизии холста. «Ок», «принимается» и другие слова одобрением не считаются.
6. **Реализация** — задачи по порядку, без ожидания между ними. **Приёмка** — один отчёт со снимками и ссылкой на demo; Андрей смотрит demo один раз.
7. **Что важнее при противоречии:** решение Андрея (DESIGN §5а, DECISIONS) → одобренное и код в `main` → Figma.

## Золотые правила

1. **Один шаг — одна завершённая вертикаль**: схема → API → экран → тест → проверка в браузере → коммит. Не начинай следующую задачу, пока текущая не на demo.
2. **Переиспользуй, а не копируй.** Экран собирается из `src/ui` и шаблонов `src/app`. Нужен новый элемент — добавь его в UI-кит, а не в экран. Переходы, шапки, состояния загрузки, пусто и ошибки уже есть в шаблонах; на странице их заново не пиши.
3. **Сервер — источник правды** о цене, остатке, правах, статусе заказа и деньгах. Клиент только отображает и отправляет команды.
   **Экономно:** экран получает только то, что показывает; запрос — по индексу и без N+1; неизменившиеся данные не перечитываются; фон не работает без работы (`docs/PERFORMANCE.md`). Горячие пути — с тестом бюджета SQL.
4. **Маленькие файлы и задачи**: до ~200 строк, один компонент или модуль на файл. Без «на будущее»: не пиши код, которого нет в задаче. Если по ходу задачи нужно поменять UI-кит или дизайн-систему больше чем в 3 компонентах — остановись, запиши это отдельной задачей (`docs/tasks/<ID>.md` и строка в PLAN.md) и сделай её отдельным PR. Новые служебные скрипты (`scripts/`) и проверки CI — только по карточке задачи.
5. **Визуал — свобода, правила — нет.** Визуальные решения принимай сам: стиль из Figma, и для недостающих экранов тоже. Противоречия в деньгах, правах и заказах — в `DECISIONS.md` и вопрос Андрею.
6. Секреты, токены и данные покупателей — только в `.dev.vars` и Cloudflare secrets, никогда в Git.
7. `main` автоматически публикуется на `demo.korzina.app`. Работай в ветке `task/<ID>`, вливай в `main`, когда проходят проверки (`npm run check`).
8. **Lavka не трогаем.** Репозиторий `vir2ozz2009/Lavka`, ресурсы Cloudflare с префиксом `lavka-`, домены `korzina.app`, `app.`, `admin.`, `lavka.korzina.app` и поддомены её магазинов, её боты и компоненты в старом холсте MagicPath — только чтение и только когда карточка задачи или `docs/specs/README.md` («Как писать спецификацию») ссылается на Lavka. Свои ресурсы Korzina называем с префиксом `korzina-`.
9. **Дёшево без потери качества.** Новый платный сервис, платная функция Cloudflare или заметный рост расхода — не подключай сам: оформи варианты с ценой в `DECISIONS.md` по `docs/COSTS.md` и спроси Андрея.
10. **Экран — только после «одобряю».** Задача с экраном не вливается в `main`, пока Андрей не одобрил ревизию MagicPath (DESIGN.md §5, шаг 3). Демо-данные на холсте — без служебных названий. Любой PR, меняющий видимое покупателю (в том числе чистка и рефакторинг), вливается только при зелёном smoke на превью и со снимками в описании (TESTING.md §7); у экранных задач снимки превью стоят рядом с одобренным холстом и совпадают с ним (DESIGN §5 шаг 6).

## Продуктовые документы из Work

При работе в Work вливаем свои PR, если они меняют только `docs/` и `AGENTS.md` (карточки, спецификации, решения, бэклог), после зелёного Check. Андрей не пишет «влей PR #…». Перед началом работы делай `git pull` — там могут быть новые карточки и решения. PR с кодом по-прежнему вливает Codex.

## Постоянные разрешения Андрея

Это заранее данное согласие: не спрашивай его повторно, действуй.

- **Можно без вопроса:** ветки `task/*`, PR и вливание в `main`; ресурсы Cloudflare `korzina-demo*` и `korzina-preview*` (Workers, сборки, D1-миграции, R2, DO, Queues, секреты — значения не выводить); поддомены `demo.korzina.app` и `*.demo.korzina.app`; отправка кода UI (`src/ui`, `src/app`, экраны `src/features/*/ui`) в проект MagicPath «Korzina» `473310532867354624` по DESIGN.md §5; чтение Figma; сетевые запросы к demo и превью; установка npm-пакетов в пределах правила 4.
- **Только с отдельного «да» Андрея в чате:** prod (`korzina-prod*`, `korzina.app` без `demo.`), всё Lavka (правило 8), платные сервисы и тарифы (правило 9), удаление данных demo, которое нельзя восстановить, отправка куда-либо секретов, `.dev.vars` и данных покупателей (не бывает разрешено).

## Проверки

- Задача закрыта, когда выполнены критерии её историй и «Готово, когда» карточки.
- Объём проверки — по размеру изменения (`docs/TESTING.md` §1): локально — `check:fast` и `test:related`; полный `npm run check` выполняет **CI на PR** — локально его не дублируй (только если CI недоступен). Правило `check:arch` не отключай — исправь код или спроси Андрея.
- Пиши тесты только на правила (по критерию истории, деньги, права, изоляция, повторы, гонки, бюджет SQL горячих путей). Не пиши тесты внешнего вида, текстов, типов и библиотек (`TESTING.md` §2).
- Для UI: открой путь в браузере на ширине 390, проверь переходы, назад, загрузку, пусто, ошибку и повтор.
- Тесты правил денег, заказа и прав не удаляй и не ослабляй без решения Андрея.
- **Каждое решение Андрея — свой тест.** Каждый пункт §9 «Решения» спецификации блока и каждая строка `DECISIONS.md`, которую задача реализует, получает хотя бы один тест правила с номером решения в названии (`«§9.3 объединение переносит заказы, адреса и избранное»`). В отчёте задачи — таблица «решение → тест». Решение без теста — задача не готова.
- **Чек-лист локальной проверки покрывает спецификацию целиком:** в конце — таблица «пункт §9…§N и история → сценарий или автотест». Пункт без строки — чек-лист не готов (`docs/specs/README.md` шаг 7).
- **Тесты на каждом этапе блока** — `docs/TESTING.md` §8: тесты правил в PR с кодом, один сквозной e2e на блок (≤ 10 всего), каждая ❌ локальной проверки — регрессионный тест, `check` ≤ 90 с.
- **Новое подключай к старому.** Добавляешь данные покупателя или магазина (новую таблицу, поле, список) — найди все места, которые переносят, сливают, копируют или удаляют такие данные (слияние профилей и гостя, выход, уборка, удаление магазина), и включи новое туда. Каждое такое место — тест «после операции новые данные на месте».
- **Скорость без потери качества:**
  - PR открывай **черновиком** (`draft`) и пушь сколько нужно — CI на черновиках не запускается. Когда задача готова, переведи PR в «Ready for review»: CI (`Check`, smoke на превью) пройдёт **один раз**.
  - Пока идёт CI готового PR — не жди: начинай следующую задачу в новой ветке от `main` (читать карточку, серверная часть). Предыдущую вливай, как только CI зелёный. Перед тем как открыть PR новой задачи — `git rebase origin/main`.
  - Мелкие замечания Андрея по виду после одобрения (отступ, текст, цвет) — не новая ревизия на холсте, а строка в `PROGRESS.md` → «Мелкие правки», их делает следующая задача первым пунктом.

## Как заканчивать чат

1. Обнови статусы историй задачи в `docs/stories/README.md` (`сделано` — только если все критерии проверены на demo).
2. Обнови `docs/PROGRESS.md` **коротко**: текущая задача, следующий шаг, одна строка задачи (итог в 1–2 предложения, коммит, ревизия MagicPath, время по часам). Подробности — в `docs/progress/<ID>.md` (до 60 строк). Старые отчёты не перечитывай.
3. Закоммить и запушь. После вливания не жди `Demo smoke`: он идёт сам; его результат проверь первым делом в следующей задаче (`gh run list`).
4. Последней строкой напиши Андрею: `➡️ Этот же чат / Новый чат / Локальный Codex. Напишите: «…»`. Когда блок готов на demo — всегда сначала локальная проверка (`docs/specs/README.md`, шаг 7), и только потом «Одобряю».
